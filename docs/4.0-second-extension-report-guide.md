# 2차 구현 보고서 작성 기준

이 문서는 2026-06-19 이후 `회귀 코드` 2차 구현 보고서를 작성할 때 사용할 목차 구조와 서술 원칙을 고정한다.

## 1. 문서 목적

- 이후 대화 context가 요약되거나 리셋되더라도 보고서 작성 방향을 유지한다.
- `docs/report-prep/`의 기계 추출 자료, git log, 구현 메모를 외부 제출용 보고서 문장으로 정리할 때 사용할 기준을 제공한다.
- 구현 명세를 새로 정의하지 않는다. 기능 동작과 데이터 계약은 기존 active spec과 실제 구현을 우선한다.

## 2. 기본 서술 방향

2차 구현 보고서는 단순 기능 목록이 아니라, 1학기 최종 구현 이후의 안정화와 확장 과정을 설명하는 개발 기록으로 작성한다.

핵심 관점:

- 2차 구현은 새 기능 추가뿐 아니라 긴 악보 성능, 재생 안정성, 편집 UX, Practice Mode, 예제/매뉴얼/배포 준비를 함께 다룬 안정화 작업이다.
- 시행착오, rollback, 실사용 테스트 결과를 숨기지 않고 설계 판단의 근거로 정리한다.
- 과장된 완성 표현보다 현재 안정판의 의미와 남은 검증 항목을 명확히 구분한다.

## 3. 권장 목차

### 3.1 작업 개요

포함할 내용:

- 2026-06-19 이후 작업의 목적
- 1학기 최종 구현 상태에서 2차 확장으로 넘어간 이유
- 테스트와 사용자 피드백 준비를 위한 안정판 구축

### 3.2 2차 구현 요약

포함할 기능군:

- 레이아웃 편집 UI
- 트랙 레이어
- YouTube 동기화
- 부분 갱신 및 장악보 성능 개선
- 영역 선택, 복사/붙여넣기, Undo/Redo
- Practice Mode / 노래방 모드
- 예제 악보, 매뉴얼, 배포 준비

서술 초점:

- 기능군별 목표와 최종 달성 상태를 짧게 정리한다.
- “무엇이 추가되었는가”를 중심으로 쓰고, 상세한 시행착오와 구조 설명은 다음 장으로 넘긴다.
- 각 항목은 지나치게 길게 쓰지 않고 보고서 전체의 지도 역할을 하게 한다.

### 3.3 주요 구현 내용

기능별 상세 설명의 본문이다.

각 기능 절은 가능한 한 아래 순서를 따른다.

```text
문제
설계 판단
구현 방식
검증
후속 문제 발견
개선 / 재검증
```

서술 원칙:

- 기능별로 “문제에서 출발해 어떤 판단으로 구현했고, 테스트 후 무엇을 고쳤는지”를 설명한다.
- 시간 순서가 중요한 경우 기능 절 내부에서 검증, 문제 발견, 개선, 재검증 흐름을 반영한다.
- 각 기능의 테스트 결과는 별도 장으로 분리하지 않고 해당 기능 설명 안에 포함한다.
- 관련 모듈, 상태 흐름, renderer/audio/parser/analyzer 경계가 중요한 경우 파일명과 역할을 간단히 언급한다.
- commit hash는 필요한 곳에 근거로 붙이되, 본문을 commit 나열로 만들지 않는다.

기능별 강조 후보:

- 레이아웃 편집 UI: layout draft, row 추가/삭제/높이 조정, renderer 좌표계와의 연결
- 트랙 레이어: active/inactive track, 편집/재생 대상 분리, Practice Mode 대상 track 기반
- YouTube 동기화: iframe mode, offset, seek/pause/resume, 음수 offset 보정
- 성능 개선: partial rebuild, layer 분리, viewport bounded rendering, RAF batching, profiler
- 편집 UX: range selection, paste preview, undo/redo history, drag edit transaction
- Practice Mode: microphone pitch input, pitch/timing judge, combo/result UI, effect bonus, Pro/Easy 정책
- 예제/매뉴얼/배포: Supabase Examples, Manual, GitHub Pages staging, 사용자 테스트 준비

### 3.4 구현상 난점

이 장은 기능 목록을 반복하지 않고, 여러 기능을 관통하는 어려운 문제를 중심으로 정리한다.

포함할 난점 후보:

- 부분 갱신과 렌더링 성능
- 글리산도, 셋잇단, hold 결합 시각화와 오디오 연결
- 마이크 기반 pitch 판정 안정화
- Practice Mode의 공정성, 관대함, 실사용성 균형
- Supabase 예제 목록과 정적 GitHub Pages 배포 구조의 절충

서술 원칙:

- “어떤 기능을 만들었다”보다 “왜 어려웠고 어떤 제약 때문에 현재 구조를 택했는가”를 설명한다.
- 실패한 접근이나 rollback은 최종 판단의 근거로만 압축해서 쓴다.
- 구현 난점과 미완성 항목을 구분한다. 난점은 해결 과정 중심, 한계는 다음 장에서 다룬다.

### 3.5 현재 완성도와 한계

포함할 내용:

- 2차 구현 목표 달성 여부
- 현재 안정판의 의미
- 장기 테스트가 필요한 항목
- 2학기 공식 보고서에서 보강할 항목

서술 초점:

- 2차 구현 목표는 달성했지만, 장기간 실사용 테스트와 다양한 환경 검증이 필요하다고 정리한다.
- 저사양 환경, 다양한 마이크/브라우저, 실제 예제 악보, YouTube embedding edge case, Supabase 운영 상태를 후속 검증 항목으로 둔다.
- 후속 확장 후보와 현재 안정판의 범위를 분리한다.

### 8.1. 현재 원고와 재개 지점

- 검토한 원고: 로컬 `1. 개발문서/주간보고서/9월 2주차 보고서.pdf` (6페이지).

- 3.1.1에는 gliss / glissChain을 eventId 기반 별도 pitch group으로 취급하는 이유와 동일 경로 중복을 별도로 검출하지 않는 한계가 작성되어 있다.
- 3.1.2 `출력 limit 설정`에는 gainScale만으로 합성 신호의 피크를 제어하기 어려운 이유, DynamicsCompressorNode 도입, masterGain 이후 출력 경로와 흐름도가 작성되어 있다.
- 3.1.2의 추가 문단은 대화에서 제안했으며, 아직 PDF 반영 여부를 확인하지 않았다. 다음 작업은 이 절을 마무리한 후 3.2를 작성하는 것이다.
- 3.2는 기존 오버랩 방식의 그림과 일부 소제목만 배치된 초안이다. 목차에는 기존 방식의 한계, 체인 전환, GlissPlaybackChain과 장음 extension, AudioGlissChainScheduleEvent 변환, 단일 oscillator 재생, 회귀 검증 순서가 잡혀 있다.
- 보고서의 2장은 이번 주 보강, 3장은 이전 보고서에서 다루지 않은 방학 후반기 오디오 보강이다. 기존 체인 도입과 이번 tuplet 판정 수정의 시점을 혼동하지 않는다.

### 8.2. 3.1.2에 추가할 설명

실제 구현 근거는 `regression-code/src/audio/oscillator_backend.ts`의 `createMasterLimiter()`이다.

| 설정 | 값 | 설명 |
| --- | --- | --- |
| threshold | -6 dB | 압축 기준 레벨 |
| knee | 6 dB | 기준 레벨 부근의 완만한 압축 전환 |
| ratio | 12:1 | 압축 구간에서 출력 레벨 증가 억제 |
| attack | 0.003초 | gain 감소 반응 시간 |
| release | 0.08초 | gain 회복 반응 시간 |

- 설정값 표와 2~3문단이면 충분하다. 흐름도의 모든 함수를 다시 설명하지 않는다.
- gainScale은 이벤트 중복 수와 활성 pitch group 수를 기준으로 개별 발음을 사전 보정하고, masterLimiter는 전체 볼륨 적용 후 합성 신호에 압축을 적용한다. 두 처리는 대체 관계가 아닌 보완 관계이다.
- 코드 이름은 masterLimiter이지만 실제로는 높은 압축 비율의 DynamicsCompressorNode이다. 고정 출력 상한이나 모든 클리핑·왜곡 제거를 보장한다고 서술하지 않는다. 설정값을 측정으로 입증한 최적값이라고 표현하지 않는다.
- attack / release는 API상 각각 gain이 10 dB 감소 / 회복하는 데 걸리는 시간이다. 단순한 시작 지연이나 완전 복구 시한으로 설명하지 않는다.
- 출력 압축은 발음 연결의 끊김을 해결하지 못한다는 점으로 3.2의 체인 구조 개선 설명에 연결한다.
- 제목 후보: `출력 피크 억제를 위한 압축 처리`.
- 참고: [MDN DynamicsCompressorNode](https://developer.mozilla.org/en-US/docs/Web/API/DynamicsCompressorNode). 이번 검토에서는 파라미터 의미 확인에 사용했으며 외부 코드를 복사한 것은 아니다.

### 8.3. 오디오 흐름도 검토 결과

대상: 로컬 `1. 개발문서/이미지/오디오 흐름.png`.

- 수정본의 직렬 신호 경로와 tremolo 없는 경우의 우회, masterGain에서 각 발음 출력이 합산되는 구조는 개념적으로 확인했다.
- 발음별 경로: oscillator → 선택적 tremoloGain → dynamicsGain → scaleGain → gain → 공유 masterGain → masterLimiter → AudioContext.destination.
- 효과 함수는 신호 전달 노드가 아니라 파라미터 자동화를 예약한다. 함수에서 제어 대상 노드로 가는 화살표는 점선으로, 실제 오디오 연결은 실선으로 구분하도록 제안했다.
- vibrato는 주 발음 oscillator의 detune을 제어한다. 별도 LFO는 제어 신호용이며 직접 출력되지 않는다. tremolo는 detune이 아니라 gain을 제어한다.
- 각 schedule 함수 내부에서 노드 생성과 주파수·효과 예약을 수행한다는 표기를 권했다. 호출 인수는 `backend.scheduleEvent(event, offsetSeconds)`로 표기한다.
- GainNode 사이의 ×는 직렬 gain 배율의 곱이라는 범례를 권했다. 이 표현 보완 사항의 최종 이미지 반영 여부는 미확인이다.

### 8.4. 다음 작성·검토 순서

1. 3.1.2의 설정값 표와 한계 설명을 원고에 반영한다.
2. 3.2.1에서 서로 다른 oscillator의 fade를 맞추는 방식과 연속 발음의 차이를 설명한다.
3. 3.2.2~3.2.5에서 체인 구성 → 일정 음정 / gliss segment 생성 → 하나의 oscillator에 주파수 변화 예약 순서로 설명한다.
4. 3.2.6에서는 스케줄 구조·시간·음높이 자동 검증과 사용자 청취 확인을 구분한다. 자동 테스트가 실제 청취 품질까지 검증했다고 쓰지 않는다.
