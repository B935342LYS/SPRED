# 2.13. 레이아웃 일괄 음정 매핑 이동 명세

최신 UI 결정: 사용자 후속 요청으로 반음 입력·실행 버튼을 `Pitch Shift [+] [−]`로 대체했다. String 드롭다운 왼쪽에 배치하며 클릭마다 선택 string을 1반음 이동한다. MIDI 0/127 경계에서는 해당 방향 버튼을 비활성화한다. 아래 입력 초기화·Enter 관련 설명은 최초 UI 구현 이력이며 현재 UI에는 적용하지 않는다. 음역·삭제 대상 수 요약과 기존 Apply 확인은 유지한다.

MinMidi·MaxMidi 검토: 현재 악기의 음역 정보 및 범위 밖 경고 기준이며 행 표시·재생 음정의 직접 기준은 아니다. 따라서 자동 이동은 필요하지 않으며 기존 값을 유지한다. 실제 악기 음역의 재설정은 별도 수동 편집으로 처리한다. OpenMidi도 유지한다.

## 1. 목적과 범위

Layout Editor에서 note 행의 음정 매핑을 같은 반음 수만큼 일괄 이동한다. 기존 레이아웃을 새로운 오타마톤에 대략 맞춘 뒤 필요한 간격을 수동으로 조정하는 시작점을 제공한다.

```text
기존 레이아웃 → 반음 단위 일괄 매핑 이동 → 미리보기 → 수동 간격 조정 → Apply
```

Regular·Deluxe·Techno 등 모델 차이와 같은 모델의 개체차 때문에 상대 음 간격이 항상 동일하다고 가정하지 않는다. 이 기능은 정확한 물리 위치 측정·자동 교정이나 기존 Layout Editor의 대체 기능이 아니다. 사용자가 전달한 상대 이동 아이디어를 기획 근거로 삼으며 외부 코드·알고리즘을 차용하지 않는다.

관련 기준: `2.4` Layout Editor, `2.5` 레이아웃 프리셋, `1.3` ScoreFile, `1.8` 런타임 파이프라인, `2.10` 편집 이력. 사용자 요청에 따라 단계별로 구현하며 중단된 3차 확장의 일괄 재개를 뜻하지 않는다.

## 2. 사용자 확정 사항

- 모든 대상 note 행의 pitch mapping을 동일한 정수 반음 수만큼 이동한다.
- 첫 UI는 반음 이동량 입력 방식이다. 예: `+2`, `-3`.
- 남는 음표의 원곡 음정은 유지한다. C4 행이 남으면 C4 음표는 변경 후에도 C4이며 새 레이아웃의 C4 위치에 표시한다.
- 기존 음표를 수용할 같은 음정 행이 없어지면 삭제될 셀을 안내하고 사용자 확인 후 Apply한다. 취소하면 현재 악보를 유지한다. 근처 음정으로 자동 이동하지 않는다.
- 일괄 이동과 저장 프리셋 재적용 모두 기존 삭제 안내·확인 흐름을 사용한다. 2026-11-03 후속 사용자 결정이며, 앞서 선택했던 음정 행 누락 시 Apply 차단 정책을 대체한다.
- 이동 후 기존 수동 편집으로 필요한 위치·간격을 미세 조정한다.

아래 UI 배치와 내부 ID 처리 등은 확정 요구를 만족하기 위한 설계 초안이다. 구현 착수 시 관련 기존 경로와 대조하여 확정한다.

## 3. 이동의 의미

물리적 위치는 draft 행 순서와 누적 height로 표현한다. 이동량을 Δ라 하면 대상 note 행의 새 MIDI는 `oldMidi + Δ`다.

| 같은 물리적 위치 | 이동 전 매핑 | +2 적용 후 매핑 |
| --- | --- | --- |
| A | C4 | D4 |
| B | C#4 | D#4 |
| C | D4 | E4 |
| D | D#4 | F4 |
| E | E4 | F#4 |

이 표는 행 위치의 매핑 변화이지, 그 행에 있던 악보 셀을 +2반음 조바꿈한다는 뜻이 아니다. 충분히 넓은 레이아웃이라면 기존 C4 음표는 새로 C4가 된 다른 위치에 표시된다. 위 다섯 행만 있는 레이아웃에서 C4 셀이 존재한다면 +2 이후 C4가 없으므로 해당 셀을 삭제 대상으로 안내한다. 사용자가 확인하면 삭제 후 적용하고 취소하면 현재 악보를 유지한다.

유지할 값:

- note/gap 행의 물리적 순서, 개수, 각 height, 전체 높이
- 전역 행, 열 너비, 열 수, 시간축, global cell
- 유지되는 악보 셀의 원곡 음정, col, rawText, track 및 string 소속
- 악보 metadata, 곡/Local offset, 트랙 활성 선택

변경할 값:

- 대상 note 행의 midi 및 MIDI 기반 표시명
- note/gap 행 ID 중 새로운 매핑에 맞춰 정합성을 조정해야 하는 값
- gap의 fromMidi/toMidi: 변경 후 인접 note를 기준으로 재계산

표시명을 바꾸는 작업과 셀 rawText는 구분한다. 사용자 셀 텍스트를 자동 치환하지 않는다.

## 4. 첫 지원 범위와 검증 초안

- 현재 Layout Editor에서 선택한 string의 note 행 전체를 대상으로 한다. UI에 대상 string과 행 수를 표시한다. 현재 단일 현 오타마톤에서는 전체 note 행이 대상이다. 다른 string까지 동시에 이동하는 기능은 포함하지 않는다.
- 유한한 정수 반음만 허용한다. 빈 입력·소수·NaN·Infinity는 실패로 처리하고 draft를 유지한다. 0은 변경 없음이다.
- 대상 note가 없으면 실행하지 않는다.
- 대상 note의 최저 MIDI를 m, 최고 MIDI를 M이라 할 때 허용 Δ 범위는 `-m .. 127-M`이다. 하나라도 0..127을 벗어나면 일괄 작업 전체를 거부한다. 클램프·일부 이동·음표 삭제로 보정하지 않는다.
- 단일 string 전체를 균일 이동하면 원래 중복이 없던 MIDI 관계는 유지된다. 최종 결과에도 중복·ID 충돌·string 참조·height를 검증한다.
- instData의 minMidi/maxMidi/openMidi는 자동 이동하지 않는 안을 사용한다. pitch mapping만 바꾼다는 범위를 지키며, 설정 음역 밖 행은 최신 `1.3` 정책대로 경고한다. MIDI 0..127 위반과 음역 metadata 경고를 구분한다.
- gap은 기존 인접 행 계산 규칙을 재사용한다. 양끝 gap도 보존하고 기존에 허용된 -1..128 경계 규칙을 따른다. 모든 gap 수치를 무조건 clamp하지 않는다.
- 행을 MIDI로 다시 정렬하거나 간격을 균등화하지 않는다. 미세 조정한 높이와 비균일 간격은 유지한다.

## 5. 기존 악보 보존과 행 ID

현재 `layout_apply.ts`는 새 note rowId 집합에 없는 셀을 삭제 대상으로 계산한다. `rowId`를 위치별로 고정한 채 midi만 변경하면 행 기준 음표의 의미가 달라지고, ID를 일괄 새로 만들면 기존 셀이 삭제될 수 있다. 어느 방식도 그대로 사용하지 않는다.

권장 설계:

1. Apply 전 현재 score의 note 행을 `(stringId, midi)`로 조회한다. rowId 문자열에서 MIDI를 파싱하지 않는다.
2. 새 draft의 같은 `(stringId, midi)` 행에는 현재 score에서 해당 음정을 가리키던 rowId를 유지하는 방향으로 ID를 정리한다. ID는 물리적 위치가 아닌 악보 참조를 보존한다.
3. 새로 들어온 음정의 행은 기존 생성 규칙에 맞춰 ID를 부여한다. 임의 ID가 포함된 외부 악보도 가능하므로 전체 ID 충돌을 검사하고, 무음 덮어쓰기 없이 실패를 보고한다.
4. gap ID와 인접 음정 경계를 재계산하고 draft의 선택 행 참조를 갱신한다. 선택은 가능하면 같은 물리적 행을 따라간다.
5. 모든 트랙의 기존 셀에 대해 원래 행의 `(stringId, midi)`를 새 레이아웃이 제공하는지 검사한다. inactive track도 검사한다. 빈 rawText를 가진 저장 셀도 임의 삭제하지 않는다.
6. 필요한 음정이 없으면 해당 셀을 삭제 대상으로 집계한다. 기존 삭제 확인 흐름에서 rowId·삭제 셀 수를 안내하고 string·음정 정보로 보완한다. 확인 시 집계된 셀만 삭제하고 취소 시 score를 변경하지 않는다. 활성 트랙만 검사하거나 같은 col끼리 병합하지 않는다.

이 방법은 유지되는 셀의 rowId·col·rawText를 보존하면서 같은 음정 행의 화면 위치만 바꾸는 것을 목표로 한다. 삭제가 없으면 `C4` 같은 절대음 토큰뿐 아니라 행 MIDI를 기본음으로 사용하는 입력, hold·tuplet·gliss 등의 기존 분석 의미도 보존해야 한다. 삭제를 승인한 경우 연결된 hold·gliss 등의 분석 결과는 기존 재분석 규칙에 따라 달라질 수 있으므로 전체 곡의 재생 결과가 동일하다고 보장하지 않는다. 단순 rawText 정규식 치환은 사용하지 않는다.

원본 score와 비교해야 하며 직전 이동 결과만을 ID 기준으로 삼지 않는다. `+2 → -2`, 반복 이동, 중간 행 추가·삭제 후에도 원래 음정의 ID가 복구될 수 있어야 한다. ID 처리의 구체 함수 계약은 구현 전 기존 draft 흐름에 맞춰 결정한다.

## 6. UI와 draft 흐름 초안

Layout Editor의 row 편집 영역에 다음을 둔다.

- `Pitch mapping shift` 제목과 대상 string 표시
- `Semitones` 정수 입력, 기본값 0, 현재 draft에서 가능한 최솟값/최댓값 표시
- `Shift mapping` 실행 버튼
- “행 간격과 남는 음표의 음정은 유지합니다. 범위 밖 셀은 확인 후 삭제됩니다. 적용 후 필요한 간격을 조정하세요.” 안내
- 이동 전/후 음역과 삭제될 셀 수 요약

입력만 바꾸면 draft를 수정하지 않고 버튼 실행 시 현재 draft에 Δ를 한 번 적용한다. 성공 후 입력은 0으로 되돌려 재클릭으로 같은 이동이 반복되는 것을 줄인다. 실패 시 입력과 기존 draft를 보존하고 이유를 표시한다. 성공한 이동은 기존 preview와 row 목록에 즉시 반영한다.

draft 이동은 유효한 레이아웃이면 허용한다. 수용할 수 없는 셀이 있어도 Apply를 비활성화하지 않고 기존 삭제 안내·확인을 거친다. 사용자는 확인 전에 이동량을 되돌리거나 필요한 행을 추가할 수도 있다. draft 편집이나 경고 표시만으로 현재 score의 셀을 삭제하지 않는다. 삭제 확인을 취소하면 score는 유지하고 draft는 추가 수정할 수 있게 둔다.

이동 후 간격 조정은 기존 Note Height·gap 높이·preview gap resize·행 추가/삭제 기능을 사용한다. 기존 note 행 MIDI 직접 편집은 현재 구현 범위가 아니므로 이 기능과 함께 자동 추가하지 않는다.

Cancel·Close·Escape는 미적용 draft를 버린다. Reset은 기존처럼 현재 score의 layout으로 돌아간다. 새 프리셋 로드·string 변경·재개방 때 이동량 입력과 미리보기 요약을 초기화하여 이전 대상의 입력이 새 대상에 적용되지 않게 한다. 대기 중인 파일 로드와의 우선순위는 `2.4`의 기존 요청 수명 규칙을 유지한다.

## 7. Apply·프리셋·되돌리기 경계

- 최종 Apply에서 현재 score와 draft를 다시 비교한다. UI의 사전 검사만으로 통과시키지 않는다.
- 일괄 이동과 같은 draft에서 수행한 수동 행 삭제를 최종 결과 기준으로 함께 집계하고, 기존 삭제 확인 경로를 재사용한다. 삭제 대상이 없으면 추가 확인 없이 적용한다. MIDI 범위 초과·ID 충돌 등 레이아웃 자체의 유효성 오류는 삭제 동의로 우회할 수 없다.
- 성공 시 기존 layout apply의 재생 reset·runtime rebuild·화면 갱신·편집 이력 초기화 정책을 따른다. 재생 중 실시간 조율이나 새로운 layout Undo를 추가하지 않는다.
- 데이터에는 적용된 midi/label/gap/ID 결과를 저장한다. 별도 영구 `pitchShift`나 악보 조바꿈 필드를 추가하지 않는다. ScoreFile·프리셋 formatVersion은 변경하지 않는 방향이다.
- 프리셋은 악보 셀을 포함하지 않는다. 이동된 레이아웃은 기존 Local/File Save로 저장할 수 있지만, 다른 악보에 적용할 때 필요한 음정이 모두 있다는 보장은 없다.
- 저장된 프리셋에는 “일괄 이동으로 생성됨” 표시를 추가하지 않는다. Local/File Load는 기존처럼 draft만 교체하고 최종 Apply에서 삭제 안내·확인을 수행한다. toolbar의 즉시 프리셋 적용도 실제 반영 전에 기존 삭제 확인을 거친다. 다른 악보의 임의 rowId까지 같은 음정으로 자동 재배치하는 범용 기능은 추가하지 않으며, 기존 프리셋의 ID 기반 호환 규칙을 유지한다.
- 외부 ScoreFile import의 구조 충돌 실패 정책은 유지한다. 손상된 rowId를 자동 복구하는 범용 reconciliation으로 확대하지 않는다.

## 8. 기존 기준과의 충돌 정리

| 출처 | 충돌 또는 차이 | 이번 초안의 해석 | 후속 문서 반영 |
| --- | --- | --- | --- |

## 9. 검증 계획

- +2/-3/0 이동, 옥타브 경계, 허용 최댓값·최솟값, 범위 초과·소수·빈 입력.
- note/gap 높이·개수·순서·전체 높이 보존 및 양끝 gap 경계.
- C4 행이 남으면 C4 셀은 이동 뒤에도 C4로 분석·재생되며 새 C4 행 위치에 표시됨. 행이 없어지면 삭제 안내 대상에 포함됨.
- 삭제 없는 이동에서는 일반 음·행 기준 음·hold·tuplet·gliss 등 분석 결과의 음정·시간·주법 보존. 삭제 승인 시 연결 이벤트는 기존 분석 규칙대로 재생성됨.
- basic/optional/extra 전체 검사, 비활성 트랙의 범위 밖 셀도 삭제 집계·확인에 포함.
- canonical/임의 rowId, ID 충돌, 반복 이동·원복, 중간 수동 수정, 다중 string의 비대상 행 보존.
- 실패·삭제 확인 취소 시 score·셀·이력·저장 슬롯 무변경. 삭제 확인 승인 시 안내된 셀만 삭제되고 남는 셀의 음정은 유지됨.
- Apply 후 ScoreFile 및 프리셋 왕복 저장 검증. Local/File 재로드 후 Apply와 toolbar 프리셋 적용에서 삭제 안내·확인·취소를 각각 검사.
- 입력·버튼·preview·Cancel/Reset/File Load를 브라우저에서 확인.
