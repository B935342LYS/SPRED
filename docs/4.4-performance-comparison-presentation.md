# 회귀 코드 성능 비교 발표 자료

> 발표·보고용 측정 자료입니다. 제품의 구현 명세가 아닙니다.

2026년 11월 18일 최종 시연 발표를 위한 성능 평가 정리입니다. 측정일은 2026년 11월 17일이며, 회귀 코드의 **산출물 재사용**과 **viewport 렌더링**이 계산 비용에 미치는 영향을 비교했습니다.

1,000열 합성 악보의 단일 셀 편집 실험에서 두 기능을 함께 적용하면 편집 시작부터 Canvas 명령 처리까지의 중앙값이 **6.05ms에서 1.30ms로 약 78.5% 감소**했습니다. 이 수치는 headless Chrome의 제한된 계산 구간이며, 실제 화면 표시 완료나 앱 전체 입력 지연을 뜻하지 않습니다.

## 발표에 사용할 핵심 표

### 두 기능의 적용 조합

**1,000열·1,302개 음표 셀·단일 셀 편집, 조건별 32회 측정. 단위 ms.**

| 산출물 재사용 | Viewport | 중앙값 | P95 |
| --- | --- | ---: | ---: |
| 없음 | 없음 | 6.05 | 7.70 |
| 있음 | 없음 | 4.45 | 5.80 |
| 없음 | 있음 | 3.25 | 5.30 |
| 있음 | 있음 | **1.30** | **2.20** |

측정 구간은 셀 변경 → 인덱스 생성 → 파싱·분석 및 렌더링 입력 생성 → Canvas 렌더 호출 반환입니다. 네 조건 모두 모든 레이어를 다시 그립니다. 여기서 부분 갱신은 **분석 산출물 재사용**으로 한정하며, 제품의 레이어 선택 재그리기는 포함하지 않습니다.

### 약 30초 설명 대본

> 편집 처리 비용을 줄이기 위해 두 가지 방식을 적용했습니다. 먼저 변경되지 않은 트랙의 분석 결과를 재사용하고, 화면을 그릴 때는 현재 보이는 영역과 주변 여유 범위만 처리합니다. 같은 1,000열 합성 악보에서 단일 셀을 편집하며 비교한 결과, 두 기능이 없을 때 6.05밀리초였던 계산과 Canvas 명령 처리 시간이 두 기능을 적용했을 때 1.30밀리초로 약 79% 감소했습니다. 이 수치는 화면 표시 완료까지의 지연이 아니라 해당 처리 구간을 측정한 결과입니다.

## 기능별 비교 결과

### 산출물 재사용의 효과

**Node 환경, 9,000열·11,802개 음표 셀, 조건별 51회 중앙값. 단위 ms.** Canvas 그리기를 제외하고 셀 변경·인덱스 생성·파싱·분석·렌더링 입력 생성까지 비교했습니다.

| 편집 작업 | 전체 재계산 | 재사용 | 감소율 |
| --- | ---: | ---: | ---: |
| 한 트랙의 1셀 변경 | 148.294 | 38.110 | 74.3% |
| 한 트랙에 32셀 삽입 | 148.827 | 38.006 | 74.5% |
| 세 트랙의 1셀씩 변경 | 153.378 | 157.209 | −2.5% |
| 첫 BPM 변경 | 149.565 | 1.938 | 98.7% |

재사용 효과는 편집 범위에 따라 달랐습니다. 세 트랙을 모두 변경하면 재사용할 트랙 산출물이 줄어들며, 이번 측정에서는 재사용 경로가 2.5% 느렸습니다. 따라서 부분 갱신이 항상 빠르다고 결론 내리지 않습니다.

### Viewport 렌더링의 효과

**Chrome 환경, 악보 시작 위치, 조건별 32회 중앙값. 단위 ms.** 이미 생성된 동일한 렌더링 입력을 사용하므로 편집·분석 비용은 제외합니다.

| 열 수 | 음표 셀 수 | 전체 폭 그리기 | Viewport 그리기 | 감소율 |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 126 | 0.50 | 0.40 | 20.0% |
| 500 | 651 | 1.80 | 0.35 | 80.6% |
| 1,000 | 1,302 | 3.55 | 0.50 | 85.9% |

화면 폭은 1,008px, 앞뒤 여유 범위인 overscan은 각각 252px입니다. 악보가 길어져도 viewport는 같은 폭을 대상으로 그립니다. 1,000열 악보의 중간 위치에서도 전체 폭 3.70ms, viewport 0.50ms로 측정됐습니다. 결과는 Canvas API 호출이 반환될 때까지의 동기 처리 비용입니다.

### 두 기능을 함께 적용한 효과

**Chrome 환경, 1,000열·1,302개 음표 셀, 조건별 32회 중앙값. 단위 ms.** 각 행은 편집부터 Canvas 명령 처리까지의 전체 구간을 직접 측정한 결과입니다.

| 편집 작업 | 둘 다 없음 | 둘 다 있음 | 감소율 |
| --- | ---: | ---: | ---: |
| 한 트랙의 1셀 변경 | 6.05 | 1.30 | 78.5% |
| 한 트랙에 32셀 삽입 | 6.10 | 1.55 | 74.6% |
| 세 트랙의 1셀씩 변경 | 6.70 | 3.50 | 47.8% |
| 첫 BPM 변경 | 6.55 | 0.70 | 89.3% |

전체 트랙을 변경하는 경우에도 viewport를 함께 적용하면 처리 비용이 줄었습니다. Node 실험과 브라우저 실험의 시간은 실행 환경과 범위가 다르므로 서로 더하지 않습니다. 감소율은 `(기준 중앙값 − 적용 중앙값) ÷ 기준 중앙값 × 100`으로 계산했습니다.

## 비교 조건과 측정 방법

### 실행 환경

| 항목 | 조건 |
| --- | --- |
| 측정 날짜 | 2026년 11월 17일 한국 시간 |
| CPU | AMD Ryzen 7 9800X3D |
| 운영 환경 | Windows x64 |
| Node | v24.12.0 |
| 브라우저 | Headless Chrome 157.0.8103.51 |
| 브라우저 배율 | zoom 1, DPR 1 |
| Viewport | 폭 1,008px, overscan 252px |
| 합성 악보 | 세 트랙에 같은 16열 패턴 반복, 패턴당 7셀 |
| 포함한 주법 | gliss, tuplet, hold, vibrato, tremolo |

### 입력과 반복 실행

각 실행은 동일한 편집 전 상태에서 시작합니다. 단일 셀은 basic 트랙의 8열 C를 `C@p(62)`로 바꾸고, 32셀 작업은 basic 트랙의 G 행 0~31열에 삽입합니다. 전체 트랙 작업은 세 트랙에서 같은 단일 셀 변경을 수행합니다. BPM은 첫 값을 120에서 140으로 바꿉니다.

- Node 비교: 100·1,000·9,000열, 각 조건 10쌍 워밍업 후 51쌍 측정. 전체·재사용 실행 순서를 번갈아 배치합니다.

- 브라우저 비교: 100·500·1,000열, 각 조건 4회 워밍업 후 32회 측정. 네 조건의 실행 순서를 회전하여 각 순서에 같은 횟수 등장하도록 합니다.

- 최초 로드와 상태 준비, bitmap 최초 할당, 검증, 콘솔·파일 출력은 측정 구간 밖에서 수행합니다.

- 느린 표본을 제거하거나 가비지 컬렉션을 강제로 실행하지 않습니다. 중앙값과 nearest-rank 방식의 P95를 기록합니다. P95는 정렬된 표본 중 95% 지점의 값입니다.

### 측정 범위

| 측정 항목 | 포함 | 제외 |
| --- | --- | --- |
| Node 산출물 비교 | 셀 변경, 인덱스 생성, 파싱·분석, 렌더링 입력 생성 | Canvas, DOM UI, 오디오, Undo 이력, 최초 로드 |
| Viewport 단독 비교 | 레이아웃 계산, 표시 범위 선별, Canvas 크기 확인, 그리기 명령 | 편집·분석, 최초 bitmap 할당, 화면 표시 완료 |
| 브라우저 네 조건 비교 | 편집·인덱스·산출물 생성부터 Canvas 렌더 호출 반환까지 | 레이어 선택 재그리기, DOM UI, 오디오, Undo 이력, 화면 표시 완료 |

Canvas 명령은 브라우저 내부에서 지연 처리될 수 있습니다. 각 표본 뒤 레이어별 1픽셀 읽기를 수행하여 대기 작업이 다음 표본으로 넘어가는 영향을 줄이고, 읽기 비용은 별도로 기록했습니다. 1,000열 단일 셀 편집의 읽기 포함 중앙값은 둘 다 없음 43.80ms, 둘 다 있음 4.10ms입니다. 이 값에는 읽기 자체의 비용이 포함되므로 발표의 핵심 표와 구분하며, 물리 화면 표시 지연으로 해석하지 않습니다.

## 검증 결과와 해석 범위

전체 재계산과 재사용 경로의 파싱·분석·렌더링 입력 내용과 순서를 비교하고, 원본 악보·기존 산출물의 보존을 검사했습니다. 무변경 편집이나 예상하지 않은 전체 재계산 fallback은 정상 표본으로 받지 않습니다. Node 도구는 실제 앱 편집 경로와도 결과를 대조했습니다. 빌드와 기존 부분 갱신 검사를 통과했습니다.

브라우저에서는 동일 화면 영역을 합성하여 근사 픽셀 비교를 수행했습니다. 전체 폭과 viewport는 그리드 레이어 구성 및 래스터 처리에 미세한 차이가 있어 픽셀 완전 일치는 아닙니다. 채널 차이가 8을 넘는 픽셀이 0.1% 이하이고, 채널 평균 차이가 0.1/255 이하이며 최대 차이가 64/255 이하인 조건을 적용했습니다. 검증한 이미지에서 표시 누락은 관찰되지 않았지만, 이 근사 검사가 모든 시각적 오류의 부재를 보장하지는 않습니다.

같은 화질을 유지하기 위해 브라우저 비교는 1,000열까지 수행했습니다. 9,000열 전체 폭 Canvas에는 해상도 축소와 bitmap 크기 제한이 개입할 수 있어 이번 표에 넣지 않았습니다.

이 결과는 **현재 코드에서 기능을 선택적으로 적용한 합성 입력 실험**입니다. 구버전과 신버전의 직접 비교, 실제 곡 전체의 성능 보장, 시연 노트북의 성능, 실제 입력 지연으로 일반화하지 않습니다. 발표에서는 “이 측정 조건에서 처리 시간이 감소했다”라고 설명합니다.
