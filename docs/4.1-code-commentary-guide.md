# 해설용 코드 주석 작성 가이드

## 1. 목적과 현재 상태

2026-10-15 사용자 요청으로 확정한 해설용 주석 작성 기준이다. 코드를 읽으며 보고서를 작성하고 면담에서 동작을 설명할 수 있도록, 선언의 역할뿐 아니라 내부 처리와 데이터 필드의 의미까지 코드 가까이에 기록한다.

2026-10-15 가이드를 작성했고, 2026-10-16 단계별 해설의 1A를 완료했다. 현재 범위와 다음 순서는 [4.2 단계별 계획](4.2-code-commentary-plan.md)과 해설본 README에서 확인한다.

적용 대상과 역할:

| 위치 | 역할 |
| --- | --- |
| `regression-code-report-commentary-2026-10-15/` | 이번 해설 작업 대상. 현재 active 구현에서 새로 복사한 코드 |
| `regression-code/` | 제품 동작의 기준. 이번 해설 주석 작업에서 수정하지 않음 |

| `regression-code-2026-06-19/` | 과거 면담용 자료. 최신 구현의 계약·흐름 판단 기준으로 사용하지 않음 |

이 가이드는 해설용 복사본의 주석 형식을 구체화한다. 저장 형식, 판정 규칙, 함수 계약 등 제품 명세를 변경하지 않는다. 동작 설명은 대상 코드와 관련 active 명세를 확인해 작성한다.

## 2. 사용자가 지정한 기준 예시

## 3. 주석 형식의 역할 분담

### 3.1 선언 앞에는 간소화된 JSDoc 유지

- 모듈 최상단: 담당 기능, 입력이 들어와 출력으로 나가는 큰 흐름, 인접 모듈과의 역할 경계를 짧게 설명한다.
- 함수 선언 앞: 무엇을 처리하는지, 각 인수의 뜻, 반환값과 실패·없음의 의미를 설명한다. 이름 있는 내부 함수, 화살표 함수, 반환 객체의 메서드도 포함한다.
- 객체 선언 앞: 객체 전체의 목적, 보관하는 상태나 설정의 역할을 설명한다. `export type` 등 타입 선언도 전체 계약을 간소화된 JSDoc으로 설명한다.
- 형식은 `/** ... */`이며 `@param`, `@returns` 대신 `- 인수 :`, `- 반환값 :`을 사용한다. 여러 인수는 각각 별도 줄에 쓴다.
- 함수가 아닌 모듈·일반 객체에는 억지로 인수·반환값 항목을 붙이지 않는다.
- 기존의 정확한 JSDoc은 유지하고 부족한 내용만 보충한다. 선언부 설명에 함수 내부 동작 전체를 몰아넣지 않는다.

```ts
/**
 * 검출 주파수를 가장 가까운 MIDI 음 번호와 그 음에서의 cent 편차로 변환한다.
 * - 인수 : frequencyHz : 검출된 주파수. 단위는 Hz
 * - 반환값 : MIDI 음 번호와 cent 편차. 유효한 음정으로 변환할 수 없으면 null
 */
```

### 3.2 블록 내부와 필드 설명에는 `//` 사용

- 함수·조건문·반복문·콜백 내부에서는 설명할 처리 바로 앞에 `//`를 둔다.
- 객체 리터럴·타입·인터페이스 안에서 설명이 필요한 필드는 바로 앞에 `//`를 둔다. 판별 유니온은 각 경우 앞에 의미를 쓰고, 필요한 경우 그 안의 필드도 설명한다.
- 설명이 여러 줄이면 각 줄을 `//`로 시작한다. 내부 동작 설명을 여러 줄의 `/* ... */`로 대체하지 않는다.
- 새로운 함수나 객체를 선언하는 지점의 JSDoc은 함수 내부에 있더라도 유지한다. 선언 설명과 동작 설명을 구분한다.
- 한 줄에 여러 필드가 있어 주석을 붙이기 어렵다면 의미를 바꾸지 않는 줄바꿈은 가능하다. 문법 구조나 필드 순서를 바꾸는 리팩토링은 하지 않는다.

## 4. 요구하는 설명 밀도

**큰 처리 블록에 요약 주석 하나가 있다는 이유만으로 해설 완료로 판정하지 않는다.** 처음 읽는 사람이 주요 호출과 상태 변화, 객체 필드를 따라가며 무엇이 어떻게 바뀌는지 설명할 수 있어야 한다.

설명 단위는 줄 수가 아니라 의미 있는 동작이다. 객체 생성, 설정, 연결, 입력 취득, 변환, 검사, 저장, 전달, 정리는 서로 다른 동작이면 별도 주석을 붙인다. 연결된 여러 줄이 하나의 연산이라면 한 주석으로 묶어도 된다. 필요한 경우 한 줄의 호출에도 주석을 붙인다. 짧은 코드라도 API의 효과나 데이터 계약이 분명하지 않으면 설명한다.

**단순하고 의미가 명확한 표현은 주석을 생략한다(2026-10-16 추가 원칙).** `ok: true`, `ok: false`처럼 문법과 역할이 분명한 값에 “성공을 표시한다” 등의 설명을 반복하지 않는다. 주변 주석이 이미 설명한 필드·대입에도 같은 뜻의 주석을 덧붙이지 않는다. 각 필드는 검토하되 모든 필드에 주석을 의무적으로 붙이지 않는다.

생략 여부는 길이만으로 판단하지 않는다. 단위·시간 기준·없음의 의미·부수 효과·원본 참조·후보와 확정의 차이처럼 코드만으로 알기 어려운 내용은 짧은 표현에도 설명한다. 판별 유니온의 경우별 계약은 유지하되, 그 아래 판별값 자체의 설명은 중복되면 생략한다.

다음 대상을 기본적으로 설명한다.

| 대상 | 설명할 내용 |
| --- | --- |
| 객체·버퍼 생성 | 무엇을 담는지, 누가 사용하는지, 언제 생성·재사용되는지 |
| API·다른 함수 호출 | 어떤 데이터를 전달하여 무엇을 얻는지, 상태 변경이 있는지 |
| 계산·변환 | 변환 전후 단위와 표현, 계산 결과를 사용하는 목적 |
| `if`·조기 반환 | 어떤 상태를 걸러 내는지, 분기 후 무엇을 처리하거나 생략하는지 |
| 반복·`map`·`filter`·`reduce` | 순회 대상, 선택·변환 조건, 결과가 저장되는 곳 |
| 상태 대입·배열 추가 | 후보 계산인지 현재 상태 확정인지, 기존 값의 유지·교체·누적 여부 |
| 비동기·콜백 | 언제 실행되는지, 대기 후 확인하는 상태, 취소·중복 방지 조건 |
| 리소스 정리 | 취소·해제·종료하는 대상과 그 소유 주체 |
| 반환 객체·필드 | 실제 의미, 값의 출처, 소비하는 단계, 단위·유효 범위·없음의 표현 |

좋은 설명은 처리 대상과 동작을 구체적으로 연결한다.

```ts
// analyser가 보관한 최신 시간 영역 파형을 재사용 중인 samples 버퍼에 복사한다.
analyser.getFloatTimeDomainData(samples);

// 복사한 파형과 AudioContext의 실제 표본 주파수를 Pitchy에 전달하여 Hz와 clarity를 얻는다.
const [frequencyHz, clarity] = detector.findPitch(samples, audioContext.sampleRate);
```

`// 분석한다`, `// 값을 저장한다`, `// 함수 호출`처럼 대상·효과를 알 수 없는 설명만으로 대체하지 않는다. 코드 식별자를 한국어로 번역하는 데 그치지 않고 그 값이 맡은 역할을 밝힌다. 설계 배경은 동작 이해에 필요한 경우에만 짧게 덧붙인다.

`?.`, `??`, 구조 분해, 스프레드, 판별 유니온, 콜백, 클로저 등 문법이 데이터 흐름을 이해하는 데 중요하면 해당 위치에서 효과를 설명한다. 일반 문법 교재 내용을 모든 사용처에 반복하지 않는다. 중괄호나 단순 증가 연산처럼 이미 설명한 동작의 기계적인 부분까지 줄마다 반복 설명할 필요는 없다.

## 5. 동작 설명 예시

아래는 `game_pitch_input.ts`의 처리 일부에 주석을 배치한 형식 예시다. 전체 함수나 실행 가능한 독립 프로그램이 아니며, 실제 코드를 수정하라는 지시도 아니다.

```ts
// 마이크 입력 노드와 분석 노드가 사용할 오디오 처리 환경을 만든다.
const audioContext = new AudioContext();

// 전달받은 MediaStream을 이 AudioContext에서 처리할 수 있는 입력 노드로 바꾼다.
const source = audioContext.createMediaStreamSource(stream);

// 입력 신호의 최신 파형을 읽어 올 분석 노드를 만든다.
const analyser = audioContext.createAnalyser();

// 각 분석 시점에 파형을 복사할 버퍼를 한 번 만들고 이후 호출에서 재사용한다.
const samples = new Float32Array(PITCH_ANALYZER_FFT_SIZE);

// 버퍼와 같은 개수의 표본을 처리하는 Pitchy 검출기를 만들어 재사용한다.
const detector = PitchDetector.forFloat32Array(PITCH_ANALYZER_FFT_SIZE);

// 분석 노드에서 읽는 표본 수를 버퍼·검출기의 입력 크기와 맞춘다.
// 이 값은 분석 창의 크기이며 분석 함수가 호출되는 간격이 아니다.
analyser.fftSize = PITCH_ANALYZER_FFT_SIZE;

// Pitchy 내부의 clarity 기준을 앱에서 사용하는 최소값으로 설정한다.
detector.clarityThreshold = MIN_CLARITY;

// 마이크 입력을 분석 노드로 연결하여 파형을 읽을 수 있게 한다.
source.connect(analyser);
```

이처럼 ‘마이크 분석 초기화’라는 한 문장 아래에 모든 단계를 숨기지 않는다. 해당 함수의 분석 반복 부분에는 파형 취득, RMS·주파수 계산, 유효성 검사, 프레임 전달, 다음 실행 예약을 다시 구분하여 설명한다.

## 6. 객체·타입 필드 설명 예시

### 6.1 결과 종류와 필드의 역할

아래는 10월 2주차 보고서 2.1.2절의 설명 방식을 필드까지 확장한 예시다. `applied`는 앱 상태를 이미 확정했다는 뜻으로 쓰지 않는다.

```ts
/** 악보 텍스트 편집의 계산 결과. 실제 앱 상태 확정은 호출 측에서 수행한다. */
export type ScoreTextEditResult =
  // 악보 변경과 파생 산출물 계산이 완료되어 적용할 상태 후보가 있는 경우다.
  | {
      kind: "applied";
      // 편집 이력 등과 함께 확정할 다음 상태 후보이며, 반환만으로 현재 상태가 바뀌지는 않는다.
      state: AppState;
    }
  // 유효한 요청이지만 악보 내용에는 변경이 없어 새 편집 이력을 만들지 않는 경우다.
  | {
      kind: "unchanged";
      // 호출 측에 전달할 상태이며, 필요한 UI 상태 처리 여부는 호출 측에서 결정한다.
      state: AppState;
    }
  // 처리할 수 없는 요청으로, 새 상태 대신 거절 안내를 전달하는 경우다.
  | {
      kind: "rejected";
      // AppState의 statusMessage와 같은 타입으로 전달하는 안내 메시지다.
      message: AppState["statusMessage"];
    };
```

### 6.2 값의 단위와 조건

필드 이름만 보고 의미를 추측하도록 두지 않는다. 특히 `null`·`undefined`·선택 필드, 시간 기준, 단위, 원시값과 채택값, 식별자의 사용 범위를 설명한다. 예를 들어 `GamePitchFrame`에서는 다음 차이를 드러낸다.

```ts
// performance.now()로 기록한 검출 처리 시각(ms). 악보 재생 시각과는 다른 기준이다.
capturedAtMs: number;

// Pitchy가 반환한 유한한 양수 주파수(Hz). 앱 필터에서 탈락해도 이 조건을 만족하면 보관한다.
rawFrequencyHz: number | null;

// 앱의 유효성 검사를 통과한 주파수(Hz). 통과하지 못하면 null이다.
frequencyHz: number | null;

// 검출값이 앱의 음정·clarity·RMS·음역 조건을 통과했는지 표시한다.
// 실제 연주 음정이 정확하게 검출되었음을 보증하는 값은 아니다.
isVoiced: boolean;
```

위 코드는 필드 주석 형식만 보여 주는 발췌다. 실제 작업에서는 대상 객체·타입의 각 필드를 검토한다. 선언부에서 설명한 계약을 객체 생성부마다 그대로 반복하기보다, 생성부에는 값의 출처와 조건부 대입처럼 그 위치에서 수행하는 동작을 보충한다.

`readonly`가 붙었다고 런타임에서 동결되었다고 설명하거나, 반환 배열을 실제 복제 없이 독립 snapshot이라고 설명하지 않는다. `capturedAtMs`를 하드웨어의 정확한 수집 시각으로, 후보 계산을 상태 확정으로, 비동기 함수 호출을 작업 완료로 바꾸어 설명하지 않는다.

## 7. 작업과 검증 절차

1. 사용자가 지정한 모듈·범위를 확인한다. 시작 지점이 정해지지 않았으면 임의로 전 파일 작업을 진행하지 않는다.
2. 이 가이드, 대상 코드, 실제 호출·소비 지점과 관련 active 명세를 읽는다. 이전 해설은 유용한 설명만 참고하고 최신 흐름에 맞는지 재확인한다.
3. 선언의 JSDoc을 유지·보충하고, 내부의 의미 있는 처리 단계와 객체 필드에 `//`를 붙인다. 기존 중복 주석은 정리하되 필요한 설명까지 축약하지 않는다.
4. 제품 코드와 기존 해설본에는 주석을 역반영하지 않는다. 코드의 호출 순서·조건·수치·식별자·타입·필드 순서·반환값을 바꾸지 않는다. 결함을 발견하면 별도로 보고한다.
5. 전후 비교에서 주석과 필요한 공백·줄바꿈 외의 변화가 없는지 확인한다. 가능하면 TypeScript의 구문 구조 또는 주석을 제외한 출력도 대조한다. 주석 제거용 단순 정규식만으로 동작 동일성을 단정하지 않는다.
6. 실제 코드 주석을 변경한 단위에서는 프로젝트의 정식 `typecheck`/`build`를 사용해 문법·타입 일관성을 확인한다. 해설본의 의존성이 준비되지 않았다면 검증하지 못한 범위를 기록한다. 문서만 작성한 단계에 제품 빌드를 반복할 필요는 없다.
7. 해설본 README에 완료 파일·다룬 범위·검증 결과·다음 위치를 남긴다. 함수 일부만 보강한 파일은 파일 전체 완료로 표시하지 않는다.

해설 완료 판단:

- 선언 앞에서 기능과 계약을 파악할 수 있는가?
- 함수 내부에서 초기화부터 반환·정리까지 주요 처리 단계가 설명되어 있는가?
- 분기의 조건과 효과, 반복 대상과 결과가 구체적으로 드러나는가?
- 객체 필드와 유니온 각 경우의 의미가 코드 또는 필요한 주석으로 분명하며, 자명한 표현의 중복 설명은 없는가?
- 단위·시간 기준·없음의 의미·후보/확정·원시/채택 구분이 정확한가?
- 중요한 API 호출은 입력과 효과를 설명하며, 실제 구현에 없는 동작을 약속하지 않는가?
- 기존처럼 큰 블록에 요약 한 줄만 달아 놓은 상태를 완료로 처리하지 않았는가?

## 8. 이전 지침과의 관계 및 다음 대화 재개

이전 해설본 README에는 주요 처리 블록을 `/* ... */`로 설명하고 기존 `//`를 흡수하는 완료 기준이 있다. 이번 사용자 지시는 **선언 앞의 간소화된 JSDoc을 유지하고 내부는 상세한 `//`로 설명하는 방식**이다. 새 작업에는 이 가이드를 적용하며, 이전 README는 과거 작업 기록으로 보존한다.

`AGENTS.md`의 ‘모든 줄에 주석을 달지 않는다’는 규칙은 줄마다 문법을 되풀이하지 않는다는 뜻으로 적용한다. 해설용 복사본에서는 의미 있는 개별 동작과 객체 필드까지 설명하는 높은 밀도를 요구한다. 제품 구현에 대한 간결한 주석 원칙과 혼동해 해설 밀도를 다시 낮추지 않는다.

다음 대화에서는 `docs/HARNESS.md` → 이 문서 → 새 해설본의 `README-commentary.md` 순서로 읽고, 사용자가 지정한 범위부터 재개한다. 가이드 작성 완료와 코드 주석 작업 착수·완료는 구분한다.
