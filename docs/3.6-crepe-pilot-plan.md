# CREPE 음정 검출 시범 도입 계획

작성일: 2026-09-18

상태: 사용자 검토용 계획. 기존 확정 원칙과 이번 권장안을 구분한다. 모델 설치·코드 구현·배포는 아직 수행하지 않았다.

## 1. 목적과 범위

현재 pitchy가 실제 악기 입력의 강한 배음을 기본주파수(F0)로 잘못 선택하는 문제를 CREPE가 줄일 수 있는지 확인한다. 정확도 개선뿐 아니라 빠른 음 이동, 입력 반응 속도, 브라우저 부하도 평가한다.

- 상위 기준: [3.4 detector 비교 및 채택 명세](3.4-practice-pitch-detector-backend-spec.md).
- 기존 계획: [3.5 5절](3.5-september-third-week-implementation-plan.md). CR-1~3 질문 ID를 그대로 이어 쓴다.
- 권장 완료 범위: 동일 WAV 비교 → 기준 충족 시 개발용 실시간 연결 → 채택/보류 결과 작성.
- 시범에서 성능이 부족하다는 결론도 유효한 결과다. 일반 사용자 배포와 기본 detector 교체는 결과 검토 이후의 별도 작업이다.

## 2. 현재 확인한 상태

| 항목 | 확인 결과 |
| --- | --- |
| 제품 detector | `regression-code/src/app/game/game_pitch_input.ts`에서 pitchy 직접 사용 |
| 입력 | AnalyserNode의 4096 sample, AudioContext의 실제 sample rate, RAF 기반 처리 |
| 현재 필터 | clarity 0.75, RMS 0.01, layout 음역 |
| 현재 시각 | sample 조회 직후 `performance.now()`를 `capturedAtMs`로 기록 |
| 공통 backend·비교 기반 | 3.4에 구현·rollback 기록은 있으나 현재 제품 경로에 해당 모듈은 없음 |
| 실험 브랜치 | 현재 로컬·remote-tracking branch 목록에 `experiment/practice-pitch-detection` 없음 |
| 원시 자료 | 현재 작업공간 파일명 검색에서 기준 WAV와 비교 runner를 찾지 못함. 다른 보관 위치의 부재까지 단정하지 않음 |
| 과거 비교 | 3.4에 pYIN/SwiftF0 채택 실패 기록. 삭제한 adapter나 임의 배음 보정은 재도입하지 않음 |

진행 위치 권장안: 구현 착수 시 최신 main에서 `experiment/practice-pitch-detection` 브랜치와 별도 worktree를 준비한다. 기존 작업 사본이 있으면 먼저 확인한다. `regression-code-extend/`를 자동으로 실험 위치로 삼지 않는다.

## 3. 유지할 확정 원칙

- 같은 원시 mono PCM을 두 detector에 제공한다. detector 결과 JSON만으로 재비교하지 않는다.
- 정답 악보 음정, 직전 pitch, 임의 octave 이동을 detector 입력이나 결과 보정에 사용하지 않는다.
- CREPE confidence에 pitchy의 0.75를 그대로 적용하지 않는다.
- RMS는 모델 입력 정규화 전 원시 신호에서 계산한다. 모델 정규화가 무음·작은 잡음을 확대해도 공통 필터가 유지되어야 한다.
- 판정 공식·효과 보너스·ScoreFile·parser/analyzer는 이번 실험에서 변경하지 않는다.
- 음성은 로컬에서 처리한다. 서버 업로드는 하지 않는다.
- 일반 사용자용 backend 선택 UI를 만들지 않는다. 개발 전용 선택과 로그로 비교한다.
- 모델 부하나 timestamp 오류를 기존 Input Sync/Display offset 값에 숨기지 않는다.

## 4. 모델과 실행 경로 권장안

### 4.1. 모델 크기

1. `tiny`로 초기화·전처리·출력 변환·실행 시간을 먼저 검증한다.
2. 같은 WAV를 `full`에도 입력해 큰 모델에서 개선 여지가 있는지 비교한다. full은 우선 offline 비교 대상이다.
3. full만 유효한 개선을 보이면 `small` 또는 `medium`을 추가해 정확도와 처리 시간의 절충점을 찾는다.

처음부터 모든 모델을 제품에 싣지 않는다. tiny의 실패를 CREPE 전체의 실패로 단정하지 않으며, full의 offline 성공을 실시간 성공으로 간주하지 않는다.

공식 데모는 원 모델보다 작은 모델을 사용하고 octave 오류가 늘 수 있다고 설명한다. 데모의 결과를 프로젝트의 품질 측정으로 대신하지 않는다. [공식 데모](https://marl.github.io/crepe/)

### 4.2. 실행 경로

| 후보 | 조사·검증할 사항 | 권장 처리 |
| --- | --- | --- |
| TensorFlow.js | 공식 데모/변환본의 출처, 현재 runtime 호환성, 원본과 동일 입력 결과 | 먼저 실행 가능성과 변환 재현성을 확인 |
| ONNX Runtime Web | ONNX 변환본의 원본 weight, 전후처리, opset, 실행 provider 지원 | TF.js와 비교 후 하나만 실시간 후보로 선택 |

라이브러리 선택은 사용자가 미리 정할 항목이 아니다. 작은 실행 검증을 거쳐 출처·호환성·속도에 근거해 결정한다. ONNX를 선택하면 3.4의 WASM CPU 기준 경로부터 확인하고 GPU 경로는 별도 측정한다.

`onnxcrepe`는 원 CREPE와 torchcrepe에서 변환·이식한 프로젝트이며 저장소 라이선스는 MIT로 확인했다. 이것만으로 특정 weight 파일과 모든 배포 의존성의 권리 확인을 완료했다고 보지 않는다. [README](https://github.com/yqzhishen/onnxcrepe), [LICENSE](https://github.com/yqzhishen/onnxcrepe/blob/master/LICENSE)

선택한 모델은 출처 URL, commit/release, variant, weight SHA-256, 파일 크기, converter/runtime 버전, 실행 provider와 라이선스를 기록한다. 라이선스 확인 후 모델과 runtime을 같은 사이트에서 제공하고, 실험 선택 시에만 지연 로딩하는 방식을 우선한다. Python 참조 실행은 개발용 수치 검증에만 사용한다.

## 5. 단계별 작업과 통과 조건

### 단계 A — 비교 자료 확보와 기준선 재현

- 기존 실험 코드·WAV 보관 위치를 확인한다. 복구가 어려우면 필요한 최소 캡처·runner만 다시 만든다.
- 같은 detector 입력 경로에서 명시적인 mono downmix 후 PCM/WAV를 기록한다.
- 과거 기준 WAV가 있으면 예비 비교에 사용한다. 없으면 실연 녹음과 합성 신호로 새 기준선을 만든다.
- 파일별 SHA-256, sample rate, sample 수, 채널 처리, 악기/장치/입력 설정을 기록한다.
- 현재 pitchy의 필터와 설정으로 먼저 결과를 재현한다. 과거 수치는 환경이 다른 현재 실행의 통과 기준으로 사용하지 않는다.

산출물: 데이터 목록, 녹음 metadata, pitchy 비교 JSON, 재현 명령.

### 단계 B — CREPE 전후처리와 변환 검증

- 공식 구현 기준인 16kHz 입력, 1024 sample frame(64ms), frame 정규화와 출력 Hz 변환을 재현한다.
- 44.1kHz/48kHz 입력을 명시적으로 resample한다. 저역 통과 필터가 없는 단순 sample 건너뛰기를 최종 경로로 사용하지 않는다.
- 원본 모델과 변환 모델에 동일한 frame을 넣고 activation·Hz·confidence 차이를 확인한다. 허용 오차는 평가용 corpus 비교 전에 기록한다.
- 첫 비교는 Viterbi smoothing을 끈 결과로 수행한다. 미래 입력을 사용하는 처리가 있으면 별도 실험으로 분리한다.
- warm-up과 반복 추론을 분리하고 tensor/model 자원 해제를 확인한다.

원본의 frame centering 및 전후처리 기준은 [CREPE core.py](https://github.com/marl/crepe/blob/master/crepe/core.py)를 따른다. TF.js는 첫 추론과 이후 실행의 비용이 다를 수 있으므로 초기 실행을 따로 측정한다. [TF.js 변환 안내](https://www.tensorflow.org/js/guide/conversion)

### 단계 C — 동일 WAV 품질 비교

- 3.4의 지속음·상하 gliss·실제 octave 도약·2~7 semitone 도약·vibrato·반복 attack·무음/잡음 코퍼스를 사용한다.
- 전체 채택 검증은 각 유형 3회 이상, 최소 두 입력 환경을 따른다. 예비 결과는 확보된 일부 자료라는 범위를 명시한다.
- 정답이 알려진 합성 신호와 실제 녹음을 분리한다. 실제 녹음의 불확실한 구간은 정답률 계산에서 제외하거나 별도 표기한다.
- 학습이 아닌 threshold 조정에도 평가 자료 과적합이 가능하므로 조정용 녹음과 최종 평가용 녹음을 분리한다.
- frame 크기가 다르므로 단순 frame 번호로 비교하지 않는다. 공통 시간 축에 정렬하고 raw 결과와 필터 통과 결과를 모두 보관한다.

| 평가 축 | 기록할 지표 |
| --- | --- |
| 음정 | 50 cent 이내 비율, 큰 음정 오류, octave/배음 오류, 지속음 jitter |
| 검출 유지 | 실제 음정 구간의 검출률, 무음·잡음 오검출률, 연속 검출 누락 길이 |
| 움직임 | 정상 도약 도달 시간, 빠른 gliss의 방향·도달음, vibrato/반복 attack 반응 |
| 실행 비용 | 다운로드 bytes, 초기화·warm-up, 추론 median/p95, 메모리 변화 |

오류가 줄어도 정상 입력을 대량으로 버린 결과라면 개선으로 판정하지 않는다. score의 pitch-class 판정으로 가려지는 octave 오류도 raw F0에서 평가한다.

산출물: backend별 시계열 JSON/CSV, 오류 구간 비교 그림, 지표표, 실시간 진입 또는 보류 이유.

### 단계 D — 통과 후보의 개발용 실시간 연결

- 공통 backend adapter를 만들되, pitchy를 분리하는 첫 변경은 기존 결과와 동작을 보존한다.
- 정확한 sample 구간과 원시 캡처가 필요하면 AudioWorklet/ring buffer를 수집 계층에 둔다. 무거운 모델 추론을 오디오 처리 callback 안에서 실행하지 않는다.
- 모델 추론은 동시에 하나만 실행하고, 밀린 요청을 무한히 쌓지 않는다. 처리 중 도착한 오래된 요청은 버리고 누락 비율을 기록한다.
- Promise 진행 중 입력 배열이 덮어써지지 않도록 frame을 소유하는 방식을 정한다.
- 중지·backend 전환·Practice 종료 시 이전 작업 결과를 세대 번호로 무효화한다. 모델·tensor·worker·마이크 자원을 정리한다.
- Worker 사용 여부는 선택 runtime의 지원과 main-thread 부하를 측정해 정한다. API가 비동기라는 이유만으로 UI가 막히지 않는다고 가정하지 않는다.
- 로드 실패·지속 성능 부족 시 실험 경로를 중지하고 pitchy로 돌아간다. 활성 backend와 원인을 로그에 남기며 비교 도중의 묵시적 전환을 허용하지 않는다.

### 단계 E — 판정과 보고

`test:game`, `build`, 같은 WAV 재실행, 장시간 실행·종료/재진입·실패 복구를 확인한다. 코드에는 기존 JSDoc 및 핵심 블록 주석 규칙을 적용한다.

최종 결론은 `제품 후보 / 조건부 재실험 / 보류` 중 하나로 정하고, 어떤 기기·음역·입력 환경에서 성립하는지 함께 기록한다. 최종 제품 반영에는 3.4의 모든 채택 조건을 적용한다.

## 6. 이번 Sync 개선과의 경계

CREPE의 64ms frame 길이는 곧바로 64ms의 추가 지연을 뜻하지 않는다. 현재 pitchy도 4096 sample window를 사용하므로 각 경로의 sample 구간과 대표 시각을 기준으로 비교해야 한다.

실험 로그에는 `frameStart`, `frameEnd`, 대표 음정 시각, 추론 시작/완료, 화면 반영 시각을 구분한다. CREPE의 중앙 기준 시각은 64ms window가 끝난 시점보다 약 32ms 앞선다. resampler 지연과 오디오 시계→performance 시계 매핑도 따로 기록한다.

현재 `capturedAtMs`는 조회 시각이라는 점을 보존해 기준선을 먼저 측정한다. 실시간 연결 전에 backend별 결과를 동일한 시각 계약으로 맞추는 변경과 그 영향을 검증한다. detector 완료 시각을 입력 시각으로 대체하거나 CREPE에 임의 고정 지연값을 빼지 않는다.

Input Sync는 입력 보정, Display offset은 화면 보정 역할을 유지한다. 기존 저장값은 자동 변경하지 않는다. backend 교체 후 사용자의 재보정 필요 여부는 측정 결과와 함께 판단한다.

## 7. 성능 기준을 고정하는 방법

3.4의 정성 기준을 유지하고, 첫 기준선 측정 후 후보 비교 전에 다음 허용치를 표로 고정한다: 검출률 하락, 무음 오검출 증가, 도약 반응 지연 증가, 추론 p95, 입력 누락 비율, 화면 반영 지연, 모델 다운로드 크기.

특정 숫자를 이번 계획에서 근거 없이 합격선으로 확정하지 않는다. 기기와 hop 간격이 정해진 뒤 값을 제안하고, 결과를 본 후 후보에 유리하게 변경하지 않는다. 수치는 보정용 자료로 정하고 별도 평가 자료로 검증한다.

속도 지표는 혼동을 피하기 위해 다음처럼 기록한다.

- 처리 배속 = 분석한 오디오 길이 / 처리 시간. `> 1`이면 실시간보다 빠르다.
- 처리 시간 비율(RTF) = 처리 시간 / 오디오 길이. `< 1`이면 실시간보다 빠르다.
- 3.4의 `sustained realtime factor > 1`은 전자의 처리 배속으로 해석한다. 실시간 적합성은 이 값뿐 아니라 p95, 입력 누락, 전체 반응 지연으로 평가한다.

| CR-2 | 실시간 성능을 판단할 기기는 무엇인가요? | 주 사용 데스크톱과 저전력 노트북, Chrome/Edge 우선 | 실제 사용할 CPU/GPU·브라우저 또는 기기명. 모바일은 이번 필수 범위에서 제외 권장 |
| CR-3 | 기존 원시 WAV와 실험 코드의 보관 위치가 있나요? 추가 녹음이 가능한가요? | 기존 오류 WAV로 시작하고 부족한 정상 도약·무음 자료를 보충 | 없다면 새 캡처부터 시작. 결과 JSON만 있으면 원시 녹음 필요 |

모델 크기·runtime·threshold·변환 방법은 기술 검증으로 정한다. CR-1~3 답변 후 이 문서를 갱신해 실행 범위를 고정한다.

## 9. 기존 문서와의 차이 및 출처

- **3.4의 aubio 우선 기록 ↔ 사용자 CREPE 계획 요청:** 이번 순서는 CREPE를 먼저 비교한다. aubio는 후속 후보로 남기며 3.4의 비교·채택 원칙은 유지한다.
- **3.4의 실험 기반 존재 기록 ↔ 현재 파일/브랜치 상태:** 역사 기록을 삭제하지 않고 복구 확인을 단계 A에 둔다. 현재 구현되었다고 가정해 작업량을 생략하지 않는다.
- **3.4의 RTF 표기 ↔ 통상적인 처리 시간 비율:** 7절처럼 양쪽 공식을 명시한다. 향후 3.4 현행화 시 용어를 통일한다.
