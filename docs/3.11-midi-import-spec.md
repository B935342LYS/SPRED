# MIDI Import 명세

작성일: 2026-10-30  
상태: 부분 확정 / 상세 변환 정책 협의 중 / 활성 작업본 구현 미착수

## 1. 목적과 적용 범위

MIDI 파일에서 선택한 트랙의 연주 정보를 변환하여 회귀 코드에서 편집할 수 있는 새 ScoreFile을 생성한다.

이 문서는 현재 대화에서 확정한 정책을 기록한다. 기존 실험본의 동작이나 검토 중인 제안을 모두 채택한 완성 명세가 아니다. 확정하지 않은 항목은 구현 전에 별도 결정한다.

- 구현 대상: regression-code/
- 참고 실험본: regression-code-extend/src/import/midi/
- 저장 계약: [1.3 ScoreFile](1.3-score-json-format.md)
- 선행 검토: [3.10 구조 검토 29~31절](3.10-code-structure-review.md)
- 기존 확장 후보: [3.3 확장 후보](3.3-third-extension-candidate-spec.md)

## 2. 결정 현황

| 항목 | 상태 | 내용 |
| --- | --- | --- |
| 출력 방식 | 확정 | 기존 악보에 병합하지 않고 새 ScoreFile 생성 |
| 곡 메타데이터 | 확정 | MIDI 텍스트·파일명에서 자동 추출/추정하지 않고 기존 기본값 사용 |
| 메타데이터 수정 | 확정 | 생성 후 기존 Details에서 사용자가 직접 입력 |
| 가져오기 진입 | 확정 | MIDI import 버튼으로 파일 입력 |
| 트랙 목록과 배정 | 확정 | 전용 UI에서 MIDI 원본 트랙 목록을 보여주고 사용자가 대상 레이어 지정 |
| 배정 관계 | 최초 일대일 선택 후 재검토 중 | 여러 원본 트랙을 하나의 대상에 병합하는 다대일 지원 여부는 미확정 |
| 채널 선택·분리 | 미확정 | 한 원본 트랙 내부의 여러 채널을 함께 가져올지 별도 선택할지 결정 필요 |
| 양자화·중첩·전역값 | 미확정 | 상세 규칙은 이후 협의 |

기존 ScoreFile에 병합하는 것과, 여러 MIDI 원본 트랙을 새 ScoreFile의 한 레이어로 합치는 것은 서로 다른 정책이다. 전자는 제외로 확정했고 후자만 현재 검토 중이다.

## 3. 새 악보 생성

1. MIDI 변환 결과는 독립된 새 ScoreFile이다.
2. 현재 악보의 note 셀, 전역값, 메타데이터에 MIDI 결과를 추가하는 병합 기능은 초기 범위에 포함하지 않는다.
3. 새 ScoreFile은 기존 저장 구조 및 검증 조건을 충족해야 한다. MIDI 전용 필드를 임의로 기존 셀에 추가하지 않는다.
4. 대상 레이어는 기존 basic / optional / extra를 사용한다. 세 레이어가 모두 존재하고, 입력이 없는 레이어는 cells: []로 표현한다. 이는 기존 ScoreFile 계약이다.

새 악보의 악기·레이아웃을 현재 악보에서 가져올지 새로 구성할지는 아직 정하지 않았다. “새 ScoreFile 생성”을 “현재 레이아웃을 반드시 폐기”하는 결정으로 확대 해석하지 않는다.

## 4. 메타데이터 정책

### 4.1. 기본값

| ScoreFile 항목 | 생성 정책 |
| --- | --- |
| musicData.musicTitle | "Unknown" |
| musicData.musicArtist | "Unknown" |
| musicData.musicGenre | "Unknown" |
| musicData.scoreWriter | "Anonymous" |
| musicData.comment | "" |
| musicData.createdAt / updatedAt | 기존 새 악보의 생성·저장 시각 정책 적용 |

곡 관련 텍스트는 생성 후 Details에서 사용자가 입력·수정한다. MIDI의 트랙명, 일반 텍스트, 저작권 문구 및 원본 파일명을 곡 제목·아티스트·장르·작성자·코멘트에 자동 대입하지 않는다. 원본 파일의 수정 시각을 악보 작성 시각으로 사용하지 않는다.

선택 난이도와 presetId는 기존 ScoreFile의 생략 허용 계약을 유지한다. MIDI 변환기가 이 선택값을 명시적으로 생성할지 생략할지는 세부 생성 정책에서 정한다. 이번 결정으로 필수 필드로 되돌리지 않는다.

### 4.2. 결정 근거

MIDI에 포함된 텍스트와 ScoreFile의 곡 제목·아티스트 등의 의미가 항상 일치하지 않는다. 추정값을 넣으면 사용자가 잘못된 내용을 삭제·수정해야 할 수 있으므로 메타데이터 자동 추출을 첫 구현에서 제외한다.

이는 곡 설명 메타데이터에 관한 결정이다. 음표, 템포, 박자처럼 악보 변환에 필요한 MIDI 정보의 분석까지 제외한다는 뜻은 아니다.

원본 트랙명·파일명을 가져오기 화면에서 식별용으로 표시하는 것은 곡 메타데이터 자동 입력과 구분한다. 트랙명은 목록 표시용으로 활용하는 안을 권고하며, 정확한 표시 형식은 UI 상세 설계에서 정한다.

## 5. 전용 UI와 트랙 배정

### 5.1. 확정된 기본 흐름

1. 사용자가 MIDI import 버튼을 통해 MIDI 파일을 입력한다.
2. 전용 UI에서 파일에 포함된 원본 트랙 목록을 표시한다.
3. 사용자가 가져올 트랙의 대상 ScoreFile 레이어를 직접 지정한다.
4. 배정 결과를 바탕으로 새 ScoreFile을 생성한다.

자동으로 원본 트랙 순서에 따라 대상 레이어를 확정하거나 트랙 이름을 곡 메타데이터로 사용하는 방식은 채택하지 않는다.

### 5.2. UI 세부 제안 — 미확정

| 요소 | 제안 |
| --- | --- |
| 트랙 식별 | 원본 트랙 번호와 이름 표시; 이름이 없으면 번호 기반 표시 |
| 보조 정보 | 음표 수 등 선택에 필요한 정보 표시 |
| 대상 선택 | 선택 안 함 / basic / optional / extra |
| 초기 배정 | 모두 선택 안 함 |
| 전역 정보 전용 트랙 | 음표가 없는 트랙은 구분 표시하고 레이어 배정과 전역값 수집을 분리 |
| 적용 절차 | 변환·검증 결과 확인 후 Apply에서 악보 교체 |
| 실패·취소 | 기존 악보 보존; 새 파일 선택 시 이전 요청 결과 무효화 |

이 표는 앞선 논의에서 제시된 권장안이며 전부 확정된 것은 아니다. 메뉴 내 버튼 위치, 중복 선택 UI, 적용 확인 및 상태 확정 후 출력 실패 처리도 상세 설계 대상이다.

## 6. 배정 관계 재검토

### 6.1. 논의 경과

사용자는 처음 일대일 대응과 수동 배정을 선택했다. 이후 여러 MIDI 트랙을 하나의 ScoreFile Track에 병합하는 경우의 구현 난도를 질문했다. 다대일이 가능하다는 검토는 수행했지만, 다대일 채택에 대한 최종 확정은 아직 없다.

따라서 현재 문서를 근거로 다대일 구현을 자동 착수하거나, 일대일 제한이 최종 확정되었다고 간주하지 않는다.

### 6.2. 선택지

| 방식 | 관계 | 추가 고려 |
| --- | --- | --- |
| 일대일 | 대상 레이어마다 원본 트랙 최대 하나 | 세 대상 레이어 기준 최대 3개 원본 트랙 선택. 단일 원본 내부의 음표 충돌은 여전히 발생 가능 |
| 다대일 | 여러 원본 트랙을 같은 대상 레이어에 배정 | 공통 시간축 유지, 중복 음·시간 중첩·양자화 충돌 처리 필요 |

원본 트랙 하나를 여러 대상에 복제하는 기능은 필요성이 논의되지 않았다. 별도 확정 없이 추가하지 않는다.

### 6.3. 병합 시 기술적 검토

| 상황 | 저장 가능성 및 결정할 사항 |
| --- | --- |
| 다른 시간의 음표 | 원본의 공통 시간축을 유지하여 같은 레이어에 배치 가능 |
| 같은 시간의 다른 음정 | 서로 다른 note 행에 배치 가능. 단선율화 여부는 별도 정책 |
| 같은 음정·시작·길이 | 중복 제거 후보. 처리 규칙은 미확정 |
| 같은 음정의 연속·겹침 | 하나의 음으로 합칠지 재발음을 유지할지 결정 필요 |
| 양자화 후 동일 좌표 | 한 트랙의 같은 (rowId, col)에 셀 하나만 저장 가능하므로 충돌 처리 필요 |

단순한 마지막 값 덮어쓰기는 채택하지 않은 상태이다. 병합 지원 여부와 무관하게 충돌·손실 보고 정책을 정해야 한다.

## 7. 이후 결정할 정책 순서

1. 일대일 유지 또는 다대일 허용 확정.
2. 트랙 내부 채널 처리, 음표 없는 트랙 및 타악기 취급.
3. 대상 악기·레이아웃 구성 방식.
4. 양자화 해상도, 최소 길이, 동일 음 재공격·겹침·좌표 충돌 처리.
5. 템포·박자 변화와 박자 분모의 변환.
6. 지원 SMF 형식·time division, sustain/pitch bend/velocity 등의 처리 범위.
7. 미리보기·경고·손실 보고, 적용·취소·실패 시 상태 유지.
8. 입력 용량·변환 규모 제한, 의존성·라이선스, 검증 사례 확정.

위 순서는 협의 진행안이며 개별 항목의 동작을 확정하지 않는다.

## 8. 기존 자료와 충돌하는 부분

| 출처 | 기존 내용 | 이번 해석·후속 조치 |
| --- | --- | --- |
| 3.3 4.2·4.4 | 새 ScoreFile 또는 현재 악보 삽입 | 새 ScoreFile 생성으로 범위 확정. 기존 후보 문구는 역사적 대안 |
| 3.3 4.3 | 타악기 제외, 단선율화 등 초안 | 현재 정책으로 자동 승계하지 않고 후속 협의 |
| 실험본 | 단일 target, 고정 선택·양자화, 첫 템포/박자 사용 | 재사용 검토 자료일 뿐 제품 확정 동작이 아님 |
| 최초 일대일 선택 | 일대일 수동 배정 | 수동 UI는 확정; 배정 cardinality는 이후 질문으로 재검토 중 |

관련 구현 경계는 storage/import/validation 및 앱 교체 흐름이다. 기존 parser/analyzer/renderer/audio 알고리즘 개편은 이번 정책 정리만으로 승인된 범위가 아니다.

## 9. 구현 및 검증 상태

본 문서는 정책 정리이며 MIDI 기능 구현 완료를 뜻하지 않는다. 활성 작업본의 MIDI 코드는 이번 작업에서 변경하지 않았다. 향후 변환 결과는 기존 validator와 parser/analyzer, 저장·재로드 경로까지 확인해야 한다.
