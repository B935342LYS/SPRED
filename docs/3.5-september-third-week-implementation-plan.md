## 1. 문서 역할과 결정 규칙

이 문서는 이번 작업의 범위, 구현 기준, 완료 조건과 미결정 사항을 한곳에 고정한다. 구현 상세를 임의로 확정하지 않고 사용자 답변으로 기준을 보완한다.

- **확정**: 사용자의 명시적 요청 또는 기존 유효 명세에서 확인된 기준이다.
- **제안**: 구현 방향의 추천안이며 사용자 결정으로 간주하지 않는다.
- **미결정**: 답변 또는 기술 조사가 필요한 항목이다. 관련 구현 방향은 확정하지 않는다.
- **현황**: 코드나 문서에서 확인한 사실이다. 문서에만 있는 과거 완료 기록은 현재 체크아웃의 구현과 구분한다.
- 답변을 받으면 질문 ID를 유지하고 결정 내용·날짜·근거를 기록한다. 반려된 제안은 확정 기준에 남기지 않는다.
- 일부 기능이 미결정이어도 다른 기능의 확정된 작업은 진행할 수 있다.
- 현재 요청은 계획 문서 작성이다. 이 문서 작성만으로 코드 변경, DB 갱신, 배포가 완료된 것으로 취급하지 않는다.

## 3. DB 접근 유지

구현 상태(2026-09-17): 로컬 구현·검증 후 사용자 요청에 따라 원본 `SPRED` main `ae04a82`, 배포용 `spredtest` main `6929c77`에 코드 변경 두 파일을 커밋·푸시했다. 배포판 typecheck/build 통과. 서버 인증 설정은 변경하지 않았다.

### 3.1. 구현 전 확인된 현황

- `regression-code/src/app/examples/example_binding.ts`는 Examples를 열 때 빈 접근 단어로 공개 목록을 요청한다.
- `example_supabase_provider.ts`는 Edge Function에 `{ accessWord }`를 전달한다. 클라이언트의 계정 로그인 세션 구조는 아니다.
- `2.11`은 접근 단어를 dialog 동안만 유지하고 닫을 때 초기화하며 localStorage/sessionStorage 저장을 금지한다.
- 여기서 사용자가 부르는 private DB는 현재 접근 단어로 열리는 테스터용 추가 카탈로그이다(DB-A1, 2026-09-16 확정).
- 실제 서버 설정, Storage 공개 여부, 토큰 발급 지원 여부는 이번 문서 작성에서 원격 확인하지 않았다.

### 3.2. 확정 기준과 구현 제안

확정 기준(2026-09-16 사용자 답변):

1. 대상은 기존 테스터용 추가 목록이다. 사용자별 계정 기능으로 확대하지 않는다.
2. 브라우저 종료 후 재방문하면 접근 단어를 다시 입력한다. localStorage를 사용하는 영구 기억 경로는 추가하지 않는다.
3. 접근 단어를 임시 보관하고 Examples 재진입 시 자동 입력한다.
4. 별도의 기억 옵션·지속 저장 관리 UI는 추가하지 않는다. 기존 제안의 기억/삭제 버튼·유지 일수 선택은 기본 범위에서 제외한다.

확정된 메모리 보관·재진입 방식(DB-A5~6 권장안 채택):

- 현재 페이지 실행 중의 메모리 변수에 서버 검증에 성공한 접근 단어만 보관한다. localStorage와 sessionStorage 모두 사용하지 않는다.
- Examples 창을 닫거나 예제 악보를 불러와도 이 변수는 유지하고, 다시 열 때 입력창에 복원한다.
- Examples 재개방 시 입력창에 복원한 단어로 공개·테스터용 추가 목록을 자동 요청한다. Load List를 다시 누를 필요가 없다. 보관한 단어가 없으면 기존처럼 공개 목록을 자동 요청한다.
- 명시적인 인증 거부 시 임시 값을 비우고 재입력하게 한다. 통신·서버 장애만으로 임시 값을 지우지는 않는다.
- ScoreFile과 URL에는 접근 정보를 넣지 않는다. 클라이언트의 임시 보관 여부만으로 서버 접근 권한을 인정하지 않는다.

페이지 새로고침·새 탭 진입·브라우저 종료 후 재방문에서는 다시 입력한다. Examples 창 닫기와 페이지 재로드를 구분하며, 전자만 임시 값을 유지한다.

## 4. DB 등록 시 재생 시간 추가

상태: **보류 확정(2026-09-16)**. 이번 DB 구현에 포함하지 않는다. 아래의 확정 답변과 검토안은 향후 재개를 위한 기록이며, 미결정 사항은 재개 시 보완한다. 기존 생성기의 null 등록과 DB 스키마·목록 표시 경로는 유지한다.

### 4.1. 확인된 현황

- `regression-code/dev/example_catalog_generator.html`은 등록 row의 `durationSeconds`를 `null`로 생성한다.
- 생성 SQL에는 이미 `duration_seconds` 컬럼과 upsert 갱신 구문이 있다.
- manifest와 목록 UI에는 재생 시간 전달·표시 경로가 있다.
- `2.11`은 재생 시간을 카탈로그 메타데이터로 정의한다. 현재 허용 값은 양의 정수 또는 값 없음이다.
- 현재 생성기의 `parseScoreJson()`은 JSON 구문, 일부 musicData 필드와 tracks 배열 등을 검사한다. 앱의 전체 ScoreFile validator를 호출하지 않으므로 등록 전에 모든 구조·시간축 오류가 걸러진다고 가정할 수 없다.
- 플레이어 전체 시간은 `app_playback_ui.ts`에서 `timeMapper.getDurationSeconds()`로 읽는다. mapper는 analyzer timing segment의 마지막 종료 시간을 사용하며, `formatPlaybackClock()`은 소수 초를 버려 표시한다. seek 입력값의 반올림과 시계 표시의 버림을 구분한다.

### 4.2. 구현 방향 제안

- 확정: 플레이어 영역에 표시하는 악보 전체 시간을 기준으로 한다(DB-T1).

- SQL 생성기는 계산된 시간을 등록 row에 넣는다. BPM 수식을 별도로 복제하기 전에 기존 코드 재사용 가능성을 확인한다.
- 정확한 내부 계산값과 목록 저장용 정수 변환을 분리한다.
- ScoreFile에 새로운 재생 시간 필드를 추가하는 것은 이번 기본 범위에 포함하지 않는다.
- 사용자 제안에 동의하는 실패 정책안: 선택 메타데이터인 시간 계산만 실패하면 `null`로 등록하고 생성기에서 해당 파일의 경고를 남긴다. JSON/필수 구조 검증 실패까지 포괄적으로 잡아 등록하는 방식은 사용하지 않는다.
- 정수 저장 제안: 플레이어 시계 표시와 같도록 초 단위 버림을 적용한다. 버림 결과가 0인 1초 미만 악보와 0초 결과는 현행 양의 정수 제약상 `null`로 둔다. 이 경계 정책은 아직 확정하지 않았다.

## 5. CREPE 시범 가동

### 5.1. 확인된 현황과 유지할 기준

- 현재 안정판 `game_pitch_input.ts`는 pitchy를 직접 사용한다.
- `3.4`에는 backend 인터페이스, WAV 캡처·동일 입력 비교 기반이 실험 브랜치에 구현되었다는 기록이 있다. 현재 위치와 실행 가능 여부는 착수 시 확인한다.
- 같은 문서에는 pYIN/SwiftF0 채택 실패와 rollback 기록이 있다. 이미 제거한 실험 경로를 이유 없이 재도입하지 않는다.
- 동일 원시 PCM/WAV의 offline 비교를 먼저 수행하고 통과 후보만 실시간으로 평가한다.
- 정답 note를 detector 입력으로 쓰거나 임의 octave 보정으로 결과를 맞추지 않는다.
- confidence는 backend별로 검증한다. pitchy의 `0.75` 기준을 CREPE에 그대로 적용하지 않는다.
- 모델 전처리, sample rate 변환, timestamp, 추론 지연을 adapter 경계에서 다룬다. 비동기 추론 중복과 종료 후 결과 반영을 막는다.
- 점수·timing·effect bonus 규칙과 backend 교체를 분리한다.
- 음성을 외부 서버로 보내는 실행 경로는 `3.4` 기준에 따라 제외한다.

### 5.2. 작업 단계 제안

1. 기존 브랜치·비교 도구·기준 WAV를 확인하고 pitchy 기준선을 재현한다.
2. CREPE 모델과 브라우저 실행 경로를 조사한다. TensorFlow.js와 ONNX 중 실제 변환 재현성·라이선스·실행 결과를 기준으로 선택한다.
3. 원본/변환 모델의 동일 입력 결과와 전후처리를 확인한다.
4. 동일 WAV로 F0, confidence, voiced 판정, 입력 시각, 처리 시간을 비교한다.
5. offline 기준을 충족하면 개발 전용 실시간 경로에 연결한다.
6. 결과와 한계를 기록하고 제품 채택 여부는 별도로 판단한다.

## 6. MIDI 데이터 구조 및 ScoreFile 생성 설계

### 6.1. 확인된 현황

- `regression-code-extend/src/import/midi/`에 parse, normalize, quantize, ScoreFile 생성 모듈이 있다.
- parser는 tempo event를 모으지만 `createGlobalCells()`는 첫 tempo와 첫 박자 정보를 사용한다.
- quantize는 note 시작·끝을 정수 column으로 반올림하고 최소 한 칸을 보장한다.
- 현재 parser는 SMPTE 시간 분할을 지원하지 않는다고 반환한다.
- `3.3`의 소수 tick 시간 보정 후보는 문법·단위·제약이 미확정이다. 예시 문자열을 사용 가능한 문법으로 간주하지 않는다.

### 6.2. 설계할 변환 흐름

1. **입력 해석:** SMF header, format, 시간 분할, track별 delta tick, note on/off, tempo, time signature, channel/controller를 조사한다.
2. **원본 정보 정규화:** absolute tick과 원본 track/channel을 유지하고 note 시작·종료를 연결한다. 중복·누락 이벤트 정책을 명시한다.
3. **기준 시간축:** 전체 tempo map으로 tick을 초 단위로 환산한다. tempo 변경을 가로지르는 노트의 길이는 `endSeconds - startSeconds`로 계산한다.
4. **표현 가능성 분석:** 노트 시작·종료와 tempo/박자 변경 위치를 기존 column·stepsPerBeat·tuplet 구조로 표현할 수 있는지 확인한다.
5. **변환 정책:** 정확히 표현 가능한 경우, 근사가 필요한 경우, 제외/실패시킬 경우를 구분한다.
6. **ScoreFile 생성안:** global cells, note/hold/tuplet, track·layout mapping을 정의한다.
7. **정합성 검증안:** 생성된 ScoreFile의 analyzer 결과와 원본 기준 시간축을 음별로 비교한다. 필요하면 오디오 schedule의 발음 경계도 확인한다.

tempo 변경을 단순히 첫 BPM으로 대체하지 않는다. 노트 길이만큼 전체 악보의 무음과 tempo 변경 위치도 검증한다. 세밀한 grid가 만드는 파일 크기·column 수·편집 성능 비용도 함께 평가한다.

### 6.4. 설계 완료 기준안

- 원본 MIDI 이벤트 → 정규화 정보 → ScoreFile 필드/셀의 대응표를 작성한다.
- PPQ tick과 ScoreFile beat의 관계, 박자표 분모, tempo가 없는 파일의 기본값을 명시한다.
- BPM 변경 경계를 가로지르는 긴 음, 매우 짧은 음, 같은 음 반복, 쉼표, 셋잇단음표, 겹치는 음을 사례로 설명한다.
- 같은 tick의 tempo event 충돌, velocity 0 note on, note off 누락, 같은 pitch 재입력, 범위 밖 음의 처리 정책을 적는다.
- 이벤트 수·pitch·음별 시작/종료 오차·전체 시간 오차·제외/근사 사유를 검증 결과 항목으로 정의한다.
- 기존 형식으로 보존할 수 없는 경우를 숨기지 않고 저장/문법 확장 필요성과 비용을 기록한다.
- 결정된 대표 파일과 기대 결과로 후속 구현을 시작할 수 있는 상태를 만든다.

영향 경계: 우선 import/validation 설계. 기존 형식 사용 시 parser/analyzer는 재사용·검증 대상이다. 소수 시간 문법을 도입하면 parser, analyzer, renderer, audio generator, 저장 검증까지 영향 분석이 필요하며 별도 결정 없이 확대하지 않는다.

## 11. Practice Display offset 구현과 후속 개선

### 11.1. 문제와 채택한 해결 방식

- 사용자는 오디오 인터페이스를 거치는 환경에서 Input Sync `+300ms`로 판정을 조절했지만, 악보가 왼쪽 경계 밖으로 가려진 뒤 연주해야 Perfect가 나오는 혼란을 보고했다.
- 코드 확인 결과 기존 스크롤은 원래 재생 시간을, 판정은 Input Sync를 적용한 시간을 사용했다. Input Sync가 악보의 붉은 기준선 좌표를 직접 옮기는 구현은 아니었다.
- 출력되는 소리와 화면을 맞추는 보정, 입력이 앱에 도착한 시점과 판정을 맞추는 보정을 분리했다. Input Sync 전체 값을 화면에도 그대로 적용하지 않는다.
- 기존 YouTube·오실레이터·입력 판정의 시간 관계를 유지하고, 고정된 붉은 기준선에 도착하는 악보의 viewport 위치만 조절하는 `Display offset`을 추가했다.

### 11.2. 구현된 기준

아래 표는 2026-09-17 최초 시범 구현 기준이다. 저장 수명과 Sync 설정 진입/종료 동작은 2026-09-18 후속 구현(11.8절)에서 갱신했다.

| 항목 | 현재 구현 |
| --- | --- |
| 설정 위치 | Practice Sync 팝업의 Display offset 영역. Input Sync와 구분 |
| 기본값·범위 | 0ms, -500~+500ms, 10ms 단위, 별도 Reset display |
| 양수 | 화면 진행을 늦춰 노트가 기준선에 더 늦게 도착 |
| 음수 | 화면 진행을 앞당겨 노트가 기준선에 더 일찍 도착 |
| 계산 | `displaySeconds = clamp(scoreSeconds - displayOffsetMs / 1000, 0, durationSeconds)` |
| 좌표 변환 | 보정된 초 → 기존 BPM time mapper → tick → 악보 x 좌표 |
| 적용 범위 | Practice 화면. 일반 재생에는 미적용 |
| 설정 수명 | 현재 페이지 메모리. Practice 종료·재진입 시 유지, 새로고침 시 0ms |
| 재생과 판정 | 실제 오디오·YouTube 재생/seek, Input Sync, 판정·종료 시각, 플레이어 시간 표시는 유지 |
| 즉시 반영 | 보정 버튼 조작 시 현재 재생/일시정지 위치의 viewport를 다시 계산 |

사용 순서는 **들리는 소리와 노트의 기준선 접촉을 Display offset으로 조절 → 연주와 판정을 Input Sync로 조절**한다. 현재 값은 실제 장치의 출력 지연을 자동 측정한 결과가 아니며 수동 보정값이다.

### 11.5. 후속 개선 A — Display offset 저장 후 재사용

상태: **2026-09-18 구현 완료**. Display offset을 별도 localStorage 키에 저장하고 재사용한다. 저장소 실패 시 페이지 메모리에서 계속 동작한다.

구현안:

- 기존 `infra/game_preferences.ts`의 Input Sync 저장 방식을 따라 Display offset 전용 localStorage 키와 load/save 함수를 추가한다.

- 조절 시 정규화한 값을 저장하고 Reset display는 0ms를 저장한다. 저장이 차단된 환경에서도 현재 페이지의 조절은 계속 동작하게 한다.
- 우선 브라우저별 공통 값 하나를 사용하며 기기·재생 방식별 프로필은 별도 확장으로 둔다.

요구 목표:

- Display offset 영역에 고정된 붉은 선과 그 선으로 다가오는 노트를 표시한다.
- 값을 바꾸면 노트의 위치 또는 선에 닿는 시점이 즉시 바뀌어 보정 방향과 양을 시각적으로 확인할 수 있어야 한다.
- Input Sync의 입력 marker와 Display offset의 노트 미리보기를 구분한다. 미리보기 때문에 기존 입력 판정이나 보정값이 변경되지 않게 한다.

확정된 후속 요구(2026-09-18):

- 일정 간격의 테스트 노트와 그에 대응되는 beep를 사용한다. 현재 악보를 미리보기에 복제하지 않는다.
- Sync 설정창을 열 때 악보가 재생 중이면 자동 일시정지한다. 오실레이터와 YouTube를 함께 일시정지하여 테스트 소리와 섞이지 않게 한다.
- 재생 위치와 Practice 점수 상태는 일시정지 정책에 따라 보존한다. 설정 중 입력은 calibration에 사용하며 일시정지한 악보의 점수 판정은 진행하지 않는다.
- 원래 정지·일시정지 중인 경우 재생을 새로 시작하지 않는다. countdown 중 설정 진입도 예약된 악보 재생이 뒤늦게 시작되지 않도록 처리해야 한다.

구현 제안:

- 고정된 붉은 선으로 일정 간격의 짧은 노트를 이동시키는 작은 미리보기로 시작한다.
- 반복 소리와 노트는 같은 기준 시간에서 출발하고, 화면에만 Display offset을 적용한다. 실제 청취 소리와 노트 접촉을 사용자가 비교한다.
- 기존 반복 beep와 공통 Start/Stop을 사용하는 구성을 우선한다. 노트 미리보기와 Input Sync meter에 별개의 테스트 소리를 동시에 실행하지 않는다.
- 기존 beep는 별도 AudioContext를 사용하므로 소리의 시작 시각·현재 악보 재생과의 관계를 확인한다. beep에 맞춘 결과가 YouTube에도 자동으로 맞는다고 단정하지 않는다.
- popup을 닫거나 미리보기를 중지하면 RAF·타이머·예약한 소리 등 해당 미리보기 자원을 정리한다. 다시 열 때 중복 실행되지 않게 한다.
- 미리보기에는 마이크 입력이 없어도 확인 가능한 노트 이동을 제공하되, 실제 음향 지연 측정은 수동 비교라는 점을 유지한다.

### 11.9. Sync 종료 후 재개 경로 및 버튼 배치 보완 — 2026-09-18

- 미세 조절 후속 확정: Display offset과 Input Sync 모두 `-10ms / -1ms / 값 / +1ms / +10ms / Reset` 순으로 배치한다. ±10ms 버튼 폭은 56px로 줄이고 값은 대칭 버튼 사이에 중앙 정렬한다.
- 두 보정값의 저장·복원·표시 정밀도를 1ms로 변경한다. 기존 ±500ms 범위와 Reset 기본값은 유지한다. 본 문서 앞부분의 10ms 정규화 기록은 최초 구현이며 이 결정으로 대체한다. `3.2`의 오래된 Input Sync ±200ms 표기는 실제 구현의 ±500ms에 맞춰 정정했다.
- 미세 조절 검증: `test:game`, TypeScript 포함 `build` 통과. Chrome에서 두 영역의 ±1/±10ms 증감, 버튼 폭·값 중앙 정렬, 새로고침 후 +1ms/+91ms 복원을 확인했다(`.agents/tmp/test-sync-fine.cjs`).

- 후속 사용자 의견: 악보 파일 자체의 타이밍이 빠를 가능성도 있으므로 이번 UI 보완에서는 오디오 동기화 로직을 추가 변경하지 않는다. 파일 결함 여부는 미확정이다.
- 미리보기 노트 중심의 기준선 접촉 시 작은 붉은 원형 효과를 표시하고 140ms 동안 감쇠한다. 노트와 동일한 AudioContext 시계 및 Display offset을 사용하며 별도 타이머나 beep 변경은 없다. Stop/닫기에서 효과 상태를 제거한다.
- UI 후속 검증: TypeScript 포함 `build` 통과. 로컬 Chrome에서 Start/Apply/Close 정렬, Reset 위치 복구, -500/0/+500ms의 접촉 직전·직후·감쇠·종료 정리를 확인했다(`.agents/tmp/test-sync-contact.cjs`).

- 사용자 보고: Sync 창을 닫고 재개한 실제 악보 오실레이터와 YouTube 사이에서 싱크 차이를 느낌.
- 확인 결과: Display offset은 화면 좌표에만 사용된다. 로컬 브라우저에서 +500/-500/0ms 변경 중 controller 시간, 오실레이터 예약 수, YouTube 호출 수, Input Sync 값이 유지됐다. 화면 보정값이 오디오 시간에 직접 적용되는 현상은 재현하지 못했다.
- 기존 `2.7` 5절은 재개마다 강제 seek를 요구했다. 같은 위치에서도 재탐색하는 경로를 확인하여, 일시정지 재개 시 영상 위치가 controller 기준 목표와 50ms 이내이면 seek를 생략하도록 해당 명세와 구현을 함께 보완했다. 최초 재생·위치 불일치·영상 시작 전 구간의 동작은 유지한다.
- 비교에는 controller 시간과 ScoreFile의 YouTube offset만 사용한다. Display offset을 오실레이터 예약이나 YouTube 위치 계산에 전달하지 않는다.
