## 3. 전체 구조 조사

### 3.1. 범위와 방법

`src/**/*.ts` 104개를 TypeScript AST로 읽고 정적 import/export의 로컬 모듈 참조를 확인했다. app 55개, core 21개, renderer 12개, audio 7개, infra 6개, orchestration 1개, track 1개, assets의 TypeScript 1개다. JSON/CSS/dev 테스트는 이 수에 포함하지 않는다.

이 조사는 동적 호출 그래프·런타임 순환·모든 함수의 책임 적합성을 검증한 것이 아니다. 타입 의존과 실행값 의존도 구분해서 해석한다.

유지할 기반:

- core에서 app/renderer/audio를 향한 정적 import가 없다.
- renderer와 audio 사이에 직접 정적 import가 없다.
- renderer item builder가 분석 결과를 표시용 데이터로 변환하는 경계가 있다.
- 편집 입력 합성, score 변경, 파생 산출물 생성, 이력 helper가 이미 분리되어 있다.
- 기능별 binding은 session 인터페이스로 외부 기능을 받는다. 다만 `setState(AppState)`의 권한 범위는 넓다.

## 5. 1단계: 편집·Undo/Redo 상세 검토

### 5.1. 기준 명세와 실제 흐름

- [2.2](2.2-ui-state-edit-mode-spec.md) 7.2: 재생성 실패 시 마지막 정상 score 보존, busy 해제, 오류 표시.
- [2.8](2.8-edit-invalidation-and-partial-rebuild-spec.md): 부분 산출물 재생성과 artifact 직접 렌더, 기존 오디오 재생성 유지.
- [2.10](2.10-undo-redo-edit-history-spec.md) 7.1: 실패 또는 무변경 patch는 이력에 기록하지 않음.
- 2.10 9절: Undo/Redo 후 selection/rangeSelection 해제.
- 2.10 10.2: partial rebuild 예외 시 오류를 표시하고 history stack 이동을 되돌림.

현재 호출 흐름:

```text
pointer click / RAF drag batch / range operation
  → session.applyScoreTextEdits (main.ts)
  → busy 표시
  → applyRawTextBatchEditToState (app_runtime.ts)
      → applyScoreCellRawTextBatch (edit_apply.ts)
      → createRuntimeDocument: 인덱스 재생성
      → partial artifact 또는 full fallback
      → 다음 AppState 반환; 실패도 AppState로 반환
  → 이력 patch 생성 또는 drag transaction에 요청 목록 누적
  → 선택적 성공 메시지 덮어쓰기
  → 렌더/UI 동기화
  → 재생 runtime 교체

Undo/Redo
  → pop helper가 만든 이동 후 history를 먼저 state에 저장
  → selection/clipboard 초기화
  → 같은 applyScoreTextEdits 호출 (recordHistory=false)
```

`popUndoHistoryEntry`/`popRedoHistoryEntry`는 기존 객체를 직접 변경하지 않고 다음 history 후보를 반환한다. 문제는 helper 자체보다 main이 후보를 편집 성공 전에 확정하는 순서에 있다.

### 5.2. 기존에 올바르게 분리된 동작

- `edit_apply.ts`는 편집 대상 track/global cell 배열을 복제하고 새 cell 객체를 넣는다. 실패한 후보 score는 반환되지 않으므로 기존 score 변경을 막는 기반이 있다.
- runtime wrapper는 편집/산출물 생성 예외를 잡아 이전 document와 산출물을 유지하고 busy를 idle로 반환한다.
- history patch는 요청 개수가 아닌 실제 before/after rawText 차이를 기록한다. 같은 좌표는 하나로 합친다.
- 빈 patch의 push는 기존 history를 그대로 반환하므로 일반 편집 실패가 가짜 이력을 추가하거나 redo를 비우지는 않는다.
- drag는 시작 score와 종료 score의 순수 차이를 한 entry로 묶는다. 실패한 batch를 요청 목록에 넣더라도 변경되지 않은 좌표는 patch에서 제외된다.
- pointercancel은 현재 구현·2.8 기준으로 pending 편집을 flush하고 이력을 끝낸다. 이름만 보고 전체 드래그 rollback으로 바꾸지 않는다.

### 5.3. 발견 사항과 우선순위

#### E1. 실패한 Undo/Redo의 이력 이동과 오류 은폐 — 우선 수정 후보

- 근거: `main.ts`의 `applyUndo`/`applyRedo`는 history를 먼저 교체한다. `applyScoreTextEdits`는 하위 결과의 성공 여부를 확인하지 않고 `statusText`를 info로 덮는다. `app_runtime.ts`의 wrapper 반환형은 `AppState`다.
- 관측: 재생성 실패 반환을 주입하면 document는 동일하지만 undo/redo stack은 이동한다. 메시지는 `Undid:`/`Redid:`가 되고 렌더·재생 초기화도 실행된다.
- 영향: 악보와 이력이 가리키는 상태가 달라지고 사용자가 실패를 알 수 없다.
- 최소 변경안: runtime 편집 결과에 성공/실패를 명시하고, history 후보와 다음 document/artifacts를 성공한 뒤 함께 확정한다. 실패 시 기존 history와 오류를 유지한다.
- 검증: Undo와 Redo 양방향의 mutation 거절 및 rebuild 예외, document/artifact/history 참조 보존, 성공 메시지 부재, 후속 호출 억제.
- 한계: 장애 주입으로 후속 제어 흐름을 확인했다. 유효한 사용자 악보에서 자연 발생한 analyzer 예외를 재현한 것은 아니다.

#### E2. 실패·동일 값 편집도 렌더와 재생 교체 실행 — 개선 후보

- 근거: `main.ts`의 후속 호출에 성공/변경 여부 분기가 없다. `edit_apply.ts`의 `updated`는 실제 변경 cell 수가 아니라 `edits.length`다.
- 관측: 실제 201자 거절은 document/history를 유지하지만 렌더·재생 reset 호출은 각각 1회 발생한다. 동일 rawText 재입력은 이력은 늘지 않지만 document를 새로 만들고 reset한다.
- 영향: 실패한 입력에도 후속 비용이 발생한다. 재생 중이면 위치 보존 reset 경로가 pause 상태로 교체하므로 불필요한 재생 상태 변화 가능성이 있다. 실제 청감은 이번 검사 범위 밖이다.
- 최소 변경안: 우선 실패 결과에서 후속 호출을 차단한다. 무변경은 별도 `unchanged` 결과로 구분하되 중복 좌표의 최종 값, 생성 후 삭제, 원래 값 복귀를 함께 검토한다.
- 검증: 동일 값, 없는 cell 삭제, 한 batch의 중복 좌표·최종 원복, redo 보존, drag 순변경 0건.
- 성능: 재생성 호출 사실만 확인했다. 시간 절감량·체감 개선은 측정하지 않았다.

#### E3. Undo/Redo 성공 후 selection 해제 불일치 — 작은 정합성 수정 후보

- 근거: main에서 먼저 selection을 null로 만들지만 `applyRawTextBatchToScore`가 마지막 edit 좌표를 다시 selection으로 넣는다.
- 관측: 실제 runtime·history helper를 사용한 정상 Undo/Redo에서도 마지막 edit의 col이 selection에 남는다. rangeSelection은 null 상태다.
- 영향: 내부 상태가 2.10의 해제 정책과 다르다. 눈에 보이는 UI 결함은 별도 확인 대상이다.
- 최소 변경안: 일반 편집의 선택 갱신과 Undo/Redo 성공 후 선택 해제를 구분해 최종 commit에서 적용한다.
- 검증: 일반 cell 편집 선택 유지와 Undo/Redo 선택 해제를 함께 검사한다.

#### E4. runtime 밖 부수효과 예외의 복구 책임 미정 — 설계 검토 후보

- 근거: main의 `finally`는 profiler 종료만 한다. busy 표시 후 UI 동기화, 이력 생성, 렌더, 재생 교체는 runtime wrapper의 catch 밖이다.
- 관측: 편집 전 `syncUiControls` 예외를 주입하면 busy가 applyingEdit로 남는다. commit 뒤 렌더 예외는 document/history 변경 후 재생 reset을 건너뛴다.
- 영향: 입력 잠금 지속 또는 화면·재생과 문서의 불일치가 가능하다.
- 최소 변경안: 계산/상태 확정과 DOM·오디오 반영 단계를 분리하고 실패 단계별 오류 처리를 둔다. 계산 실패 rollback과 이미 발생한 브라우저 부수효과 복구를 같은 것으로 취급하지 않는다.
- 미확정: 렌더/오디오 실패 후 문서 rollback, 새 문서 유지·재생 중지, 재시도 중 어느 정책을 채택할지는 현재 명세만으로 고정하지 않는다. 해당 구현에 착수하기 전에 사용자와 확정한다. E1 수정은 별도로 진행 가능하다.

#### E5. 범위 편집 UI 상태가 적용 전에 변경됨 — 후속 조사 후보

- 근거: `edit_pointer_binding.ts`의 delete/cut/paste는 선택·clipboard·preview를 먼저 바꾸고 반환값이 void인 `applyScoreTextEdits`를 호출한다.
- 영향 추정: 실패하면 이전 선택·붙여넣기 문맥을 잃을 수 있다. 드래그 pending 목록도 호출 전에 비운다.
- 최소 변경안 후보: 편집 결과를 호출자에게 전달하고, 성공 후 처리와 실패 복구를 명시한다. Cut의 clipboard 보존 정책은 별도로 확인한다.
- 한계: 호출 순서만 정적으로 확인했다. range DOM 상호작용 및 실제 브라우저 장애 재현은 하지 않았다.

#### E6. 이력 생성의 반복 선형 조회 — 성능 계측 후보

- 근거: `buildCellHistoryPatches`는 고유 target K개마다 before/after cell 배열을 `find`로 조회한다. 각 관련 배열 크기를 N이라 할 때 조회 비용은 최악 O(KN)이다. 좌표 중복 제거 자체는 Map을 사용한다.
- 개선 후보: 변경 대상 조회표 또는 이미 존재하는 인덱스를 사용할 수 있는지 확인한다. 새 전역 캐시를 먼저 추가하지 않는다.
- 우선순위: E1보다 낮다. 실제 큰 범위 편집의 history 시간과 lookup 준비 비용을 비교한 뒤 판단한다.

## 6. 최소 개편 제안과 적용할 개념

다음은 검토 제안이며 아직 제품에 반영하지 않았다.

1. **명시적인 결과 타입**: `applied / unchanged / rejected`처럼 결과를 구분한다. 오류 여부를 UI 메시지 문구나 level로 추측하지 않는다. E1의 첫 수정은 applied/rejected부터 시작할 수 있다.
2. **후보 계산 후 상태 확정**: 다음 document/artifacts/history를 지역 값으로 준비한 뒤 성공한 경우 한 번에 state에 반영한다. 기존 immutable history helper를 유지한다.
3. **계산과 부수효과 분리**: 편집 결과 계산과 render/playback 호출을 구분해 성공 조건과 예외 책임을 드러낸다.
4. **필요한 동작만 받는 인터페이스**: 검증 가능한 편집 조율 함수에 renderer·playback callback을 전달하는 정도부터 검토한다. 전역 DI 컨테이너는 필요하지 않다.

이는 결과를 구분하는 union, 상태 변경의 원자적 확정, 순수 계산과 외부 효과 분리라는 개념을 적용하는 안이다. Undo를 위해 Command 클래스 계층을 추가할 필요는 확인하지 못했다. 기존 patch history를 보존한다.

예상 영향 경계:

- app/edit 조율: 결과 해석, 이력 확정, 선택 해제, 성공 후 callback.
- runtime: 다음 산출물 또는 실패 결과 전달.
- parser/analyzer: 알고리즘과 출력 계약 유지.
- renderer/audio: 이번 E1 변경에서는 내부 알고리즘을 바꾸지 않고 호출 조건만 조정.
- storage/import/validation: 저장 형식·외부 import 기준 유지. 음수 열/미등록 rowId 방어는 별도 항목이다.

권장 작은 변경 단위:

1. E1의 결과 전달·성공 후 이력 확정과 E3 선택 해제. 실패 시 렌더/재생 호출 억제 포함.
2. E4의 전후 실패 정책 확정과 예외 경계 보완, E5 호출자 동기화 검토.
3. E2 무변경 생략과 E6 조회 최적화는 별도 검증·계측 후 반영.

## 10. 단계별 복구·범위 편집 UI 확정 — 2026-10-05

### 10.1. 확정한 정책과 구현

사용자는 화면과 재생 상태를 맞추고, 전체 refresh 하나로 실패를 처리하기보다 단계별로 책임을 분리하는 권장안을 수용했다. 확정된 악보·이력을 유지하는 정책, 잘라내기 삭제 성공 시 clipboard 확정 정책을 적용했다.

- `edit_commit_effects.ts`: 확정된 편집의 외부 효과 조율. 정상 화면 → 오디오 갱신. 화면 예외 → 모든 재생 중단 → 전체 표시 한 번 복구 → 성공 시 오디오 갱신. 복구 실패는 중단 상태 유지. 오디오 갱신 예외도 정리 후 실패 결과로 반환하며 자동 반복하지 않는다.
- 각 단계는 `ready` 또는 실패 단계(render/playback/stop)를 반환한다. main은 이 결과로 `outputSyncError`와 사용자 안내를 관리한다. 문서·이력 계산과 외부 효과를 같은 rollback 경계로 취급하지 않는다.
- `uiAfter`는 rangeSelection/rangeClipboard/pastePreview만 받는 제한된 후보 입력이다. range binding의 선행 setState·overlay 변경을 제거하고 삭제·잘라내기·붙여넣기의 성공 상태에 반영한다. 복사는 기존 독립 동작을 유지한다.
- 오류 상태는 busy와 별개다. Play·Seek·Practice를 모델 guard와 버튼 disabled 양쪽에서 막는다. 편집·Undo/Redo·저장·로드는 허용한다. 다음 편집은 전체 표시 경로부터 시도하며 화면과 새 재생 준비가 모두 성공하면 차단을 해제한다. 실제 소리는 자동 재개하지 않는다.
- 오류 상태의 전체 표시는 입력 악보를 다시 적용하거나 parser/analyzer를 재실행하는 refresh가 아니다. 이미 확정한 renderInput으로 표시만 다시 만든다.
- `resetPlaybackForCurrentStatePreservingPosition`은 새 runtime 후보와 일시정지 위치를 준비한 뒤 기존 것을 교체한다. 실패한 후보 controller와 backend를 회수한다. runtime 생성 도중 실패도 생성된 backend를 정리한다.
- 추가 발견: controller가 `ensureStarted()`를 기다리는 동안 stop/dispose한 뒤 준비가 완료되면 재생을 시작할 수 있었다. 실패 복구의 중단 보장을 위해 요청 세대와 disposed 상태로 취소를 연결했다. app의 비동기 완료에서도 교체된 runtime이나 중단 상태가 YouTube/RAF를 다시 시작하지 않도록 확인한다.
- 정리 동작은 애니메이션, controller, backend, YouTube pause, preview 순으로 각각 시도한다. 하나의 예외가 뒤의 정리를 막지 않는다. 정리 자체의 실패는 잠금을 유지하고 원인을 보고한다.

영향 경계: app/edit의 UI 후보·효과 조율, playback runtime 자원 수명, controller 비동기 요청 취소, playback/practice 진입 guard. parser/analyzer/renderer 알고리즘, audio schedule, 저장 JSON은 변경하지 않았다. 새로운 모듈은 현재 필요 동작 네 개를 callback으로 받아 조율하며 전역 이벤트 버스나 DI 컨테이너는 도입하지 않았다.

## 11. E2 무변경 batch 생략 및 비교 측정 — 2026-10-09

### 11.1. 범위와 구현

사용자는 기준 성능 측정→최소 구현→재측정에 동의했으며 개선이 미미하거나 악화되면 복원도 고려하도록 요청했다. 사용자 백업 커밋 `7d758f8`과 깨끗한 작업 트리를 시작 기준으로 확인했다.

- edit_apply는 기존 좌표 Map과 요청 좌표별 최종 edit Map을 이용해 최종 rawText/존재 여부를 비교한다. 입력 길이·필수 global 시작 셀 삭제·gap·트랙 검증은 유지한다. 중복 좌표를 합치기 전에 입력 제한을 검사한다.
- note/global 적용의 공통 비교를 내부 `applyCellEdits`로 묶었다. 최종 변경이 없으면 원본 score 참조를 반환한다. 공개 `updated` 필드는 호환상 요청 수 의미를 유지하며 변경 판정에 쓰지 않는다.
- runtime은 `applied` / `unchanged` / `rejected` 결과를 구분한다. 무변경이면 인덱스·분석·렌더 산출물 생성 전에 반환한다.
- main은 무변경 시 이력 계산·drag 요청 누적·악보 draw·재생 교체를 생략한다. 선택과 uiAfter 후보, busy·상태·overlay UI는 반영한다. 일반 무변경은 redo를 보존한다. historyAfter가 있는 Undo/Redo 명령의 스택 이동 정책은 유지한다.
- 기존 출력 오류 또는 새 UI 표시 오류는 기존 applyEditEffects 복구 경로를 이용한다. 무변경이라도 필요하면 전체 표시와 재생 교체를 수행한다.
- 한 batch 내부 원복과 여러 프레임에 걸친 drag 원복을 구분한다. 후자는 중간 실제 변경을 표시하고 종료 시 순변경 이력만 생략한다.
- 영향 경계는 app/edit의 순수 셀 적용, app_runtime의 계산 분기, main의 확정 후 효과 분기다. parser/analyzer/renderer/audio 내부 및 저장 형식은 변경하지 않았다. E6 이력 조회 비용 개선과 변경 batch의 추가 부분화는 미포함이다.

## 12. E6 이력 조회 상세 검토 — 2026-10-09

### 12.1. 현 경로와 원인

제품 코드 변경 전 조사다. 직전 E2 작업 트리를 보존하고 `edit_history.ts` 및 main의 일반 편집/drag 종료 호출을 확인했다. 고유 대상마다 before/after의 cells.find를 수행하므로 배열 길이 N, 대상 수 K일 때 최악 O(KN)이다. 같은 1,000개 대상이라도 배열 앞쪽이면 탐색이 일찍 끝나고 뒤쪽이면 대부분의 배열을 반복 확인한다. 앞선 E2 성능 fixture는 앞쪽 열을 사용했으므로 뒤쪽 범위의 이력 비용을 대표하지 않는다.

일반 편집은 `previousState.document.indexes`와 `nextState.document.indexes`가 이미 존재한다. `cellMapByTrackId`와 `globalCellMapByCoord`에는 필요한 rawText가 있다. drag는 시작 시 beforeScore만 보관하고 종료 시 전체 순변경을 계산하므로 시작 인덱스의 수명을 별도로 보존해야 한다.

### 12.2. 대안과 조사 측정

조사 코드 `regression-code/dev/benchmark_history_lookup.ts`는 제품 helper와 두 대안을 비교한다.

1. 현재 배열 find 방식.
2. 매 호출마다 before/after의 셀 Map을 새로 만드는 방식. 조회표 생성 비용 포함.
3. 이미 있는 runtime의 두 좌표 Map을 사용하는 방식. 기존 인덱스 생성 비용은 측정에서 제외한다. 이력만을 위해 인덱스를 새로 만들라는 제안이 아니다.

Node v24.12.0, Ryzen 7 9800X3D, 128/9,000셀, 1/64/128 또는 1,000개 대상, 앞/뒤쪽 편집을 비교했다. 조건별 5회 워밍업 후 21표본(표본당 5회 호출), 방식 순서를 번갈아 3라운드 실행하고 각 중앙값을 다시 중앙값으로 집계했다. 단위는 ms이며 아래는 대표 결과다.

| 셀 수 | 대상 수·위치 | 현재 find | 매번 Map 생성 | 기존 인덱스 재사용 |
| --- | --- | --- | --- | --- |
| 128 | 1·앞 | 0.00040 | 0.02028 | 0.00040 |
| 128 | 128·뒤 | 0.02476 | 0.06714 | 0.03076 |
| 9,000 | 1·앞 | 0.00026 | 1.98868 | 0.00014 |
| 9,000 | 1·뒤 | 0.01280 | 1.85138 | 0.00026 |
| 9,000 | 64·뒤 | 0.76472 | 1.79358 | 0.01542 |
| 9,000 | 1,000·앞 | 0.79406 | 2.25814 | 0.29232 |
| 9,000 | 1,000·뒤 | 11.27798 | 2.13686 | 0.24602 |

작은 악보 전체 편집에서는 인덱스 대안도 0.006ms 증가했다. 작은 차이의 통계적 유의성이나 전체 앱 속도 향상은 확인하지 않았다. 이 측정은 history helper만의 비용이며 DOM·분석·오디오·이력 스택 push는 포함하지 않는다. 큰 뒤쪽 범위에서 기존 인덱스 재사용의 이점이 명확해 후속 구현 후보로 채택하되, 브라우저 앱 명령 전체와 메모리 수명은 구현 단계에서 추가 확인한다. 현재 방식의 모든 문제를 임시 Map으로 해결하는 안은 작은 편집을 악화시키므로 권장하지 않는다.

기존 helper와 후보의 결과 동등성 25조건(성능 fixture 12개, 추가 6종의 정방향/역방향 12개, 누락/gap 1개)을 비교했다. 삭제·생성·원복·중복 좌표·global의 track 무시·patch 순서와 null 처리 등을 포함한다. 유효한 중복 없는 ScoreFile을 전제로 하며 잘못된 중복 셀 데이터의 find/Map 차이를 호환 대상으로 삼지 않는다. 최종 typecheck 통과. 제품 수정이 없으므로 제품 전체 빌드나 브라우저 회귀 검사는 이번 조사에서 반복하지 않았다.

### 12.3. 권장 구현 범위

- 이력 helper 입력을 필요한 두 Map만 갖는 읽기 전용 조회 계약으로 좁힌다. AppState/AppDom이나 새 전역 캐시는 받지 않는다.
- 일반 편집은 이미 계산된 전후 인덱스를 전달한다. 이력 때문에 별도 인덱스를 생성하지 않는다.
- drag 시작 시 두 Map의 참조만 담는 작은 snapshot을 보관하고 종료/취소 후 해제한다. 전체 AppState나 분석·렌더 결과를 추가 보관하지 않는다. 타입을 Pick으로 선언하는 것만으로 런타임 객체의 다른 속성이 사라지는 것은 아니므로 실제 보관 객체도 두 속성으로 구성한다.
- undoStack에는 계속 문자열 patch만 저장한다. 인덱스를 이력 entry에 보관하지 않는다.
- 중복 대상 순서, global의 track 무시, 없는 cell의 null, 순변경 0건 생략, 실패 전 상태 확정 경계는 유지한다.
- 영향 경계는 edit_history의 조회 계약과 main의 두 호출 경로 및 drag 시작 상태다. E2의 rawText 적용, parser/analyzer/renderer/audio 알고리즘은 수정하지 않는다.

### 14.1. 범위·근거·한계

이번 단계는 조사이며 제품 코드는 변경하지 않았다. `2.2`, `2.8`, `2.10`, `2.5`의 상태·산출물·이력·프리셋 경계를 기준으로 app session, partial artifact 입력, preset 저장 의존성을 읽었다. 기존 E2/E6 미커밋 작업은 보존했다. 외부 자료나 구현 메모를 기준으로 사용하지 않았다.

재현 도구: `node docs/review-support/review-state-boundaries.cjs`. TypeScript AST로 직접 `session.setState(...)` 호출, 직접 `dom.*` 접근, 전체 AppState setter가 있는 Session 타입을 수집한다. 근거는 `docs/review-support/state-boundary-review.json`이다. 10개 session 타입과 88개 직접 setState 호출 지점을 확인했다. 이는 변경 가능한 상태 필드의 수나 runtime 호출 횟수가 아니다. helper 내부 변경, alias·간접 호출 및 다른 이름의 session은 자동 집계 범위 밖이며 대표 helper와 호출부는 별도로 읽었다.

main의 closure가 실제 state 참조를 보관하지만 `appSession.setState`가 전달 객체를 그대로 저장하므로, 실제 다음 상태 구성 책임은 각 binding/runtime/UI helper에 분산되어 있다. 이 구조가 곧 현재 버그라는 뜻은 아니다. 전체 객체를 읽고 쓸 권한이 작업 책임보다 큰 지점을 좁힐 수 있다는 유지보수 관점의 발견이다.

### 14.3. S1 / A3 — partial artifact 입력 축소: 첫 권장 범위

근거: `orchestration/partial_rebuild/partial_rebuild_artifacts.ts`는 `state: AppState`와 nextDocument·edits를 받는다. 실제로 읽는 state 속성은 정확히 `parsed`, `analysis`, `renderInput`, `activeTrackIds` 네 개다. note/global 두 helper도 같은 네 항목 범위 안에서 작동한다. 이전 document·busy·history·gameMode·clipboard·DOM은 필요하지 않다. 행 방향과 구조는 이전 renderInput에 이미 반영되어 있으므로 reverseRows까지 추가할 이유도 없다.

문제는 실제 잘못된 상태 접근이 발견되었다는 것이 아니라 API가 불필요한 UI 상태 접근을 허용하며 순수 계산 시험 fixture에도 전체 AppState를 요구한다는 점이다. AppState import는 type-only이므로 이를 지우는 것만으로 runtime 의존/번들 크기가 줄었다고 주장하지 않는다.

최소 제안:

- 기존 결과 타입 `ScoreTextEditPartialArtifacts`의 parsed·analysis·renderInput 묶음을 이전 산출물 입력으로 재사용한다.
- 입력은 `previousArtifacts`, `activeTrackIds`, `nextDocument`, `edits`로 표현한다. 이름·readonly 호환은 구현 시 확인한다.
- app_runtime 호출부가 세 산출물을 명시적으로 묶어 전달한다. 타입만 Pick으로 바꾸고 전체 AppState를 계속 전달하는 방식보다 실제 데이터 전달도 일치시킨다.
- 내부 helper도 좁은 산출물 계약을 사용한다. 계산 알고리즘·note/global/mixed fallback·정렬·참조 재사용은 바꾸지 않는다.
- `ScoreTextEdit`/invalidation helper의 app/edit 의존은 여전히 남는다. 이번 한 번에 이를 core로 옮기거나 모든 app 의존을 제거했다고 표현하지 않는다.

영향 경계: app_runtime → orchestration 입력 계약. parser/analyzer/renderer 알고리즘과 audio·저장 형식은 그대로다. 검증은 note/global/mixed 및 reverseRows의 전체 생성 대비 결과와 비편집 산출물 참조 보존, typecheck/build를 중심으로 한다. 기존 test:partial과 test:edit가 기본 검증 기반이다. 성능 최적화가 아닌 책임/시험 범위 개선이므로 이번 변경에 속도 향상 수치를 요구하거나 주장하지 않는다.

### 14.4. S2 / A2 — 기능 session의 변경 권한 축소: 이후 국소 적용

범용 `setState(AppState)`를 `patchState(Partial<AppState>)`로 바꾸는 것만으로는 소유권이 정해지지 않는다. 여전히 document와 history를 임의로 바꿀 수 있고 연동 필드 확정 규칙도 표현하지 못한다. reducer·전역 이벤트 버스·DI 컨테이너의 전면 도입도 현재 근거로는 필요하지 않다.

S1 이후에는 Examples처럼 실제 직접 변경이 busy/status 두 영역뿐인 기능에서 제한된 진행/결과 보고 계약을 시험하는 안이 작다. 실제 악보 교체는 기존 loadScoreJsonText 명령을 유지한다. 다만 busy 해제를 단순 공통 setStatus에 숨기지 않고 시작·성공·실패·닫기의 기존 의미를 명시해야 한다. 상태 갱신부가 실행 시점 최신 상태를 읽도록 하되, 이 변화가 비동기 요청 취소를 대신한다고 생각해서는 안 된다.

Edit panel의 좁은 mode setter는 첫 후보로 단순해 보이지만 실제로 loop 전환과 fitScoreHeight의 ViewBindingSession까지 얽힌다. 이와 같은 간접 helper를 무시한 기계적 Pick 적용은 다른 곳에 전체 setter를 남기거나 타입 단언을 늘릴 수 있다. 먼저 명령별 읽기/쓰기 목록을 확정하고 변경할 기능 하나만 선택한다. 최종 session API는 이 후속 상세 검토에서 결정한다.

AppDom 역시 직접 사용하는 DOM만 줄인다고 끝나지 않는다. 대부분 syncUiControls/render 등의 공용 helper에 전체 dom/state를 넘긴다. 공용 UI 동기화를 기능별로 분리할 필요가 확인된 후 DOM 계약을 줄이며, 지금 수십 개의 Pick 목록을 만드는 작업은 우선하지 않는다.

### 14.5. S3 / A5 — 프리셋 데이터 계약의 소속

infra/layout_preset_storage는 app/layout의 UserLayoutPresetData와 parse/serialize 함수를 import한다. 확인한 타입·검증/직렬화 코드는 DOM 없는 순수 데이터 처리이며, 현재 경로만으로 runtime UI 부작용이나 순환 결함이 확인된 것은 아니다. 다만 하나의 layout_types/layout_preset 영역에 저장 DTO와 UI draft 변환이 섞여 있다.

저장 포맷·검증·직렬화가 UI와 독립적인 공용 프리셋 모듈에 속하고, app/layout은 draft 변환을 담당하도록 분리할 후보로 기록한다. localStorage 접근은 infra에 남긴다. JSON 키·version·오류 조건·기본 슬롯 fallback은 변경하지 않는다. 여러 소비자·기본 preset asset·검사 import가 함께 움직이므로 S1보다 뒤에 둔다. 폴더 이동 자체를 성능 개선으로 보지 않는다.

### 14.6. 인접 영역 관측과 후속 분리

- File read 완료는 loadScoreJsonText로 넘기고 오류에서는 최신 state를 읽는다. 오래된 AppState 전체를 비동기 callback에서 그대로 재확정한다고 단정할 근거는 없다. 다만 파일 요청 순서를 관리하는 토큰은 해당 경로에서 보이지 않는다.
- Examples의 manifest에는 requestId/open 확인과 최신 요청 finally가 있다. score fetch 경로에는 같은 확인이 없다. Practice의 microphone 요청에는 requestId와 완료 시 최신 상태 읽기가 있다. 따라서 모든 async binding이 같은 수준의 취소 처리를 한다고 일반화하지 않는다.
- 이 비대칭이 실제 사용자 재현에서 어떤 영향을 주는지는 아직 확인하지 않았다. 요청 간 우선순위·닫기·파일 로드와의 상호작용은 4단계 수명 검토로 남기며 이번 구조 변경에 조용히 포함하지 않는다.
- Details metadata는 createRuntimeDocument를 호출하고 YouTube metadata는 기존 인덱스를 재사용한다. 이는 기존 A6 재생성 범위 후보이며 3단계에서 계측·참조 계약을 확인한다.

### 14.7. 진행 순서와 완료 상태

권장 순서: **S1 partial artifact 입력 축소 → S2 기능 하나의 session 명령 계약 → S3 preset 데이터/저장 경계**. S2의 전 기능 확대와 AppDom 대규모 분리는 별도 필요성이 확인될 때만 진행한다. 3단계 중복 연산과 4단계 비동기 정책을 함께 개편하지 않는다.

## 15. 상위 계층 역참조 재확인 — 2026-10-09

### 15.2. app 외부에서 app으로 향하는 참조

### 15.3. 순환과 조사 한계

명시적 import type 또는 모든 specifier가 type인 import를 제외한 실행 import 그래프에서는 순환 강연결 집합이 0개다. 타입 import까지 포함하면 `app_types.ts`, `edit/edit_default.ts`, `pitch_label.ts`의 그룹 1개가 있다. app_types는 DefaultNoteEditInput 타입을, edit_default는 pitch_label 함수를, pitch_label은 AppState/DefaultNoteEditInput 타입을 참조한다. 실행 import만으로 완성되는 순환은 아니다. 타입 결합 후속 후보이며 즉시 실행 오류로 취급하지 않는다.

해석 대상 로컬 TS import의 미해결 경로 0개, 명시적 dynamic import/require 호출 0개. JSON/CSS/raw resource, 외부 패키지, 번들러 변환 결과, 함수 callback에 의한 동적 호출 그래프는 이 조사 대상 밖이다. 실행값 분류는 소스 import 문법 기준이며 실제 번들 초기화 실험을 수행한 것은 아니다.

### 15.4. 다음 개선 순서에 반영

1. S1은 AppState 의존 제거로 한정한다. 이 단계가 끝나도 app/edit의 두 import가 남는다고 명시한다.
2. 이후 편집 명령 타입·편집 종류 분류가 app과 orchestration 사이의 공용 계약에 속할지 검토한다. UI와 무관한 부분만 이동하고 mutation·DOM helper를 함께 옮기지 않는다. orchestration의 app 역참조를 완전히 제거하려면 이 결정까지 필요하다.
3. S3의 프리셋 공용 데이터/검증 분리는 infra와 bundled preset의 타입 참조를 함께 정리할 수 있다.
4. game offset의 기본값·정규화는 공용 정책 모듈로 분리할 작은 후속 후보다. 저장 키·정밀도·보정 범위와 게임 동작을 변경하지 않는다.

기존 14절의 session 권한 검토와 별개의 의존 방향 목록으로 관리한다. 공용 계약의 위치는 실제 구현 범위 선정 때 결정하며, 경로를 정리하기 위해 모든 모듈을 한 번에 이동하지 않는다. 새 발견은 문서화했으며 활성 명세와 충돌하는 동작 변경은 제안하지 않았다.

### 21.1. A4 marker 중복 생성

app_runtime의 buildAnalyzedCanvasRenderInput은 globalMarkerItems와 noteMarkerItems를 각각 만든 뒤 buildCanvasMarkerItems를 호출한다. 이 함수는 같은 두 builder를 다시 호출해 정렬 병합한다. 따라서 이 전체 생성 경로에서는 각 그룹의 생성과 그룹 내부 정렬이 두 번 실행된다. 부분 artifact 경로는 이미 생성/재사용한 목록을 새 배열에 합쳐 공용 sortCanvasMarkerItems로 정렬한다.

권장 최소안은 app_runtime의 통합 markerItems도 기존 두 목록을 새 배열에 담고 sortCanvasMarkerItems로 정렬하는 것이다. builder 공개 API의 삭제·캐시 도입·부분 draw 확대는 필요하지 않다. comparator는 입력 배열을 제자리 정렬하므로 반드시 새 배열에 적용한다. 통합/분리 목록이 marker 객체를 공유하게 되는 참조 변화는 소비자의 mutation 여부를 확인하고 기존 부분 경로와 대조해야 한다.

검증 계획은 기존 builder 대비 값·순서 일치, 입력 그룹 배열 순서 보존, global/겹친 track/gliss/tuplet/활성 track 조합, test:partial의 전체 대비 동등성, 편집·트랙 회귀 및 build다. 전후 성능 측정은 marker 생성 또는 전체 renderInput 생성 구간으로 한정하고 draw나 재생 전체 개선으로 해석하지 않는다. 최초 로드·전체 산출물/트랙·행 방향 갱신 경로가 대상이며 모든 단일 셀 편집이 이 경로를 거친다고 일반화하지 않는다.

### 21.2. A6 Details metadata 인덱스 재생성

applyMusicDataEditToState는 musicData만 교체하지만 createRuntimeDocument를 호출해 buildScoreIndexes를 다시 실행한다. 해당 인덱스 입력은 layout.rowDefinitions, tracks, globalLines.cells이며 musicData를 읽지 않는다. 후속 최소안은 Details에서도 새 score/문서 객체를 만들되 기존 indexes를 유지하는 것이다. 제목·작성자·comment·난이도 변경이 행/트랙/셀 참조를 보존한다는 조건을 명시한다. 기존 parsed/analysis/renderInput/history는 이미 재사용 중이다. Details의 session.render, timestamp·동일 값 처리, 입력 검증, YouTube 정책을 함께 바꾸지 않는다. 특히 기존 화면 전체 render 호출이 남으므로 Details 작업 전체가 상수 시간이 된다고 주장하지 않는다.

검증 계획은 metadata 반영, 기존 악보 불변, 새 인덱스 생성 결과와의 동등성 및 기존 index 참조 보존, 변경 후 셀 조회·편집·Undo 경로, 실제 Details UI와 build다. 악보 규모별 helper/실제 적용 구간을 구분해 측정한다.

### 23.5. 명세와 동작 차이

- 출처: 2.4 9.4의 Cancel은 변경을 버린다는 규칙과 L3의 재개방 draft 변경.
- 차이: 이전 파일 읽기 callback이 Cancel 이후에도 새 draft에 적용된다.

- 기존 verify-countdown-lifecycle에 기록 관측점을 추가했다. 실제 binding의 pause/resume은 기록 참조를 유지하고 Stop은 비우며, 새 countdown 완료 직전 초기화됨을 확인했다. 초기 시험의 'countdown 시작 즉시 초기화' 기대는 기존 동작과 달라 실패했으며 시험을 수정했다. 제품 초기화 시점은 변경하지 않았다.
- 카운트다운 12조건 및 seek 관측, 기존 verify-async-lifecycle 통과, pageerror 0개. 입력 기록 연결 시험의 Practice 상태/프레임은 fixture이며 실제 마이크 청취 검증이 아니다.
- test:game, test:audio, test:youtube, TypeScript 포함 build 통과. 첫 build 시 루트에서 실행하여 package.json 경로 오류가 발생했고 regression-code 프로젝트에서 다시 실행해 통과했다.

성능 향상을 계측하거나 주장하지 않는다. 외부 코드·의존성 추가 없음. 기존 10월 10~13일 변경을 보존했다. 전체 판정 추출과 다른 대형 파일 분리는 후속 검토 범위로 유지한다. 보고서는 `docs/report-prep/implementation-records/2026-10-14-game-input-history.md`.

## 29. MIDI import 재검토와 다음 구조 개선 후보 — 2026-10-20

### 29.1. 범위와 판단

사용자가 채택한 순서는 MIDI 요구사항/실험본 검토 → 제한된 구조 개선 → MIDI 구현 → 음정 개선 실험이다. 이번에는 코드와 활성 명세를 대조하고 작은 입력으로 관측했으며 제품·실험본 코드를 수정하지 않았다. 아래 설계는 검토안으로 active 명세를 대체하지 않는다.

영향 경계는 storage/import/validation과 앱 상태 확정이다. MIDI 파서·정규화는 import 내부에 두며 기존 rawText parser/analyzer/renderer/audio generator를 외부 형식에 맞춰 개편하는 것은 선행 목표가 아니다.

### 29.2. 실험본의 재사용 범위

`regression-code-extend/src/import/midi/`의 midi_parse → midi_normalize → midi_quantize → midi_scorefile 흐름과 midi_types는 재사용 검토 기반이다. `midi-file` 1.2.4는 설치 package 기준 MIT이며 현재 제품에는 없는 의존성이다. 실제 도입 시 해당 버전 원문과 번들 포함 범위를 확인하고 라이선스 inventory/페이지를 함께 갱신한다. 이번에는 외부 소스 코드를 복사하지 않았다.

- parser는 track별 delta 누적, noteOn velocity 0 처리, tempo/박자 event와 track/channel 정보를 수집한다. SMPTE time division은 거절한다. format 2 등 지원 형식 경계는 구현 전에 별도 확정/검증해야 한다.
- normalizer는 track/channel 필터와 note on/off 짝짓기, 중복 시작 및 종료 없는 음 진단을 갖는다. 같은 channel/pitch 재공격 시 기존 음을 닫는 정책은 무손실 변환 보장이 아니다.
- quantizer는 시작/끝을 반올림하고 길이를 최소 한 칸으로 만든다. 보정량·짧은 음 연장·양자화로 생긴 충돌을 별도 설명하지 않는다.
- converter는 선택된 입력들을 하나의 targetTrackId에 모은다. 원본별로 basic/optional/extra에 다르게 할당하는 UI/계약은 없다. 현 binding은 전체 트랙, 타악기 제외 채널, 해상도 4, highest를 고정한다.
- sourceTrackIndexes와 sourceChannels는 각각 전역 필터다. 서로 다른 트랙에서 서로 다른 채널을 고르려면 (trackIndex, channel) 선택 단위를 표현하는 새 계약이 필요하다.
- 0–127 MIDI 전용 layout 생성은 선택 가능한 대안이지 현재 악기 preset을 대체하는 확정 정책이 아니다. converter의 global rowId는 고정되어 있어 임의 layout을 받는 범용 변환기로 간주하면 안 된다.
- 기존 앱 binding 전체를 복사하면 이후 개선된 요청 수명·상태 확정 정책을 잃을 수 있다. 변환 모듈/fixture만 검토해 현재 앱에 새 기능 경계를 연결한다.

### 29.3. 확인한 변환 한계

| 항목 | 코드 근거 / 관측 | 후속 방향 |
| --- | --- | --- |
| 템포·박자 | midi_scorefile.createGlobalCells는 첫 tempo와 첫 numerator만 사용, denominator와 이후 변화 미사용 | note와 global 변화를 같은 시간 변환 정책으로 처리. 미지원 변화는 명시적으로 보고 |

관측 입력: C4 [0,960), E4 [240,480), PPQ 480, SPB 4, highest 정책, tempo 120@0/90@480, 박자 6/8. 결과는 C4 col0와 E4 col2 둘 다 수입, 경고 0, global은 col0의 BPM120/BPB6/SPB4/DYN100만 생성했다. 이 결과는 템포 변화·분모의 소실과 시작 시각이 다른 겹침 유지의 증거다. 6/8을 어떤 beat 단위로 표현할지는 아직 채택하지 않았다.

### 29.5. MIDI 구현 전에 정할 정책

- 첫 범위는 새 ScoreFile 초안 생성 권장. 기존 악보 병합·전체 문서 Undo는 별도 확장으로 둔다(2.10의 file load 제외 정책 유지).
- source track/channel 선택 단위와 각 target track 배정, 여러 source를 한 target에 합칠 때의 겹침 처리.
- 대상 layout: 현재 악기 음역, 사용 음역 기반 새 layout, 0–127 전체 MIDI layout 중 선택.
- 양자화 해상도·최소 길이·같은 음 재공격·양자화 충돌 정책 및 손실 보고. 임의 소수 column 저장이나 analyzer 미세 시간 확장을 선행하지 않음.
- 템포/박자 변화, 박자 분모, 지원 SMF 형식과 time division, sustain/pitch bend/velocity 등 미지원 표현 처리. 타악기 기본 제외 여부.
- preview 중 취소/새 파일 선택과 Apply 시점. 성공한 검증 후보만 악보 교체, 이전 요청 결과 무효화. Examples식 최소 session 계약을 참고하되 전체 AppState setter는 새 기능에 넘기지 않음.
- 입력 파일 크기와 변환 후 데이터 규모 제한은 구분. import 전용 처리량 제한은 사용자 정책으로 정하며 전역 cell-count 제한을 임의로 추가하지 않음.

### 29.6. 명세 충돌과 검증 범위

- 충돌 출처: docs/1.3-score-json-format.md 필수 필드·실패 조건 ↔ 현재 score_validate의 누락 허용. 이번 해석: 1.3을 기준으로 R1 보완 후보 선정. 문서의 필수 조건을 약화할 필요 없음; 구현과 회귀 검사가 필요.
- 충돌 출처: 3.3의 단선율 정책 초안/실험 함수 이름 ↔ 실제 다른 시작 시점의 겹침 유지. 이번 해석: 실험을 완성 정책으로 승계하지 않음. MIDI 구체 명세에서 겹침/화음 처리 결정을 갱신해야 함.

## 30. 선택 metadata 정책 변경 및 로드 결과 계약 구현 — 2026-10-20

사용자는 29절 R1의 필수 검사 추가 대신 난이도와 presetId를 선택값으로 변경하도록 결정했다. 소비 코드의 직접 접근 위험을 설명한 뒤 누락 난이도는 기존 기본값, presetId는 custom 취급으로 확정했다. 29절의 필수 필드 보완 권고는 이 결정으로 대체한다. R2는 구현, R3 객체 입력 진입점은 이후 판단으로 보류한다.

### 반영 범위

- 저장 타입은 선택 scoreDifficulty, 개별 선택 난이도, 선택 presetId를 표현한다. validator는 누락을 허용하고 제공된 값의 object/유한 숫자/string 형태만 검사한다. 기존의 누락 허용을 명시적 계약으로 정리하며 잘못된 타입은 허용으로 해석하지 않는다.
- Details는 누락 난이도를 0으로 표시하고 적용 시 입력값을 기록한다. Practice는 기존 1/2/3 기본값을 유지한다. 로드·단순 저장은 누락 필드를 자동 생성하지 않는다.
- 레이아웃 슬롯 조회·계열 비교는 누락 presetId를 custom으로 취급한다. 독립 프리셋을 생성할 때 누락된 instData.presetId를 custom으로 채워 기존 프리셋 검증/파일 왕복 계약을 유지한다. 별도 프리셋 파일 자체의 필수 ID를 제거하지 않는다.
- main.loadScoreJsonText는 검증 거절 false / 화면·재생 연결까지 정상 완료 true를 반환한다. FileBindingSession도 boolean 계약을 명시하고 Examples는 이 반환값을 직접 사용한다. UI statusMessage.level로 결과를 추정하지 않는다.
- 상태 확정 뒤 출력 예외는 기존처럼 전파한다. 새 악보 롤백·자동 복구·새 결과 계층을 도입하지 않았다. 출력 실패 후 정책 변경은 별도 범위다.

### 검증

정식 build(타입·라이선스 검사 포함), test:score, test:layout, test:game, test:examples 통과. 누락/부분 난이도·presetId의 로드/저장 왕복, 부정확한 타입 거절, custom 프리셋 생성/재로드, Practice 기본값을 회귀 검사에 추가했다. test_view의 Clear All 난이도 단언은 선택 타입에 맞춰 optional access만 수정했고 기존 Fit Height 기대값은 이번 범위에서 고치거나 test:view를 재실행하지 않았다.
