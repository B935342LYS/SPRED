## 1. 목적과 적용 범위

MIDI 파일에서 선택한 트랙의 연주 정보를 변환하여 회귀 코드에서 편집할 수 있는 새 ScoreFile을 생성한다.

이 문서는 현재 대화에서 확정한 정책을 기록한다. 기존 실험본의 동작이나 검토 중인 제안을 모두 채택한 완성 명세가 아니다. 확정하지 않은 항목은 구현 전에 별도 결정한다.

기존 ScoreFile에 병합하는 것과, 여러 MIDI 입력을 새 ScoreFile의 한 레이어로 합치는 것은 서로 다른 정책이다. 전자는 제외, 후자는 지원으로 확정했다.

## 3. 새 악보 생성

1. MIDI 변환 결과는 독립된 새 ScoreFile이다.
2. 현재 악보의 note 셀, 전역값, 메타데이터에 MIDI 결과를 추가하는 병합 기능은 초기 범위에 포함하지 않는다.
3. 새 ScoreFile은 기존 저장 구조 및 검증 조건을 충족해야 한다. MIDI 전용 필드를 임의로 기존 셀에 추가하지 않는다.
4. 대상 레이어는 기존 basic / optional / extra를 사용한다. 세 레이어가 모두 존재하고, 입력이 없는 레이어는 cells: []로 표현한다. 이는 기존 ScoreFile 계약이다.

새 악보의 레이아웃은 6.8의 고정 MIDI 전 음역 구성으로 생성한다. 현재 악보 레이아웃이나 선택 음표의 사용 음역에 따라 축소하지 않는다. instData의 구체적인 이름·family·presetId 및 stringId는 별도 확정한다.

## 4. 메타데이터 정책

### 4.1. 기본값

| ScoreFile 항목 | 생성 정책 |
| --- | --- |
| musicData.musicTitle | "Unknown" |
| musicData.musicArtist | "Unknown" |
| musicData.musicGenre | "Unknown" |
| musicData.scoreWriter | "Anonymous" |
| musicData.comment | "" |
| musicData.createdAt / updatedAt | 기존 새 악보의 생성·저장 시각 정책 적용 |

곡 관련 텍스트는 생성 후 Details에서 사용자가 입력·수정한다. MIDI의 트랙명, 일반 텍스트, 저작권 문구 및 원본 파일명을 곡 제목·아티스트·장르·작성자·코멘트에 자동 대입하지 않는다. 원본 파일의 수정 시각을 악보 작성 시각으로 사용하지 않는다.

선택 난이도와 presetId는 기존 ScoreFile의 생략 허용 계약을 유지한다. MIDI 변환기가 이 선택값을 명시적으로 생성할지 생략할지는 세부 생성 정책에서 정한다. 이번 결정으로 필수 필드로 되돌리지 않는다.

### 4.2. 결정 근거

MIDI에 포함된 텍스트와 ScoreFile의 곡 제목·아티스트 등의 의미가 항상 일치하지 않는다. 추정값을 넣으면 사용자가 잘못된 내용을 삭제·수정해야 할 수 있으므로 메타데이터 자동 추출을 첫 구현에서 제외한다.

이는 곡 설명 메타데이터에 관한 결정이다. 음표, 템포, 박자처럼 악보 변환에 필요한 MIDI 정보의 분석까지 제외한다는 뜻은 아니다.

원본 트랙명·파일명을 가져오기 화면에서 식별용으로 표시하는 것은 곡 메타데이터 자동 입력과 구분한다. 트랙명은 목록 표시용으로 활용하는 안을 권고하며, 정확한 표시 형식은 UI 상세 설계에서 정한다.

## 5. 전용 UI와 트랙 배정

### 5.1. 확정된 기본 흐름

1. 사용자가 MIDI import 버튼을 통해 MIDI 파일을 입력한다.
2. 전용 UI에서 악기별로 구분 가능한 입력 목록을 표시한다. 다른 악기는 원본 트랙·채널 경계와 무관하게 나누어 배정할 수 있어야 한다.
3. 사용자가 가져올 입력의 대상 ScoreFile 레이어를 직접 지정한다. 여러 입력을 같은 레이어에 배정할 수 있다. 타악기 항목은 목록에 표시하되 비활성화한다.
4. 배정·SPB에 따라 새 ScoreFile 후보를 생성·검증하고 길이·음표 수·보정/손실 경고를 표시한다.
5. 사용자가 Apply를 누르면 검증된 후보로 현재 악보를 교체한다. Apply 전 취소·변환/검증 실패에서는 현재 악보를 유지한다.

자동으로 원본 트랙 순서에 따라 대상 레이어를 확정하거나 트랙 이름을 곡 메타데이터로 사용하는 방식은 채택하지 않는다.

### 5.2. UI 세부 정책 — 일부 확정

| 요소 | 제안 |
| --- | --- |
| 트랙 식별 | 원본 트랙 번호와 이름 표시; 이름이 없으면 번호 기반 표시 |
| 보조 정보 | 음표 수 등 선택에 필요한 정보 표시 |
| 대상 선택 | 선택 안 함 / basic / optional / extra |
| 초기 배정 | 확정: 모두 선택 안 함 |
| 전역 정보 전용 트랙 | 음표가 없는 트랙은 구분 표시하고 레이어 배정과 전역값 수집을 분리 |
| 적용 절차 | 확정: 변환·검증 요약 확인 후 Apply에서 악보 교체 |
| 실패·취소 | 확정: Apply 전 취소·파싱/변환/검증 실패 시 기존 악보 보존; 새 파일/설정 변경의 후보 무효화는 6.16 참조 |

이 표는 앞선 논의에서 제시된 권장안이며 전부 확정된 것은 아니다. 메뉴 내 버튼 위치, 중복 선택 UI, 적용 확인 및 상태 확정 후 출력 실패 처리도 상세 설계 대상이다.

## 6. 다대일 배정과 충돌 정책

### 6.1. 논의 경과

사용자는 처음 일대일 대응을 선택한 뒤 다대일의 구현 난도를 검토했으며, 2026-10-30 후속 논의에서 다대일 지원을 확정했다. 수동 배정은 유지한다.

후속 답변에서 6.4의 중첩·양자화 충돌 규칙도 채택했다. 양자화 반올림 등 잔여 상세와 정책 정리·구현 착수는 구분한다.

### 6.2. 비교와 채택 결과

| 방식 | 관계 | 추가 고려 |
| --- | --- | --- |
| 일대일 제한 — 미채택 | 대상 레이어마다 원본 트랙 최대 하나 | 단일 원본 내부에서도 충돌 발생 가능 |
| 다대일 — 채택 | 여러 입력을 같은 대상 레이어에 배정 | 공통 시간축 유지, 중복 음·시간 중첩·양자화 충돌 처리 필요 |

원본 트랙 하나를 여러 대상에 복제하는 기능은 필요성이 논의되지 않았다. 별도 확정 없이 추가하지 않는다.

### 6.3. 병합 시 기술적 검토

| 상황 | 저장 가능성 및 결정할 사항 |
| --- | --- |
| 다른 시간의 음표 | 원본의 공통 시간축을 유지하여 같은 레이어에 배치 가능 |
| 같은 시간의 다른 음정 | 서로 다른 note 행에 배치하여 화음 유지 |
| 같은 음정·시작·길이 | 중복 제거 |
| 같은 음정의 연속·겹침 | 6.4의 재발음·발음 구간 합집합 규칙 적용 |
| 양자화 후 동일 좌표 | 한 트랙의 같은 (rowId, col)에 셀 하나만 저장; 같은 시작은 합치고 소실을 보고 |

단순한 마지막 값 덮어쓰기는 사용하지 않는다. 충돌·손실 보고의 세부 UI와 집계 형식은 추가 확정한다.

### 6.4. 중첩 처리 — 확정

대상 레이어·변환 후 음정별로 양자화된 구간을 처리한다(구간은 시작 포함·끝 제외). 서로 다른 음정은 화음으로 유지하고 자동 단선율화하지 않는다.

- 같은 음정·같은 시작: 하나의 발음으로 합치고 가장 늦은 종료를 사용한다. 완전 중복과 양자화로 다른 시작이 합쳐진 손실을 구분하여 집계한다.
- 같은 음정·다른 시작의 중첩: 다음 시작에서 재발음하되 이미 진행 중이던 음들의 종료까지 포함하여 발음 구간의 합집합을 유지한다. 예: C4 [0,8), [3,5) → [0,3), [3,8). 개별 성부 길이와 음색은 보존되지 않는다.
- 끝과 다음 시작이 같은 연속 음: 재발음을 유지한다. 다음 시작이 없는 곳에서 종료 이벤트만으로 새 발음을 만들지 않는다.
- 중첩이 없는 구간 사이의 쉼은 유지한다. 충돌 집계와 대표 사례를 보고하고, 세부 보고 형식은 별도 확정한다.

위 규칙은 원본 note on/off 짝짓기 이후의 확정 변환 정책이다. 같은 채널·음정의 원본 note 중첩을 어떻게 짝지을지는 별도 결정해야 한다.

### 6.5. 악기별 입력 목록·타악기 — 상세 협의

- 확정: 다른 악기는 트랙·채널과 무관하게 구분하여 배정 가능해야 한다. 같은 악기도 출처별로 표시하며 자동 통합하지 않는다.
- 초기 목록은 원본 트랙·채널·악기별 항목을 유지한다. 같은 악기도 출처별로 선택 가능하며 다대일 배정으로 사용자가 합친다. 악기명 우선 표시 및 구체적인 라벨 형식은 UI 제안이다.
- 권장: 음 시작 시점의 bank/program으로 악기를 식별하고, 중간 program 변경 전후의 음을 구분한다. GM 이름 표시 범위, 미지정 악기, MIDI port 및 같은 시각의 상충 메시지는 추가 협의한다.
- 확정: 타악기는 목록에 보이되 배정 불가. 권장안은 GM 채널 10을 우선 판별 기준으로 삼는 것이며, 비GM/GS/XG 및 SysEx 기반 드럼 판별 범위는 미확정이다. 타악기가 섞인 원본 트랙 전체를 제외하는 것으로 확대 해석하지 않는다.

### 6.6. 시간 해상도와 형식 — 상세 협의

- 확정: 정수 SPRED tick(그리드 한 칸) 단위로 양자화한다. MIDI 원본 tick(PPQ에 따른 단위)과 구분한다. SPB 기본값은 4이며 변환 전 사용자가 변경할 수 있다. 박자 분모에 따른 환산은 별도 확정한다.
- 확정: 원본 시작/끝 시간과 출처를 중간 데이터에 보존하고 마지막 단계에서 정수 그리드로 양자화한다. 정수 변환 검증 후 잇단음 자동 생성을 후속 단계로 확장한다. 초기 자동 잇단음 생성은 제외한다. 원본 시간 보존은 변환 중 데이터에 관한 것으로 ScoreFile 영구 필드 추가를 뜻하지 않는다.
- 확정: 시작과 끝을 각각 가장 가까운 정수 칸으로 반올림한다. 정확히 반 칸이면 뒤쪽 칸으로 반올림한다. 반올림 후 0칸 길이가 되면 종료를 시작 + 1칸으로 보정한다. 비정상 원본 음의 수리와는 구분하며 그 처리 범위는 별도 협의한다.
- 비음수의 연속 SPRED 위치를 s/e라고 할 때 startCol = floor(s + 0.5), endCol = max(startCol + 1, floor(e + 0.5))로 표현한다. 양자화 및 최소 길이 보정 이후 6.4의 중첩 처리를 적용한다.
- 시작/끝 이동과 최소 길이 연장을 변환 보고에 포함한다. 원본 대비 보정과 중첩 병합 손실은 구분한다. 세부 집계/UI는 후속 협의한다.
- 확정: SMF Format 0/1 + PPQ를 초기 지원하고 Format 2 및 SMPTE time division은 명시적으로 거부한다.
- 잇단음 후속 단계에서는 그룹 길이·분할 수·허용 오차·쉼/hold·중첩 결합을 별도 결정한다. 소수 col 저장으로 기존 ScoreFile 계약을 변경하지 않는다.

### 6.7. MIDI 해석 경계 — midi-file 채택 확정, 설치 전

- 바이너리 해독은 `midi-file`을 사용한다. `parseMidi(Uint8Array)`로 header와 트랙별 이벤트 배열을 얻는다. 가변 길이 delta·running status·메타 이벤트의 바이트 해독은 라이브러리가 담당한다. 음 연결·악기 분류·양자화 및 ScoreFile 변환은 SPRED에서 구현한다.
- SPRED 변환기: 지원 형식/PPQ·규모 검증 → 트랙별 delta 누적 → 공통 시간축의 채널/port 상태 해석 및 note on/off 짝짓기 → 출처·악기별 목록 구성 → 사용자 배정 → 그리드 양자화 → 대상별 중첩 처리 → ScoreFile 생성·기존 validator 및 로드 경로 적용.
- 표시용 출처와 연주 상태의 범위는 구분한다. 같은 port/channel의 program/controller가 다른 트랙에 있을 수 있으므로 트랙별 악기 상태를 무조건 독립 취급하지 않는다. 동시각 상충 이벤트·누락 note off·중복 note on 처리 상세는 추가 협의한다.
- `@tonejs/midi`는 notes/time/duration/instrument 등을 제공하는 상위 대안이며 내부적으로 `midi-file`을 사용한다. 비교 후 원본 출처와 변환 손실 진단을 직접 통제하기 위해 낮은 수준의 midi-file 이벤트 API를 채택했다. 상위 라이브러리로 구현 불가능하다는 뜻은 아니다.
- 두 저장소 모두 MIT 고지를 확인했다. 기존 실험본 검토 기록의 midi-file 1.2.4는 참고 이력이며 제품 설치 버전을 확정한 것이 아니다. 도입 시 실제 버전 원문·전이 의존성·번들 및 기존 라이선스 inventory/고지를 확인한다. 채택은 확정했으며 아직 코드 복사·설치는 하지 않았다.

### 6.8. SPB와 레이아웃 — 기본 정책 확정

- SPB는 한 박에 배치할 칸 수다. 기본값 4를 사용하며 변환 전에 사용자가 변경할 수 있다. 기존 parser 계약은 1~999 정수이며 import UI의 추가 제한·규모 예산 및 박자 분모와의 결합은 추가 결정한다. 4/4에서 SPB 4는 16분음표, 8은 32분음표 간격이다.
- 레이아웃은 전역 행 4개(bpm/beatsPerBar/stepsPerBeat/dynamics)와 MIDI 0~127 note 행 128개로 구성한다. gap 행은 생성하지 않는다. 모든 행 높이 21px, baseColumnWidthPx 21로 기본 셀은 21×21px 정사각형이다.
- 사용자 최초 표현의 0~128 및 note 행만이라는 범위는 추가 확인을 거쳐 0~127 총 128개 + 필수 전역 행 유지로 확정했다. 선택 음역으로 축소하는 이전 제안은 미채택이다.
- instData, 빈 선택/유효 음 없음 처리, 전역 행 초기값, 표시 순서 및 음이름 표기는 후속 확정한다.

### 6.9. 10월 5주차 보고서 PDF 필드 대응안 검토 — 제안과 확정 구분

검토 대상은 저장소 루트 `10월 5주차 보고서.pdf`의 5~6쪽 3.3절이다. 본문 추출과 표 이미지로 검토했다. PDF 원본은 수정하지 않았다. 아래 검토는 아직 미확정인 정책을 자동 채택하지 않는다.

### 6.10. Dynamics와 곡 전체 길이 — 확정 / 비정상 입력 상세 협의

- 가져오기 결과의 dynamics는 col 0에 rawText "100"을 생성하고 변화 셀을 생성하지 않는다. 이후 사용자의 일반 편집을 제한하는 뜻은 아니다. velocity의 강도는 변환하지 않지만 velocity 0의 note 종료 의미는 해석한다. CC의 음량·표현 변화로 Dynamics를 생성하지 않는다. sustain 등 음 길이에 영향을 주는 제어의 지원 범위는 별도 협의한다.
- 악보 길이는 원본 MIDI 곡 전체를 기준으로 한다. 선택되지 않은 트랙·악기 및 변환에서 제외하는 타악기가 더 늦게 끝나더라도 전체 종료 산정에서 제외하지 않는다. 선택한 파트가 먼저 끝난 뒤의 빈 악보 구간을 유지한다.
- 근거: 선택한 음만 기준으로 줄이면 사용자가 전체 길이를 수동 복원해야 하며 반주 도중 악보가 먼저 끝날 수 있다. 이전의 선택·변환 후 음표만을 기준으로 하는 제안은 폐기한다.
- 종료 기준 확정: 모든 원본 트랙의 End of Track(EOT) 절대 tick 중 최댓값을 곡 종료로 삼아 명시된 후행 무음을 포함한다. 마지막 noteOff 시각만으로 줄이지 않는다. EOT 누락·중복·이후 이벤트·끝나지 않은 음 등 비정상 입력은 별도 실패/보정 정책이 필요하다.
- 끝 경계 확정: 곡 종료가 그리드 사이에 있으면 올림한다. 음 시작/끝의 최근접 반올림 규칙과 별도다. 최소 1칸 보정된 note가 이를 넘으면 그 note의 endCol까지 수용하고, 추가 길이와 경계 오차를 보고한다. 최종 columnCount는 배타적 종료 경계이므로 무조건 +1하지 않는다.
- 정상 EOT의 최댓값을 연속 SPRED 위치로 환산한 값을 songEndPosition, 최종 변환 음의 종료 칸 최댓값을 maxNoteEndCol이라 하면 columnCount = max(ceil(songEndPosition), maxNoteEndCol)이다. 음 없음·길이 0 입력의 허용/실패 정책은 아직 결정하지 않았다. 부동소수 오차로 정수 경계가 한 칸 늘어나지 않도록 환산·올림 구현을 검증한다.
- 정수 columnCount에서는 원본 종료와 정확한 시각 일치가 불가능한 경우가 있어 조기 종료보다 후행 여유를 허용한다. 올림 자체의 여유는 1칸 미만이며 최소 길이 보정에 따른 추가 확장은 별도 집계한다. 템포/박자 변화 위치 양자화의 누적 시간 오차는 이 끝 경계 규칙만으로 해결되지 않으므로 전역값 정책에서 별도 검증한다. 입력 MIDI와 별도 반주 파일 자체의 길이·템포 차이를 자동으로 해결하는 기능으로 확대 해석하지 않는다.
- 후행 구간의 템포/박자 변화도 선택한 note가 끝났다는 이유로 버리지 않는다. columnCount 10000 및 저장 용량 제한 초과 시 조용히 잘라내는 정책은 채택하지 않았다. 명시적인 실패/해상도 조정 정책은 후속 결정한다.

### 6.11. 템포·박자 — 전체 변화 및 분모 환산 확정

- 확정: 원본의 첫 값뿐 아니라 곡 전체 템포/박자 변화를 가져온다. 음표 선택 여부와 전역 이벤트 수집을 분리한다. 실제 이벤트 출처 우선순위·상충·같은 칸 충돌·끝 경계 이벤트 처리는 후속 결정한다.
- 확정: 박자 분모에 해당하는 음표를 SPRED 한 박으로 대응한다. MIDI 박자 n/d, 4분음표당 microseconds를 u라 하면 BPB=n, BPM=(60,000,000/u)×d/4이다. SPB는 사용자가 정한 한 박당 칸 수를 유지한다. 이는 복합박자의 음악적 강박을 추론하는 정책이 아니라 저장/시간 환산 기준이다.
- 예: quarter-note BPM 120인 6/8은 BPB 6, BPM 240이다. SPB 4일 때 한 마디는 24칸이고 1.5초다. 4/4는 BPB 4, BPM 120, 한 마디 16칸·2초다.
- 분모 변화가 있으면 원본 tick→연속 칸 위치를 구간별로 누적해야 한다. 분모가 바뀌는 시점에는 MIDI tempo event가 없어도 SPRED BPM 환산값이 바뀔 수 있다. 전역 변화 위치의 양자화·값 정밀도 및 기존 BPM 1~999 범위 밖의 처리 규칙은 추가 협의한다.
- 분모가 d로 일정한 구간에서 원본 tick 길이 Δt, PPQ=P, SPB=S라 하면 칸 증가량은 Δx=(Δt/P)×(d/4)×S다. 구간 시작까지 누적한 위치에 Δx를 더한 뒤 양자화한다. tempo 변화는 이 칸 위치 계산에 직접 관여하지 않고 실제 시간 환산에 관여한다.

### 6.12. 전역 변화 양자화·충돌·시간 오차 — 기본 규칙 확정

- 변화 위치 확정: note와 같은 연속 칸 시간축에서 최근접 정수 반올림, 반 칸은 뒤쪽으로 이동한다. 변화를 임의로 마디 시작까지 이동시키지는 않는다. 위치 이동량을 보고한다.
- 서로 다른 원본 시각이 같은 칸에 모이는 경우 확정: 원본 시간순으로 tempo·박자 상태를 모두 적용한 뒤 해당 칸의 마지막 유효 상태를 BPM/BPB 셀로 출력한다. tempo와 분모 변화의 결합 상태를 먼저 구한 후 BPM을 계산하여, 분모 변경에 따른 BPM 갱신을 놓치지 않는다. 중간 상태 소실을 집계한다.
- 위 충돌안은 원본 시각이 다른 변화의 양자화 충돌에 관한 것이다. 서로 다른 트랙에서 동일 원본 tick에 상충하는 전역값을 기록한 경우는 시간상 우열이 없으므로 별도 우선순위/거부 정책을 정한다. “마지막 상태”를 파일 순서 무조건 덮어쓰기 규칙으로 확대하지 않는다.
- 전체 변화 수집은 모든 변화가 정수 그리드에 무손실 저장됨을 보장하지 않는다. 원본 tempo map의 EOT 실제 시각과 변환 후 timing map의 종료 실제 시각을 비교하고 차이를 보고한다. 중간 note 시작/끝 시간 오차도 따로 평가한다.
- 종료 보완 확정: 변환 후 악보가 원본 EOT보다 실제 시간상 먼저 끝나면, 현재 columnCount 이후에 마지막 전역 상태를 유지한 빈 칸을 필요한 최소 개수만큼 추가한다. 이는 6.10의 칸 위치 올림만으로 남는 누적 오차를 보완한다. 이미 원본 종료 이상이면 불필요하게 추가하지 않는다. 중간 연주 시점의 동기화 오차를 해결하지 않으며 크기 제한을 넘으면 조용히 잘라내지 않는다.
- 비어 있는 초기 전역값, EOT 위치의 전역 이벤트, 범위 밖 BPM·상충 이벤트 및 입력 오류는 별도 후속 질문으로 결정한다.

### 6.13. PPQ 고해상도 그리드 대안 검토 — 폐기 결정

사용자가 SPB=PPQ 및 열 너비 축소로 원본 경계를 정수 칸에 보존하는 대안을 제안한 뒤, 규모 검토를 거쳐 폐기하기로 결정했다. 아래는 비교 이력이며 구현 후보가 아니다. 기존 SPB 기본 4·21px 정사각형 정책과 정수 변환 검증 후 잇단음 확장 순서를 유지한다. 6.12의 기본 규칙은 후속 대화에서 확정했다.

- 4/4에서는 SPB=PPQ로 원본 tick 하나를 한 칸에 대응할 수 있다. 현재 분모 기준 정책에서 일반식은 SPB=4×PPQ/d다. PPQ480·6/8이면 SPB240이다. SPB=PPQ를 고정하면 6/8은 tick당 2칸, 2/2는 0.5칸이므로 항상 정수 경계를 보장하지 않는다. 정수 SPB·분모 변화·상한을 함께 검토해야 한다.
- 현재 코드 제한: columnCount 최대 10000, SPB 1~999 정수, baseColumnWidthPx 1 이상의 정수, Score JSON 8MiB. 폭을 줄여도 데이터 열/셀 수는 줄어들지 않는다.
- 합성 규모 계산: 4/4·quarter-note BPM120·4분·PPQ480에서 SPB4는 1920열, SPB480은 230400열(120배). 10000열은 약 10.42초다. 기존 한 박 폭 84px를 유지하려면 열 너비 0.175px가 필요하여 현 저장 계약 밖이다.
- 빈 칸 128×230400개를 전부 저장하는 것은 아니다. 다만 음이 차지하는 각 칸에 시작/hold 셀이 필요하다. 연속 단일 음정 230400셀, rowId=s1-note-60의 compact JSON 배열만 약 10.88MiB로 계산했다. 실제 MIDI 성능 벤치마크가 아니라 메타데이터 제외 합성 크기 계산이다.
- 대안 후보: note 시작/끝·템포/박자·EOT 및 필요한 박 경계의 공통 시간 간격으로 최소 정확 해상도를 계산한다. 단순 4/4·PPQ480에서 모든 시각과 PPQ의 최대공약수가 40이면 SPB12로 보존 가능하다. 미세한 연주 차이로 최대공약수가 1이면 원래 PPQ로 돌아가므로 일반적인 해결 보장은 없다. 분모 변화에는 추가 정수 SPB 조건 검토가 필요하다.
- 결론: PPQ 고해상도 안은 폐기한다. 최대공약수 기반 최소 정확 해상도 탐색도 비교 아이디어일 뿐 구현 계획으로 자동 승계하지 않는다. 바이너리 시간 경계 보존이 중첩·미지원 MIDI 표현까지 무손실 변환한다는 뜻은 아니다.

### 6.14. 후속 잇단음 확장 방향 — 해상도 검토

- 사용자 제안: SPB와 5잇단을 조합하면 4분음표를 1/20로 나누는 실용적인 해상도를 얻을 수 있다. 이는 잇단음의 초기 동시 구현 승인이나 모든 음을 5분할로 강제하는 정책 확정이 아니다.
- 4분음표가 한 박인 구간에서 SPB4, 한 칸 길이의 tuplet group을 5등분하면 각 slot은 4분음표의 1/20이다. 일반식은 group 길이 L칸, 분할 수 N일 때 slot=L/N tick이며, SPB4라도 group이 여러 칸이면 1/20이 아니다. 분모가 8인 구간은 앞서 채택한 박 기준에 따라 별도 환산한다.
- BPM120(4분음표 기준)에서 1/20 그리드 간격은 25ms, 최근접 양자화의 각 경계 오차는 최대 12.5ms다. 이는 타이밍 간격 계산이며 실제 품질 검증 결과가 아니다.
- 셀 하나의 slot 문자열로 세분하므로 곡 전체 열 수를 PPQ만큼 늘릴 필요는 없다. 다만 slot 수에 따른 rawText 길이·parser/analyzer 처리량은 증가하고 200자 제한과 화음·hold 연결을 검증해야 한다.
- 5분할 고정으로 모든 리듬이 정확해지는 것은 아니다. 셋잇단 등은 별도의 분할 수/그룹 길이를 검토한다. 3/5 등 후보의 자동 선택 기준은 후속 상세 명세 대상이다.
- 현재 잇단음은 note 표현이다. 전역 템포/박자 셀은 여전히 정수 col에 놓이므로 잇단음만으로 6.12의 전역 변화 위치·충돌·시간 오차 문제가 사라지지는 않는다.
- 사용자 확정 방향: 후속 잇단음 변환은 노트 시작/끝의 정수 칸 반올림을 더 세밀한 slot 경계 대응으로 대체한다. 전역 템포/박자 셀은 정수 col과 최근접 반올림을 유지한다. 초기 정수 변환 검증 후 확장하는 순서는 바꾸지 않는다.
- 그리드에 정렬된 마디 경계의 전역 변화는 위치 반올림 오차가 없다. 모든 MIDI 입력이 그런 위치에 변화를 기록한다고 가정하지 않으며, 연속적인 tempo 변화 등 비정렬 입력의 이동·소실·실제 시간 오차 보고와 종료 보완은 유지한다. 일반 파일에서 오차가 작다는 실측 결론은 아직 없다.
- 일반 SMF에는 원래 악보의 n잇단 그룹·분할 비율을 확정해 주는 표준 note 속성이 없다. tick 시각의 패턴으로 표현 후보를 추정해야 한다. 특정 제작 도구의 독자 데이터는 일반 지원 계약으로 삼지 않는다. MusicXML의 time-modification과 달리 원래 표기 복원을 보장하지 않는다.
- 예: PPQ480에서 0/160/320에 시작하는 세 음은 한 박 3분할에 정확히 맞지만, 더 큰 분할의 일부 슬롯이나 연주 타이밍으로도 해석될 수 있다. 정확한 그리드 적합과 작곡자의 잇단음 의도 확정은 구분한다. note 길이만으로 판별하면 staccato·gate 길이 차이 때문에 오판할 수 있다.
- 후속 권장안(미확정): 원본 시작/끝과 주변 리듬을 여러 그룹 길이·분할 수 후보에 맞춰 오차를 평가하고, 충분히 정확한 후보 중 단순한 표현을 선호한다. 맞지 않는 시각에는 더 세밀한 양자화나 정수 방식 fallback·손실 보고가 필요하다. 분할 수 상한·오차 허용치·fallback 정책은 별도 확정한다.

### 6.15. 전역 초기값 및 원본 동시각 충돌 — 확정

- 초기값 확정: 첫 tempo event 이전에는 4분음표당 500000 microseconds(quarter-note BPM120), 첫 박자 event 이전에는 4/4를 사용한다. tick 0의 유효 이벤트가 있으면 해당 값을 우선하며, 곡 중간의 첫 이벤트를 곡 시작까지 소급하지 않는다. 최종 BPM은 그 시점 분모 기준으로 환산하고 col 0에 필수 초기 전역 셀을 생성한다.
- 동일 원본 tick의 충돌: 같은 트랙 안에서는 파일 이벤트 순서를 유지하여 종류별 마지막 값을 취하고, 서로 다른 트랙의 같은 종류 값이 같으면 중복 통합한다. 상충하면 아래 우선순위와 경고 후 계속 규칙을 따른다. 충돌 자체를 이유로 중단하는 이전 제안은 미채택이다.
- tempo와 timeSignature는 다른 종류이므로 같은 tick에 있다는 이유만으로 충돌이 아니다. 두 상태를 결합해 BPM/BPB를 계산한다. 원본 시각이 다른 변화의 양자화 충돌은 이미 확정한 6.12 규칙을 따른다.
- 동시각 충돌의 우선순위·경고 후 계속 정책은 사용자 확정 사항이다. BPM 범위 밖·EOT 비정상 입력·음 종료 누락 등 다른 오류 처리는 후속 결정한다. 유효하지 않은 수치까지 허용하는 결정은 아니다.
- 용어 확인: 여기서 트랙은 원본 MIDI 트랙이고 충돌 대상은 tempo/timeSignature다. 예: 원본 tick480에 트랙A가 quarter-note BPM120, 트랙B가 BPM90을 기록한 경우다. 목적지 ScoreFile trackId 배정과 무관하며 하나의 전역값을 골라야 한다. note 구간 교집합이나 화음 충돌을 뜻하지 않는다.
- 노트 겹침은 사용자 재확인으로 기존 6.4를 유지한다. 같은 음 [0,8), [3,5)는 [0,3), [3,8)로 재발음·합집합 길이를 유지하고, 다른 음정은 화음으로 유지한다. 나중 note 종료에 맞춰 앞 음의 꼬리를 삭제하는 안은 채택하지 않는다.
- Format 0/1의 tempo는 공통 재생 시간축을 정하는 정보이며 악기별 독립 BPM이 아니다. Format 1의 첫 트랙 tempo map 배치 원칙과 달리 다른 트랙에 이벤트가 있는 실제 파일 사례도 보고되어 있다. 발생 빈도를 측정한 것은 아니며 동시각 상충을 일반적인 음악 표현으로 취급하지 않는다.
- 확정: 동일 tick·동일 종류의 상충에 한해 원본 첫 트랙(index0)에 값이 있으면 이를 우선한다. 없으면 상충 후보 중 원본 트랙 번호가 가장 작은 트랙의 값을 사용한다. 같은 트랙 내에서는 마지막 이벤트다. 선택·무시한 값과 출처를 경고로 보고하고 변환은 계속한다. 이는 명시적인 호환성 정책이지 비표준 입력의 원래 의도를 보장하는 규칙이 아니다. 서로 다른 tick의 변화는 기존 전체 수집 정책을 유지한다. 원본 동시각 충돌을 해결한 뒤 6.12의 양자화 충돌을 처리한다.

### 6.16. 입력 선택과 적용 UI — 기본 흐름 확정

- 최초 파일 분석 후 모든 비타악기 입력은 '선택 안 함'으로 표시하고 사용자가 대상 레이어를 지정한다. 타악기 비활성화는 기존 확정 정책을 따른다. 기본 자동 배정은 하지 않는다.
- 사용자 배정·SPB를 바탕으로 변환 후보를 생성·검증한 뒤 예상 길이·음표 수·보정/손실 경고를 보여주고, Apply에서 현재 악보를 교체한다. 파일 선택만으로 교체하지 않는다.
- Apply 전 취소·파싱/변환/검증 실패에서는 현재 악보를 유지한다. 이 기본 흐름을 사용자 확정했다. 상태 교체 이후 renderer/audio 출력 실패의 복구 규칙은 별도 후속 결정한다.
- 현재 설정과 다른 후보를 적용하지 않도록 새 파일 선택이나 설정 변경 시 이전 후보·비동기 결과를 무효화하는 설계를 제안한다. 자동 재변환/별도 변환 버튼, 로딩 UI 및 세션 상세는 후속 결정한다.

### 6.17. 악기 변경과 타악기 판별 — 2026-10-31 기본 정책 확정

- 확정: 음 시작 시점의 악기 상태를 따라 원본 트랙·port·채널·bank/program별로 목록을 구분한다. 같은 출처에서 같은 bank/program의 피아노→바이올린→피아노라면 두 피아노 구간은 한 피아노 항목에 모으고 바이올린을 별도 항목으로 둔다. 악기 변경 당시 이미 진행 중인 음은 시작 시점의 소속을 유지한다. 다른 출처의 같은 악기를 자동 통합하지 않는다.
- 이 항목 구분은 선택/배정용이며 원본 악기의 음색을 SPRED에서 재현하는 기능으로 확대하지 않는다. program 미지정·bank 변경 확정 시점·동시각 상태 충돌·이름 표기 정책은 별도 후속 결정한다.
- 확정: 타악기는 초기 범위에서 GM 방식의 채널 10(내부 인덱스 9)을 기준으로 식별하여 목록 표시·비활성화한다. 다른 채널의 GS/XG/기기별 SysEx 드럼 지정 자동 판별은 초기 지원에서 제외한다. 비GM 파일의 완전한 판별을 보장하지 않으며 트랙 이름으로 추측하여 제외하지 않는다.
- 제외 대상은 드럼 맵 파트다. 일반 선율 채널의 실로폰·마림바 등 음높이가 있는 타악기를 악기명만으로 제외하지 않는다.

## 7. 이후 결정할 정책 순서

1. 원본 note 짝짓기·비정상 입력 처리 상세 확정(midi-file 및 변환 후 중첩 규칙은 확정).
2. 채널/port 상태·미지정 program·bank 변경 적용 시점·음표 없는 트랙 등의 상세 확정(출처별 bank/program 그룹 및 초기 GM 채널10 타악기 판별은 6.17에서 확정).
3. 대상 악기 metadata·레이아웃 표시 순서/라벨(전역 4행 + note 128행, 21px 정사각형은 확정).
4. SPB 입력 UI·규모 제한 상세(기본 4와 변경 허용, 반올림·최소 1칸·보정 보고·잇단음 후속 단계는 확정).
5. 전역값 범위·끝 경계 이벤트 상세(초기값·원본 동시각 충돌은 6.15에서 확정; 최근접 위치, 동일 칸 마지막 상태/손실 보고, 실제 종료 부족 시 빈 칸 추가도 확정).
6. sustain/pitch bend/velocity 등의 처리 범위(Format 0/1 + PPQ 및 2/SMPTE 거부는 확정).
7. 미리보기·경고·손실 보고, 적용·취소·실패 시 상태 유지.
8. 입력 용량·변환 규모 제한, 의존성·라이선스, 검증 사례 확정.

위 순서는 협의 진행안이며 개별 항목의 동작을 확정하지 않는다.

## 8. 기존 자료와 충돌하는 부분

| 출처 | 기존 내용 | 이번 해석·후속 조치 |
| --- | --- | --- |
| 3.3 4.2·4.4 | 새 ScoreFile 또는 현재 악보 삽입 | 새 ScoreFile 생성으로 범위 확정. 기존 후보 문구는 역사적 대안 |
| 3.3 4.3 | 타악기 제외, 단선율화 등 초안 | 타악기 목록 표시·비활성화는 새 사용자 결정으로 확정; 단선율화는 자동 승계하지 않음 |
| 실험본 | 단일 target, 고정 선택·양자화, 첫 템포/박자 사용 | 재사용 검토 자료일 뿐 제품 확정 동작이 아님 |
| 최초 일대일 선택 | 일대일 수동 배정 | 후속 사용자 결정으로 다대일 지원 확정. 수동 배정 유지; 하네스 최신 재개점 갱신, 과거 기록은 유지 |
| 사용자 최초 레이아웃 표현 ↔ 1.3 저장 계약 | 0~128 note 행만 ↔ MIDI 0~127 및 전역 4행 필수 | 추가 확인으로 전역 4행 + note 128행, gap 없음 확정. MIDI 명세·하네스 갱신; 1.3 변경 불필요 |
| 이전 에이전트 제안 ↔ 사용자 곡 길이 결정 | 선택한 note의 마지막 종료 ↔ 원본 곡 전체 종료 유지 | 사용자 결정을 채택하고 선택 기준 축소안을 폐기. 3.11·하네스·보고서 기록 갱신; 기존 저장 계약 변경 불필요 |

관련 구현 경계는 storage/import/validation 및 앱 교체 흐름이다. 기존 parser/analyzer/renderer/audio 알고리즘 개편은 이번 정책 정리만으로 승인된 범위가 아니다.

## 9. 구현 및 검증 상태

본 문서는 정책 정리이며 MIDI 기능 구현 완료를 뜻하지 않는다. 활성 작업본의 MIDI 코드는 이번 작업에서 변경하지 않았다. 향후 변환 결과는 기존 validator와 parser/analyzer, 저장·재로드 경로까지 확인해야 한다.
