# 편집 후 산출물 갱신 비교

`regression-code/`에서 실행한다.

```powershell
npm.cmd run bench:edit-rebuild
# 결과를 모을 폴더를 직접 지정할 수도 있다. 같은 폴더의 결과 파일은 덮어쓴다.
npm.cmd run bench:edit-rebuild -- ..\.agents\tmp\presentation-benchmark
```

기본 출력은 저장소의 `.agents/tmp/edit-rebuild-<UTC 실행시각>/`이다.
`comparison.csv`는 표 계산 프로그램에서 열 수 있는 비교표,
`results.json`은 반올림 전 표본·조건·편집 명령·악보 해시·검증 결과다.
모든 사례의 검증과 측정이 끝난 뒤 파일을 저장한다. 실패한 실행의 부분 출력은 발표 자료로 사용하지 않는다.

## 비교 범위

현재 제품 함수로 동일한 원본에 동일한 편집을 적용한다.
두 경로 모두 셀 변경과 런타임 인덱스 재생성을 포함하며,
그다음 전체 산출물을 생성하거나 이전 산출물을 재사용한다.
기존 profiler 세션은 시작하지 않고 외부 타이머 하나로 전체 계산 시간을 잰다.
제품의 profiler·UI·parser·analyzer·renderer·audio 구현은 변경하지 않는다.

- 포함: 셀 변경, 인덱스 생성, 파싱·분석, renderer 입력 생성/병합.
- 제외: 최초 로드·검증, 상태 준비, Canvas draw 및 화면 표시, DOM, audio schedule, Undo 이력, 결과 비교, 파일 출력.
- Node 계산 시간이며 브라우저 반응속도·FPS·음향 지연을 나타내지 않는다.
- 구버전과 신버전의 비교가 아니라 **현재 코드의 전체 재계산과 재사용 경로 비교**다.
- fallback·무변경·편집 거절은 실패 처리하므로 빠른 무변경 편집이 표본에 섞이지 않는다.

## 입력과 검사

합성 악보 100/1,000/9,000열을 사용한다. 세 트랙에 같은 16열 패턴을 반복한다.
패턴당 7셀로 gliss, tuplet, hold, vibrato, tremolo를 포함한다.
끝의 불완전한 패턴은 만들지 않는다. 실제 셀 수와 활성 트랙은 JSON에 기록한다.
실제 곡의 성능 또는 모든 악보의 성능 상한을 대표하지 않는다.

| 사례 | 실제 변경 | 의도 |
| --- | --- | --- |
| note-single | basic의 8열 C를 C@p(62)로 변경 | 한 트랙 갱신 |
| note-batch-32 | basic의 G 행 0~31열에 입력 | 32셀 일괄 삽입 |
| note-all-tracks | 세 트랙의 8열 C를 변경 | 재사용 이점이 작은 조건도 포함 |
| global-bpm | 첫 BPM을 120에서 140으로 변경 | 전역 산출물 갱신 |

전체·재사용 경로의 문서/인덱스·파싱·분석·renderInput을 deepStrictEqual로 비교한다.
제품의 실제 편집 함수 결과와도 대조한다. 반복 이후 마지막 결과를 다시 비교하고,
원본 문서·기존 산출물·명령의 불변성을 검사한다. 검사는 측정 구간 밖에 둔다.

## 측정과 발표 해석

각 사례를 10쌍 워밍업한 뒤 51쌍 측정한다. AB/BA 실행 순서를 교대하며,
항상 같은 원본에서 시작한다. 준비·콘솔 출력·검증은 타이머 밖이다.
GC를 강제로 실행하거나 느린 표본을 제거하지 않는다.
중앙값과 nearest-rank P95를 저장하며 표에서만 반올림한다.
감소율은 `(전체 중앙값 - 재사용 중앙값) / 전체 중앙값 × 100`이다.
음수는 재사용 경로가 더 느린 경우이며 그대로 남긴다.

발표 표에는 Node 버전, CPU, 열/셀 수, 51회 중앙값, 측정 범위를 함께 적는다.
전체 트랙 편집 등 이득이 작거나 음수인 결과도 숨기지 않는다.
한 프로세스의 반복 측정이므로 환경·실행 간 변동까지 입증하지 않는다.
발표용 수치는 시연 노트북에서 다른 부하를 줄인 상태로 다시 실행하고,
필요하면 별도 프로세스로 반복하여 결과가 크게 달라지는지 확인한다.
실제 발표 악보를 측정하려면 별도로 그 악보에 맞는 고정 편집 사례를 정해야 한다.

외부 코드·새 의존성은 사용하지 않았다. 기존 `benchmark_runtime_reuse.ts`의
워밍업·교대 측정·동일성 검사 방식을 프로젝트 내부 참고로 사용했다.

합성 악보와 편집 사례는 `benchmark_edit_fixture.ts`에서 관리한다.
브라우저 viewport/전체 그리기 및 네 조건 비교는 `benchmark_render.md`를 따른다.
Node와 브라우저의 실행 환경 및 포함 범위가 다르므로 두 표의 수치를 더하지 않는다.
