목표는 화면 좌표계가 유지되는 셀 편집에서 변경 영향 영역만 지우고 복원하며, 그 밖의 기존 픽셀을 보존하는 것이다. 전체 렌더 아이템 재사용과 Canvas 픽셀 재사용을 구분한다. 이벤트 diff 또는 아이템 patch만으로 부분 재그리기가 완료되었다고 판단하지 않는다.

착수 전에는 edited track/global 산출물 재계산, eventId 기반 item patch, viewport 선별이 구현되어 있다. 그러나 기본 viewport 경로는 동적 레이어의 가시 범위를 다시 그리며, `dirtyTickRange`를 실제 삭제·복원 범위로 사용하지 않는다. 비viewport 경로의 일부 dirty-range 처리는 이번 목표가 주 실행 경로에 적용되었다는 근거가 아니다.

## 3. 유지할 처리 경계

1. `app_runtime.ts`가 `partial_rebuild_artifacts.ts`를 호출해 편집 후 전체 `renderInput`을 포함하는 새 AppState를 만든다.
2. 전체 `renderInput`은 스크롤·zoom·전체 재그리기의 기준으로 계속 보관한다.
3. 기존 base 입력 재사용을 유지한다. 셀 편집에서 `createCanvasRenderInput()`을 다시 호출하지 않는다.
4. 주 변경 시작점은 `partial_rebuild_plan` 및 그 이후의 orchestration/renderer 연결이다. VR-D1에 따라 선행 `partial_rebuild_artifacts.ts`의 track 병합 순서 보완도 좁게 포함한다.
5. parser/analyzer의 갱신 범위, RuntimeDocument/index 재생성, 오디오 전체 재생성, 편집 이력·batching 의미는 유지한다.

영향 경계는 app의 계획 전달, orchestration의 변경 판단, renderer의 표시 영역 산정·삭제·복원이다. 저장/import/validation, parser/analyzer, audio generator 경계는 이번 작업에서 수정하지 않는다.

artifact 순서 보완은 사용자 승인된 범위 예외다. 전체 renderInput 생성과 분석 범위를 유지한다는 원칙은 그대로다.

## 4. 전체 상태와 부분 입력

`PartialRebuildPlan`은 변경 이벤트·그룹·fallback을 표현하는 논리적 계획이다. `partialRenderInput`은 계획을 화면 좌표와 결합한 실행 입력이다. renderer-owned 타입명은 `CanvasPartialRenderInput`을 사용한다. 전체 AppState나 core 분석 타입을 renderer 입력으로 전달하지 않는다.

부분 입력에 필요한 정보:

| 정보 | 의미 |
| --- | --- |
| 렌더 기준 식별 정보 | 마지막으로 그린 layout/view와 요청의 일치 여부를 검증할 정보 |
| 레이어별 dirty 영역 | 해당 레이어에서 지우고 복원할 CSS pixel 사각형 목록 |
| 레이어별 draw 대상 | 최신 전체 renderInput에서 dirty 영역에 걸치는 아이템을 조회한 목록 |
| 실행 구분 | 부분 재그리기 / 그리기 불필요 / 기존 viewport 재그리기 fallback |

부분 목록은 최신 아이템의 참조를 이용한다. 전체 아이템을 깊은 복사하거나 두 개의 독립적인 진실 원천을 만들지 않는다. 삭제 아이템은 draw 대상에 들어가지 않지만 이전 표시 영역은 dirty 계산에 필요하다. 따라서 계획 구성 중에는 편집 전·후 입력을 모두 사용할 수 있어야 한다.

`unchanged`도 지울 영역과 겹치면 복원 대상이다. 변경 ID 목록만으로 draw 목록을 만들지 않는다. 반대로 dirty 영역 밖의 unchanged는 draw하지 않는다.

책임 분리 권장안:

| 주체 | 책임 |
| --- | --- |
| app | 전후 renderInput, DOM에서 읽은 표시 옵션, 논리적 변경 힌트 전달 |
| orchestration | 변경 그룹·ID·논리 fallback 결정. renderer-owned 힌트로 변환 |
| renderer 부분 입력 생성 | 전후 표시 비교, 좌표·경계 계산, 교차 아이템 선별, 화면 기준 검증 |
| renderer 실행·상태 | clip/clear/draw, 실제 적용한 입력 버전·좌표계·bitmap 기준 기록 |

`PartialRebuildPlan` 전체에는 analyzer 이벤트와 audio 계획이 있으므로 renderer에 직접 넘기지 않는다. `CanvasPartialRenderInput`은 한 번의 실행 요청이며 AppState에 별도의 지속 갱신 상태로 보관하지 않는다. 기존 AppState 의존 orchestration 전체 재편은 이번 범위가 아니다.

## 5. 부분 재그리기 허용 조건

아래 조건을 모두 만족해야 한다.

- 이전 Canvas 출력이 현재 편집 전 상태와 일치하며 최초 그리기가 완료됨
- 기존 계획에 fallback이 없음
- 스크롤 위치, viewport/overscan 범위, Canvas 원점이 같음
- 레이아웃, 행 순서, 열 크기, zoom/speedScale, DPR, Canvas bitmap 크기와 변환이 같음
- 색상·투명도·텍스트 표시·잇단음 표시 등 출력 옵션이 같음
- 변경 영향 영역과 그 영역에 걸치는 아이템을 안전하게 결정할 수 있음

화면 조건 변경, 구조 편집, resize, 초기 화면, 불명확한 경계, 오래된 요청은 기존 전체 viewport 경로로 처리한다. 전체 viewport 재그리기는 전체 악보 폭의 bitmap 생성을 뜻하지 않는다.

렌더 요청 사이에 다른 편집이나 스크롤이 끼면 마지막으로 실제 그린 상태를 기준으로 계획을 합치거나 fallback한다. 화면은 이전 상태인데 최신 한 건의 diff만 적용하는 것을 금지한다.

화면 기준 구현 권장안: 마지막 실제 Canvas 원점, overscan 포함 bitmap 범위, bitmap 크기, 해상도 상한이 반영된 effective DPR/transform, 입력 버전, layout/표시 옵션을 renderer가 기록한다. 현재 DOM 값으로 마지막 draw 범위를 추정하지 않는다. 기존 app의 viewport 캐시와 중복된 진실 원천을 만들지 않고 renderer 결과에 맞춰 동기화한다. overscan 내부 스크롤로 draw가 생략된 경우도 원점 일치를 검사한다. 화면 밖 편집의 no-op은 기존 bitmap 범위 전체에 영향이 없음을 확인한 뒤 입력 버전만 갱신하며, 그리지 않은 새 범위를 그린 것으로 기록하지 않는다.

## 6. dirty 영역 계산

1. 변경된 이벤트와 관련 아이템의 편집 전·후 표시 영역을 합친다.
2. 삭제는 이전 영역, 추가는 이후 영역, 변경은 양쪽 영역을 사용한다.
3. 레이어별로 계산한다. 여러 사각형은 필요에 따라 합칠 수 있으나 실제 사용한 합친 영역 전체의 복원 대상을 다시 조회한다.
4. viewport bitmap에 해당하는 영역과 교차시킨다. 화면 밖 변경이라도 화면 안으로 이어지는 연결선·텍스트가 있으면 그 부분을 포함한다.
5. 실제 표시 영역의 교집합이 없고 화면 조건이 같으면 입력 상태만 갱신하고 Canvas 호출을 생략한다.

표시 경계에는 노트 사각형 외에 글자 폭·돌출, stroke와 안티앨리어싱 여유, 주법, gliss 연결선, tuplet/노트 마커를 포함한다. `dirtyTickRange`는 후보 범위이며 최종 픽셀 경계의 대체물이 아니다. CSS pixel과 DPR이 반영된 bitmap 좌표 변환을 한곳에서 일관되게 처리한다.

연결 상태가 바뀌면 unchanged ID의 파생 표시도 달라질 수 있다. orphan gliss와 연결선 등은 변경 ID 자체에 한정하지 않고 관련 표시의 전후 경계를 포함한다. 필요한 관계를 확정할 수 없으면 fallback한다.

범위 축소와 복원 정확성을 위한 구현 권장안:

- global text는 셀 식별 기준으로, global/note marker는 종류와 표시 속성·연결 결과를 기준으로 전후 DTO를 비교한다. `changedEventIds`가 비어 있어도 전역 변경은 있을 수 있다. 새 배열 참조만으로 모든 항목을 changed 처리하지 않는다.
- 표시 경계 계산은 renderer 안에서 draw의 좌표·폰트·정렬·주법 계산과 공유한다. 기존 tick 필터만 재사용하면 범위 밖에서 돌출한 텍스트를 놓칠 수 있으므로, 후보 조회 자체가 실제 표시 경계를 포함해야 한다.
- 서로 먼 변경은 복수 사각형으로 유지한다. 필요 이상의 단일 min/max 범위 병합을 피한다.
- 복원할 unchanged 아이템의 전체 경계를 다시 dirty에 합치는 연쇄 확장은 하지 않는다. 변경 영향으로 확정한 dirty에 교차 아이템을 clip하여 복원한다. 파생 표시 자체가 달라진 경우는 변경 영향에 포함한다.
- 하나의 sourceEventId에서 여러 렌더 아이템이 나올 수 있으므로 부분 조회·참조 재사용에서 eventId와 item의 1:1 관계를 가정하지 않는다.

VR-D2 확정 범위: 변경 이벤트/렌더 아이템의 전후 표시 영역을 단위로 처리한다. 하나의 아이템 안에서 텍스트 anchor·body·effect 중 바뀐 부분만 별도로 diff하거나 dirty 단위로 분해하는 최적화는 구현·후속 계획에서 제외한다. 텍스트 돌출과 주법을 포함하는 전체 표시 경계 산정 및 복원은 화면 정확성을 위해 계속 필요하다. 이 결정은 별도 globalText/mute/marker 아이템의 구분이나 레이어별 복원을 없애는 의미가 아니다.

## 7. 레이어 삭제와 복원

각 레이어에서 다음 순서를 지킨다.

```text
dirty 영역의 합집합으로 clip 설정
  → dirty 영역 clear
  → 최신 renderInput에서 교차 아이템을 기존 순서로 draw
  → clip과 context 상태 복원
```

- 부분 경로에서는 레이어 전체 `clearRect`, Canvas width/height 재할당, 전체 viewport draw를 수행하지 않는다.
- 기존 draw 함수에 포함된 전체 clear는 부분 실행과 분리한다. 기존 full 경로의 동작을 유지한다.
- clip은 보존 영역에 반투명 항목을 중복 합성하거나 텍스트를 덧칠하는 일을 막는다.
- 겹치는 dirty 사각형 때문에 같은 픽셀에 여러 번 합성하지 않는다. 합친 clip에서 아이템을 한 번씩 그리거나 겹치지 않는 영역으로 나눈다.
- 노트 body/effect → gliss → text → overlay 등 기존 전체 렌더의 순서를 유지한다. 트랙 사이의 겹침 순서도 보존한다.
- note/global text나 grid/global marker처럼 같은 Canvas를 공유하는 표시는 지워진 영역에서 함께 복원한다. unchanged를 이유로 필요한 배경·공유 레이어 항목을 누락하지 않는다.
- 정적 base/layout 레이어는 변경이 없으면 건드리지 않는다. 선택·재생 커서 등 별도 UI overlay는 기존 갱신 경로를 유지하되 지워지거나 잔상이 남지 않도록 검증한다.

전체 builder, track 교체, event patch, 부분 복원은 동일한 그리기 순서를 보장해야 한다. 기존 builder의 비교 규칙을 공유하거나 동일한 순서를 보존하는 병합을 사용한다. 단순히 변경 항목을 배열 끝에 붙이지 않는다. clip에 의존한 전체 목록 draw 대신, dirty와 교차하는 목록을 먼저 선별한 후 draw한다.

## 8. 구현 순서

1. 전체 생성·artifact track 병합·event patch의 그리기 순서를 보장한다. 겹친 트랙의 순서 회귀 검사를 먼저 둔다.
2. renderer-owned 힌트/부분 DTO와 실제 화면 기준을 연결한다. no-op/partial/fallback을 명시적으로 구분한다.
3. 일반 노트의 추가·수정·삭제를 부분 draw에 연결하고, 새로 생성한 전체 입력의 full render와 비교한다.
4. 텍스트 돌출, mute, 주법, 겹친 트랙, gliss/orphan, tuplet 마커의 경계·복원을 확장한다.
5. 전역 DTO 비교와 공유 레이어 복원을 연결한다.
6. batch/undo/redo, 스크롤·resize·DPR 전환, 픽셀 비교·호출 계측·성능 및 회귀 검사를 수행한다.
7. 검증 후 배포 사본 동기화·빌드·배포를 별도 단계로 진행하고 실제 완료 상태를 기록한다.

중간 단계에서 미지원 표시를 fallback할 수 있다. 일반 편집을 무조건 fallback시키거나 가시 영역 전체를 dirty로 지정한 채 완료로 처리하지 않는다. 최종 목표는 기존 지원 표시를 포함한 셀 편집에 적용하는 것이며, 남은 fallback 사유는 구체적으로 기록한다.

## 9. 검증 및 완료 기준

자동 검사와 실제 브라우저 Canvas 비교를 함께 수행한다.

- 동일한 편집 후 상태를 fresh full viewport render와 partial render로 각각 출력하여 레이어별 픽셀을 비교한다. 같은 브라우저·폰트·DPR에서 비교하며, 허용 오차가 필요하면 근거와 범위를 명시한다.
- full 비교 기준은 편집 후 악보에서 정규 builder로 새로 생성한 입력도 포함한다. 같은 patch 입력을 양쪽에 공유하는 비교만으로는 순서 오류를 검출할 수 없다.
- dirty 영역 밖 픽셀 보존, 영역 밖 unchanged draw 생략, 영역 안 unchanged 복원을 확인한다.
- draw/clear 호출 계측으로 부분 경로가 실제로 실행되는지 확인한다. 전부 fallback한 결과가 full render와 같다는 이유만으로 통과시키지 않는다.
- 추가·삭제·음정/길이 변경·텍스트 변경·뮤트·주법·겹친 반투명 트랙·gliss 연결/해제·tuplet·전역 timing/dynamics를 포함한다.
- viewport 경계, 화면 밖 편집, reverseRows, zoom/DPR 변화, 스크롤과 편집의 연속 발생, batch/undo/redo를 포함한다.
- `test:partial`, `test:edit`, `test:layout`, 관련 renderer 검증 및 `build`를 수행한다. 브라우저 실행 수단과 기존 테스트 구성을 확인한 후 필요한 검사를 추가한다.
- 기존 `test:view`의 Fit Height 기대값 불일치는 사용자 결정에 따라 별도 보류 사항이다. 이번 작업의 새 실패와 구분하고 이를 핑계로 관련 신규 검사를 생략하지 않는다.
- 동일 악보·viewport·편집 조건에서 draw 아이템 수, clear 면적, 처리 시간을 비교한다. 단발 측정으로 일반 성능 향상을 단정하지 않는다.
- 추가 회귀 사례: extra/basic 겹침의 편집 전후 순서, event diff가 빈 전역 편집, unchanged 이벤트의 orphan 전환, tick 밖 긴 텍스트의 교차 복원, 떨어진 두 셀 batch, overscan 안 스크롤 직후 편집, no-op 후 후속 스크롤.
- 성능은 부분 입력 생성/경계 조회, draw, 편집 전체 시간을 분리한다. 전체 이벤트 diff·배열 identity 변경에 따른 visible index 재구성·track 재분석·오디오 재생성 비용은 남는다. draw 감소를 전체 편집 지연의 동일 비율 감소로 해석하지 않는다.

완료는 전체 렌더와 같은 결과, 보존 영역 불변, 실제 draw 범위 축소, 안전한 fallback을 모두 확인한 상태이다. 문서 작성 또는 입력 patch만으로 완료 표시하지 않는다.

## 13. 로컬 구현·검증 결과 — 2026-09-29

### 구현과 재개 위치

- `src/renderer/canvas_viewport_renderer.ts`: 마지막 실제 입력·원점·bitmap/transform·표시 옵션을 renderer 내부에서 관리한다. 전후 DTO 표시 비교, 경계 캐시와 x축 조회, 복수 dirty 사각형, 레이어별 clip/clear/복원을 담당한다. 부분 입력은 최신 아이템 참조로 만들며 AppState에 별도로 저장하지 않는다.
- `canvas_paint_bounds.ts`, `canvas_note_renderer.ts`, `canvas_marker_renderer.ts`: 실제 draw와 좌표·폰트 계산을 공유한다. 텍스트 돌출, 주법, mute, gliss/orphan, tuplet, 전역 마커를 경계에 포함한다. 전체 viewport 선별도 같은 경계를 사용한다.
- `canvas_item_order.ts`: 전체 builder, artifact track 병합, event patch가 공통 정렬을 사용한다. VR-R2/VR-D1의 두 순서 문제를 함께 수정했다.
- `app/main.ts`와 `app_ui_sync.ts`: 편집 전 입력과 논리 fallback만 renderer-owned 힌트로 전달한다. app의 viewport 캐시는 renderer가 실제로 그린 범위를 따른다. plan 전체나 core 이벤트를 renderer에 전달하지 않는다.
- VR-R1~R6 대응을 연결했고, VR-R7은 떨어진 dirty를 분리하되 VR-D2의 아이템 단위를 유지한다. parser/analyzer/audio/storage 계약은 변경하지 않았다.
- 화면 밖 편집은 입력 기준만 갱신하고 Canvas 호출을 생략한다. 초기 화면, view/옵션 변경, 실제 bitmap 변경, 오래된 입력, plan fallback은 전체 viewport 경로를 사용한다. 기존 지원 표시를 종류별로 일괄 fallback하는 제한은 없다.

### 검증 및 측정의 한계

- `npm run test:canvas` 추가: Playwright로 로컬 Chrome에서 실행한다. 기본 설치 Chrome을 사용하며 다른 실행 파일은 `SPRED_CHROME_PATH`로 지정한다. 테스트가 임시 Vite 서버와 브라우저를 종료한다.
- 합성 Canvas 사례 240개(20종 × zoom 3종 × DPR 4종), 독립 정규 builder와 비교하는 실제 편집/batch/undo/redo 66단계, 실제 앱 UI 연결 6개 및 view/bitmap/stale/fallback 전환 검사 통과. 역순 행, 겹친 트랙, 빈 event diff의 전역 편집, 파생 orphan 변화, overscan 스크롤과 no-op 이후 스크롤을 포함한다.
- dirty 밖 픽셀은 오차 없이 일치해야 한다. dirty 안은 alpha와 8-bit premultiplied RGB 차이 2 이하, effective DPR 0.5 미만에서는 3 이하를 허용한다. 동일 장면을 새 Canvas에 clip하여 그리는 독립 대조에서도 각각 최대 2/3 차이가 발생함을 확인했다. 반복 픽셀 읽기에 따른 Chrome GPU/CPU 전환 차이는 테스트의 `willReadFrequently` 고정으로 통제한다. 모든 브라우저·폰트·GPU에 대한 보장은 아니다.
- 실제 draw/clear 호출을 계측하며 no-op은 0회다. 9,000개 아이템 악보의 동일 단일 편집에서 draw 대상은 full viewport 73개 → partial 3개, clear 면적은 243,000 → 810 CSS px²였다.

- `test:partial`, `test:edit`, `test:layout`, `test:track`, `typecheck`, `build` 통과. 기존 `test:view` Fit Height 불일치는 합의대로 수정·검증 대상에서 보류했다.

### 코드 기준 시간·공간 복잡도

E=전체 analyzer 이벤트 수, N=노트/뮤트 아이템 수, K=변경 이벤트 수, M=전역·파생 표시 수, V=viewport draw 대상, R=병합 후 dirty 사각형 수, D=dirty와 교차하는 draw 대상이다. `Sort(n)`은 실제 엔진/배열 상태에 따른 비교 정렬 비용이며 보통 상한 분석에서 O(n log n)으로 둔다. Map/Set 조회는 평균 O(1), 이벤트/텍스트 길이는 고정일 때의 표다.

| 단계 | 구 버전 | 현재 버전 | 해석 |
| --- | --- | --- | --- |
| eventDiff | O(E + Sort(E)) | 동일 | ID Map/합집합/정렬 후, unchanged도 전후 JSON fingerprint를 계산. 모두 유지되는 E개이면 JSON.stringify 2E회. 실제로는 총 이벤트 직렬화 길이 비용도 포함 |
| diff 이후 plan 생성 | O(K + Sort(K)) | 동일 | 변경 ID 정렬과 전후 시간 범위 산정. 그룹 종류 수는 상수 |
| note/mute patch | O(N + K) | O(N + K + Sort(N)) | 현재 추가 정렬은 겹친 트랙의 올바른 합성 순서 보장을 위한 비용 |
| artifact track 병합만 | O(N + M) | O(N + M + Sort(N) + Sort(M)) | parser/analyzer 비용을 뺀 병합 부분. 이번 실측에서는 실행하지 않음 |
| renderer 준비, 일반 단일 변경 | O(N + Sort(N) + M + Sort(V)) | O(N + M + K² + NR) | 구 버전은 patch가 새 배열을 만들면 viewport index를 다시 생성/정렬. 현재는 일반 이벤트 diff 없이 ID 조회표를 재사용하나 전체 scene 구성과 교차 조회 순회는 남음 |
| 실제 draw | V개 아이템 | D개 아이템 | 시간은 각 아이템의 글자·효과·연결선 복잡도에도 의존. 준비 비용 표와 분리 |

현재 식의 K²는 dirty 사각형 병합 상한, NR은 dirty별 교차 조회 상한이다. 지원 표시의 이벤트당 아이템 수가 일정하지 않으면 K 대신 실제 변경 표시 수를 사용해야 한다. 긴 연결선 때문에 구 viewport index 역방향 후보 순회가 V보다 클 수도 있으나 최대 N 순회는 식에 포함된다. 변경 전후 마커 그룹의 fingerprint 비용은 M 및 직렬화 길이에 비례한다.

K/M/R이 작게 고정되면 현재 renderer 준비는 O(N)이다. 하지만 앞의 eventDiff는 그대로이고 patch에도 정렬이 있어 **부분 갱신 전체를 O(K)로 줄인 것은 아니다**. 거의 정렬된 입력의 sort 실측은 최악 상한보다 작을 수 있어, 실제 시간은 두 버전 모두 이번 범위에서 대체로 선형에 가까웠다.

보조 공간도 고정 크기 아이템 기준 두 버전 모두 대략 O(E+N+M+K) 규모다. 현재는 표시 경계·fingerprint·ID 조회표를 지속 보유하여 상수 비용이 추가된다. Map/WeakMap의 GC 시점, 가변 길이 텍스트, Canvas bitmap 메모리는 이 점근 표만으로 바이트 수를 산정할 수 없으며 실제 heap 사용량은 이번에 측정하지 않았다.

- 결론: 이번 변경은 실제 draw 범위를 줄였지만, 부분 갱신 계산 전체의 점근 복잡도를 낮추지는 않았다. 이번 조건에서는 계산 합계도 유의미하게 줄지 않았다. 가장 큰 공통 비용은 unchanged까지 전체 직렬화하는 eventDiff다. 이를 바꾸는 작업은 이번 계측에서 수행하지 않았으며 별도 설계·검증 대상이다.

## 16. eventDiff 단순화 격리 실험 — 2026-09-29

### 결정 범위

사용자는 구현 복잡도 대비 성과를 기준으로 부분 갱신을 되돌리는 선택도 열어 두고, 먼저 eventDiff 단순화 가능성을 검토하기로 했다. 이번에는 제품 코드를 바꾸지 않고 비교 함수만 임시 Vite 변환으로 바꾸었다. 14장의 plan 재사용 구현은 그대로이며 아래 후보는 미적용이다.

사용처 확인: 구 버전도 plan의 ID/그룹을 item patch 및 unchanged 아이템 참조 재사용에 사용한다. 현재 버전은 픽셀 부분 복원에도 사용한다. audio 계획은 생성하지만 실제 audio 갱신 경로의 소비는 찾지 못했다. 따라서 plan 전체를 무사용 객체로 간주해 삭제하면 안 된다. 제거안은 artifact 전체 입력으로의 직접 렌더 및 정렬/fallback 계약을 함께 검토해야 한다.

### 비교 후보와 방법

`node dev/benchmark_event_diff_experiment.cjs`로 재현한다. ID Map·정렬·중복 감지·결과 객체 형식은 유지하고 비교식만 바꾼다.

1. 기존: 전후 JSON.stringify 비교.
2. 참조 우선: 같은 객체이면 unchanged, 다르면 기존 JSON 비교. 지속 캐시는 없다.
3. JSON 캐시: 참조 우선 + WeakMap에 객체별 JSON 문자열 저장. 다음 편집에서 이전 이벤트 직렬화를 재사용한다.
4. 구조 직접 비교: 유효한 analyzer plain DTO를 재귀 비교한다. 키 순서, undefined 객체 필드 생략 등을 이번 DTO 범위에서 기존 JSON 비교와 맞춘 실험 함수다. 범용 JSON 대체 라이브러리로 사용하지 않는다.

- Chrome `154.0.8037.58`의 같은 세션에서 네 후보를 교대 실행했다. 각 조건 3라운드, 워밍업 5회 후 20회 측정. 단일 이벤트의 텍스트 변경, 입력 준비·복제는 측정 밖이다.
- 미변경 이벤트 객체를 모두 재사용하는 상한 조건, 1/3을 재생성하는 조건, 전부 재생성하는 조건을 분리했다. 재생성에는 deep clone을 사용하여 합성 입력이 동일한 중첩 객체까지 공유해서 유리해지지 않도록 했다.
- 실제 score 편집 9회에서도 참조를 확인했다. 3트랙의 첫 note 편집은 27개 중 미편집 track의 18개 참조를 재사용하고, global 편집은 27개 모두 재사용했다. 같은 track의 미변경 이벤트는 재생성된다. 따라서 “9,000개 중 1개만 새 객체”라는 가정만으로 개선 폭을 추정하면 안 된다.
- 분류·순서·previous/next 참조 동일성을 기존 diff와 비교한 1,036개 검증 통과. 실제 analyzer 출력과 역방향 비교, 추가/삭제, 중복 ID, 중첩 primitive의 개별 변경, optional undefined 및 키 순서 변화가 포함된다. 별도 재실행 1,018개도 통과했다. 변경 객체는 새 복사본을 사용한 조건이며 임의 mutation 지원을 보장하지 않는다.

### 위험·복잡도와 권장 판단

- 참조 우선은 가장 작은 변경이다. 별도 상태 없이 미편집 track과 global 편집의 불필요한 직렬화를 제거한다. 다만 단일 track 전체 재생성에는 큰 효과가 없다. 현재 유효 DTO에서 같은 참조의 전후 JSON 결과는 같으므로 캐시 방식처럼 객체 수명 전체의 불변성을 요구하지 않는다.
- 캐시는 전체 재생성에서도 약 16~19% 줄었지만 문자열 보관 메모리와 불변 객체 수명 계약이 추가된다. 초기 cache miss 비용은 워밍업 중앙값에 포함되지 않는다. 캐시한 객체를 나중에 수정하면 **실제 변경을 놓치는 반례**가 재현됐다(기존 changed 1 / 캐시 changed 0). analyzer 내부에는 이벤트 조립 중 mutation이 있고 공개 타입도 readonly 계약이 아니므로, 완료된 산출물의 불변성 검토 없이 제품에 넣지 않는다.
- 일반 구조 비교는 이번 전체 재생성 조건에서 오히려 느렸다. 전문 필드별 비교 함수로 확대하면 스키마 유지보수 부담도 생기므로 현재 추천하지 않는다.
- 세 후보 모두 전체 ID 조회·정렬·diff entry 생성은 남는다. O(K) 알고리즘으로 바뀌는 것이 아니며, 줄이는 것은 직렬화 횟수/문자열 생성 비용이다.
- 현재 권장안은 참조 우선 비교를 작은 독립 개선 후보로 두고, 캐시는 보류하는 것이다. 이 개선은 구 viewport renderer에도 적용할 수 있으므로 **새 부분 renderer 유지의 근거로 혼동하지 않는다**. 최종 유지/단순화 판단은 같은 diff 개선을 적용한 경로끼리 비교해야 한다. 제품 적용·모듈 제거·배포는 이번 실험에서 수행하지 않았다.
