# 3.9. Artifact 직접 렌더 구현 계획 해설

작성일: 2026-10-01. 상태: **구현 및 자동 검증 완료 / 커밋·배포 미수행**. 계획의 처리 흐름과 파일별 설명을 유지하고, 실제 결과는 9절에 기록한다.

## 1. 이번 변경의 목적과 결론

`eventDiff → partialRebuildPlan → renderInput patch` 단계를 제거하고, 이미 완성된 artifact의 `renderInput`을 기존 renderer에 직접 전달한다. 전체 이벤트를 다시 비교하고 배열을 재조립하는 비용과 관리할 모듈 수를 줄이는 것이 목적이다.

**plan 관련 4개 파일과 `core/analyze/event_diff.ts`를 삭제했다.** 단, plan 파일에 함께 들어 있는 편집 종류별 redraw scope 판정은 옮겨서 유지한다. `partial_rebuild_artifacts.ts`도 유지한다. 부분 parser/analyzer 갱신까지 없애는 계획이 아니다.

여기서 “전체 입력을 직접 렌더”한다는 말은 전체 악보를 매번 Canvas에 그린다는 뜻이 아니다. 완성된 입력을 제공하되 기존 가상화와 note/global/all 레이어 갱신 분기를 그대로 사용한다. 변경된 이벤트만 찾아 draw하는 별도 알고리즘은 두지 않는다.

## 2. 현재 상태와 검토 근거

구현 착수 전 제품 코드는 부분 draw 실험 이전의 `aac9969` 상태로 복원되어 있었다. 검토 시 로컬 HEAD는 문서 변경을 포함한 `23423dc`다. 이후 별도 실험 경로에서 plan/patch를 생략하고 artifact 순서를 보정하는 방식을 확인했다.

- 편집·undo·redo 72단계에서 전체 builder와 산출물 및 Canvas 출력을 비교했다.
- 실제 app 연결 12개 검사에서 eventDiff가 호출되면 예외를 발생시키도록 설정하고 직접 렌더 경로를 확인했다.
- 이는 제품 구현 완료나 모든 악보·구조 편집·오디오 동작 검증 완료를 의미하지 않는다.

| 노트 수 | 기존 artifact 이후 처리 | 직접 경로 |
| ---: | ---: | ---: |
| 900 | 2.30ms | 0.40ms |
| 3,000 | 6.00ms | 0.40ms |
| 9,000 | 17.80ms | 0.50ms |

단일 track 합성 악보에서 가운데 노트 **1개**를 변경한 시험이다. 9,000개가 모두 화면 안에 보이는 조건이 아니며 가상화를 켰다. 기존 측정 구간은 이벤트 수집·diff·plan·patch·renderer이고, 직접 경로는 배열 복사·정렬·같은 renderer다. artifact 생성, 이력 처리, UI 동기화, 오디오 재설정 및 실제 화면 표시 완료 시간은 위 표에서 제외했다. 일반 사용 환경에서 같은 개선 폭을 보장하지 않는다.

재현 조건·원본 로그·한계는 [직접 렌더 검토 기록](report-prep/3.8-partial-redraw-review/1.2-artifact-direct-review.md)에 있다. 이 자료는 로컬 보고서 보관 영역이며 Git 추적 대상이 아니다. 이전 부분 draw 실험의 실패 근거와 이번 제거 실험의 성능 근거를 보고서에서 구분한다.

## 3. 변경 전후 흐름

현재:

```text
편집 batch → 문서/index 갱신
  → 편집 track/global의 parser·analyzer·render item 재생성
  → 기존 산출물과 병합하여 완성된 artifact 생성
  → 이전/이후 전체 이벤트 수집 → eventDiff → plan 생성
  → plan에 따라 이전/새 renderInput을 다시 patch
  → note/global/all 분기 → 기존 viewport renderer
```

변경 후:

```text
편집 batch → 문서/index 갱신
  → 편집 track/global의 parser·analyzer·render item 재생성
  → 전체 builder와 같은 순서로 병합하여 완성된 artifact 생성
  → 편집 종류로 note/global/all 판정 → 기존 viewport renderer
```

artifact는 변경분만 담은 목록이 아니라, 변경하지 않은 산출물까지 포함한 다음 상태의 완성된 입력이다. 따라서 eventId로 이전 입력과 한 번 더 조합할 필요가 없다. 다만 현재 병합 순서 문제는 먼저 보완해야 한다.

## 5. 남길 기능과 책임 경계

### 5.1 편집 종류별 갱신

기존 `getScoreTextEditInvalidationKind(edits)` 결과를 사용한다.

| 편집 종류 | 렌더 범위 |
| --- | --- |
| noteCell | note |
| globalCell | global |
| mixedCell 등 나머지 cell batch | all |

이 판정은 편집 batch를 확인할 뿐 이전/이후 전체 analyzer 이벤트를 비교하지 않는다. 구조 변경의 별도 앱 갱신 경로도 유지한다. 실패·같은 값 입력·빈 batch의 기존 처리, undo/redo, 선택 상태, 편집 batching, 재생 위치 보존 및 실제 오디오 재설정은 유지한다.

### 5.2 artifact의 순서 보장

현재 track 교체는 “수정하지 않은 track 항목 + 수정 track의 새 항목”을 붙인다. 원래 앞에 그려져야 할 항목이 배열 끝으로 이동하면 겹친 track·마커의 출력이 달라질 수 있다. 기존 eventId patch에도 유사한 순서 문제가 있다.

전체 builder의 기존 순서를 기준으로 note/mute는 startTick → rowId → track draw order, marker는 종류별 기준 tick → 기준 rowId → track draw order로 정렬한다. 동일 키 항목의 순서까지 전체 builder와 일치하는지는 테스트로 확인한다. global text 및 global/note marker 결합 규칙도 기존 전체 builder와 맞춘다.

정렬은 **변경 그룹을 병합할 때** 수행한다. 변경하지 않은 그룹을 매번 복사하거나 스크롤·draw 때마다 정렬하지 않는다. 기존 상태가 공유하는 배열을 제자리 정렬하지 않고 새 병합 배열을 정렬하여 이전 상태·이력을 보호한다. 전체 builder와 artifact가 같은 정렬 함수를 사용하므로 규칙을 중복 관리하지 않는다.

이는 일부 겹침 상황에서 기존 잘못된 출력 순서를 고치는 변경이다. 기존 화면의 모든 픽셀을 그대로 재현하는 것이 아니라 독립 전체 builder 결과를 정답으로 검증한다.

### 5.3 제거하지 않는 계약

- analyzer의 `eventId`, renderer의 `sourceEventId` 및 이벤트 출력 구조는 유지한다. diff 삭제와 ID 삭제는 별개다.
- renderer의 `CanvasDirtyTickRange`와 nonviewport 범위 렌더 기능은 남긴다. plan 전용 타입이 아니며 기존 renderer에서 사용한다.
- 저장/import 형식, parser 해석, analyzer 의미, 오디오 생성 계약은 바꾸지 않는다.
- 실제 draw는 renderer, 부분 산출물 조합은 orchestration, UI 분기는 app이 담당한다. analyzer에 UI 갱신 판정을 넣지 않는다.
- 텍스트·주법별 세분화, dirty-pixel 부분 복원, 새 캐시·인덱스 관리 계층은 추가하지 않는다.

## 6. 주의할 동작 차이와 권장 판단

**중복 eventId 감지:** 기존 diff는 중복 ID를 감지해 plan fallback에 반영했다. main에서 이 fallback은 patch 생략/전체 렌더에 쓰이며 별도 runtime 재분석을 실행하지 않는다. 직접 경로는 ID 매칭 patch를 하지 않으므로 그 방어 분기는 필요 없어지지만, diff에 있던 중복 감지 자체도 사라진다. 권장안은 analyzer의 ID 고유성 테스트를 유지·보강하고 편집마다 전체 ID 검사를 새로 추가하지 않는 것이다. 런타임 진단 보장까지 필요하다면 별도 요구로 결정한다.

**nonviewport:** dirtyTickRange를 넘기지 않으면 해당 scope 전체를 다시 그린다. viewport 검증만으로 이 경로의 비용·동작까지 동일하다고 주장하지 않는다. 제품화 때 범위 없는 호출의 출력도 확인하되 기존 renderer API는 보존한다.

**복잡도:** 전체 이벤트 flatten·ID 정렬·내용 비교·patch 순회는 제거된다. 하지만 문서/index 갱신, 편집 track 재분석, 산출물 병합, 정렬, viewport 인덱스 준비는 남는다. 변경 그룹의 아이템 수를 M이라 하면 추가 병합 정렬은 일반적으로 O(M log M)이며 “변경 1개이므로 전체 작업 O(1)”인 설계는 아니다.

## 7. 구현 순서와 완료 기준

1. 전체 builder를 기준으로 artifact의 내용·순서, 변경하지 않은 track/global 재사용을 검증하는 테스트를 준비한다.
2. 정렬 규칙을 공용화하고 artifact 병합 순서를 고친다. 이전 배열을 변이시키지 않는지 확인한다.
3. main의 scope helper를 옮기고 plan·patch 연결을 제거한다. 완성된 artifact 입력을 그대로 사용한다.
4. 삭제 예정 5개 파일과 전용 테스트/import를 정리한다. `src/`와 `dev/`의 잔여 참조를 검색한다.
5. `build`, `test:partial`, `test:analyze`, `test:edit`, `test:layout`, `test:track`, `test:audio`, `test:game`을 실행한다. 관련 가상화 검증을 위해 `test:view`도 확인하고 기존 실패와 신규 회귀를 구분한다.
6. 실제 앱에서 편집·undo/redo·혼합 편집·화면 밖 편집 후 스크롤·역방향 행·겹친 track·gliss/tuplet/mute·전역 timing/dynamics를 확인한다. 별도 구조 변경 및 nonviewport 출력도 확인한다. 재생 위치·재생 결과는 UI/오디오 검증으로 보완한다.
7. 동일 입력·측정 구간으로 제품 구현의 비용을 다시 측정한다. 앞선 임시 실험 결과를 제품 측정값으로 대체 기재하지 않는다.
8. 실제 구현 완료에 맞춰 2.8 등 관련 명세와 HARNESS를 갱신하고 결과·잔여 한계를 기록한다.

기존 설치 환경에서 검증은 가능했지만, 복원된 lock의 `@emnapi/wasi-threads` 1.2.2/1.2.3 불일치로 `npm ci`가 실패한 이력이 있다. 재현 환경 제약으로 기록하며 의존성 수정은 이번 plan 제거와 구분한다. 이전 `test:view`의 FitHeight 관련 실패도 재확인 후 구분하여 보고한다. 구현 후 실행 결과는 9절에 기록한다.

## 8. 명세 충돌과 재개 안내

- **충돌 출처:** 2.8은 eventDiff/plan/patch 모듈을 현재 구조로 명시한다. 3.8은 부분 draw 실험 기록이다.
- **충돌 내용:** 이번 계획은 2.8의 후속 plan/patch 단계를 제거하며, 3.8의 dirty 영역 복원을 재도입하지 않는다.
- **이번 해석:** 현재 제품과 향후 계획을 구분한다. 사용자 승인 후 이 계획을 구현했으며 현재 계약은 갱신한 2.8을 따른다. 3.8은 HARNESS의 최신 결정에 따라 보관 기록으로 취급한다.
- **후속 갱신:** 구현 시 2.8의 모듈 목록·계획 타입·fallback·오디오 계획 설명과 관련 명세 참조를 실제 경로에 맞게 수정한다. 실패 실험 및 보고서 근거는 보존한다.

다음 작업자는 9절과 HARNESS 최신 상태, 현재 diff를 먼저 확인한다. **5개 파일 삭제 + 부분 artifact 생성 유지 + 병합 순서 보완**을 적용했다. 중복 ID는 테스트 중심 권장안을 적용했고 런타임 전수 진단은 추가하지 않았다. 커밋·배포는 수행하지 않았다.


## 9. 구현 결과와 검증 기록 (2026-10-01)

4절의 파일 조치를 적용했다. `src/`와 `dev/`에는 삭제한 모듈의 import나 plan 실행 참조가 남아 있지 않다. 2.8의 eventDiff/patch 및 미채택 세분화 설명을 현재 artifact 경로로 정리하고 2.1의 관련 설명도 갱신했다.

구현 중 전체 입력 동등성 검사에서 통합 `markerItems` 역시 기존 artifact에서는 단순 연결되고 전체 builder에서는 정렬된다는 차이를 확인했다. note/global 편집 양쪽에서 통합 배열도 공용 규칙으로 정렬한다. 과거 검토가 비교한 5개 그룹에 더해 현재 Node 테스트는 전체 renderInput을 비교한다.

검증 결과:

- `build`, `test:partial`, `test:analyze`, `test:edit`, `test:layout`, `test:track`, `test:audio`, `test:game`, `test:score`, `test:parse`, `test:examples` 통과.

### 제품 경로 성능 재측정

Chrome 154.0.8037.58, 한 track의 일반 노트, 가운데 1개 변경, viewport/반복 조건은 2절과 같다. 제품의 정렬된 artifact를 양쪽에 동일하게 주고, 보존한 기존 plan/patch 모듈 적용 경로와 현재 직접 renderer 경로를 비교했다. 따라서 아래 기존 경로는 완전한 구 버전 앱 실행이 아니라 **공유 artifact 이후 처리의 대조군**이다.

| 900 | 1.60ms | 0.30ms | 1.10ms |
| 3,000 | 5.10ms | 0.30ms | 2.90ms |
| 9,000 | 17.50ms | 0.50ms | 8.30ms |

3라운드 중앙값의 중앙값이다. 현재 경로의 정렬은 artifact 생성 안으로 이동했으므로 후속 처리 0.50ms만 보고 정렬 비용까지 포함됐다고 해석하면 안 된다. artifact 포함값도 history/UI/audio 처리와 화면 표시 완료 시간은 제외한다. 과거 수치와 환경별 변동을 분리해 읽는다.
